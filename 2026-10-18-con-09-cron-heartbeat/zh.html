Dead Man’s Switch：監控「根本沒有執行」的排程工作

這篇文章要說明，如何用簡單的 heartbeat，找出根本沒有開始執行的排程工作。

前言

排程工作正常運作時，很容易被忽略。報表每天早上出現，備份每天晚上執行，清理工作自動刪除舊資料。排程器逐漸變成背景的一部分。

這會形成一種特殊的監控問題。一般錯誤可能留下 stack trace、失敗狀態或紀錄。但如果排程器根本沒有啟動程式呢？此時可能沒有程序、沒有紀錄，也沒有錯誤事件。失敗的形式是「什麼都沒有發生」。

Dead man’s switch 就是用來處理這種情況。工作只有在完整成功後，才送出完成訊號。獨立的 monitor 會期待訊號在指定時間內抵達。如果沒有收到，就發出 alert。

重點不是那一次 network request，而是從工作外部監控預期結果。「沒有回報錯誤」只是很弱的證據。「預期的完成訊號準時抵達」則是強得多的證據。

看不見的失敗

許多監控系統從 failure event 開始。應用程式捕捉 exception 並回報，排程器記錄 non-zero exit code，紀錄規則搜尋 failed 或 timeout。這些方法都有幫助，但共同前提是：某個東西至少執行到足以回報問題的階段。

排程工作可能在那之前就消失。Schedule 可能被停用，機器可能離線，設定可能損壞，啟動 runtime 所需的 credential 可能無法使用，排程器本身也可能停止。因為工作從未取得控制權，所以無法回報自己的失敗。

因此，一片安靜的 dashboard 可能造成誤判。安靜可能代表健康，也可能代表整條回報路徑都已失效。監控需要一個帶有期限的問題：「這個特定工作，是否在預期時間完成？」

這個問題把「缺席」轉換成可測量的狀態。Monitor 保存最後一次成功 heartbeat，再將該時間與預定排程及允許延遲相比。結果可以是 fresh、late 或 missing。延遲或缺少的訊號，現在就成為其他系統看得見的事件。

概觀

基本流程包含五個部分。排程器觸發工作，工作開始執行，完成真正的處理，驗證結果成功，最後才送出完成 heartbeat。

成功 heartbeat 應放在工作的最後，並且位於真正處理與結果驗證之後。

如果一開始就送 heartbeat，回答的是錯誤問題。它只能證明程式已開始，不能證明工作已完成。工作可能先送訊號，再於中途失敗。Monitor 仍顯示 green，但真正需要的結果並不存在。

訊號也應明確識別工作與環境。每日報表與每週清理不應共用同一個 monitor，因為它們的 schedule、deadline 與處理程序不同。分開的 identity 才能讓 last-success time 具有意義。

Monitor 必須足夠獨立，才能看見失敗。如果工作與 heartbeat checker 使用相同的排程器、主機及通知路徑，一次故障就可能讓兩邊同時停止。完全獨立不一定實際，但避開明顯的單一共同故障點很有價值。

Heartbeat 設計

定義預期時間

Schedule 本身不等於 deadline。整點啟動的工作，可能在幾分鐘後才完成。Monitor 需要一段預期完成區間，包含一般執行時間與少量延遲空間。這個空間應反映實際行為，而不是任意設得很大，最後把失敗藏起來。

對頻繁執行的工作，可以在錯過一次或數次 interval 後發出 alert。對每日工作，可以等到正常完成區間結束。實用原則很簡單：在遺失的結果開始造成影響時警告，但要早於下一個使用者依賴它的時間。

回報成功，而非活動

所有必要步驟成功後，才能送出 heartbeat。如果工作建立檔案，就檢查檔案存在且可使用。如果寫入資料，就驗證相關寫入。如果傳送報表，就依照工作真正承諾的 delivery 判定。最終訊號應代表承諾的結果已發生，而不只是程式跑到了最後一行。

讓失敗維持可見

不要在成功與失敗都會經過的廣泛 cleanup block 中，送出同一個成功 heartbeat。這會讓每次執行都看起來正常。Failure path 可以傳送不同的診斷資訊，但絕不能更新 last-success clock。

讓重送保持安全

Network retry 可能讓同一個 heartbeat 傳送多次。Monitor 應把同一次完成的重複訊號視為無害。真正重要的是最新且有效的成功時間，而不是可能被 retry 放大的計數。

討論

外部 checker 負責設計的另一半。它知道完成訊號應在何時抵達，也會記錄最新 heartbeat。允許區間結束後，它判斷狀態是 fresh 還是 late，並透過操作人員看得到的路徑發出 alert。

Monitor 把缺少的完成訊號，轉換成明確的延遲狀態與 alert。

優點

  • 可以找出從未開始的工作。
  • 衡量 freshness，而不只搜尋錯誤。
  • 為每個排程結果建立清楚的 deadline。
  • 概念簡單，可加入 script、container 與 timer service。

缺點

  • 不恰當的 deadline 會製造雜訊或延後偵測。
  • 若在驗證結果前就送出，heartbeat 仍可能說謊。
  • Checker 與 alert channel 也成為需要測試的基礎設施。
  • Green heartbeat 證明完成，但不一定證明資料品質。

最後一點很重要。報表可以準時完成，但內容仍然錯誤。備份可以成功結束，卻無法還原。Heartbeat monitoring 很適合回答一個狹窄問題：預期的工作是否準時回報成功完成？內容驗證、還原測試與 business-level check 仍是不同的控制措施。

我也希望 alert 能攜帶足以採取行動的 context。實用的 alert 應標示工作名稱、預期區間、上次成功時間，以及下一個檢查位置。不應該讓操作人員只為了確認什麼東西延遲，就必須搜尋好幾個 dashboard。

最後，監控路徑本身也需要測試。安全測試可以暫時不送 heartbeat，或使用專門的 test monitor。目標是證明訊號缺席會產生 alert，而且 alert 會抵達預定位置。只查看一條已設定的規則，不代表這條路徑真的運作。

結論

排程工作可能因為根本沒有執行，而在沒有任何錯誤的情況下失敗。這讓「缺席」成為我們必須偵測的訊號。

Dead man’s switch 使用完成 heartbeat 與獨立 deadline 解決問題。把 heartbeat 放在驗證完成之後，追蹤最後一次成功，並在訊號延遲或缺少時發出 alert。這個問題應保持狹窄且誠實。

更廣泛的教訓很簡單：監控應證明預期結果確實發生。安靜的系統不會自動等於健康的系統。

其他

我想為排程 script 試做一個小型共用 heartbeat wrapper。它會記錄 job identity、start time、completion time 與簡短 result label。成功訊號仍然只在最後送出。

我也想依 dependency 檢視排程工作。共用同一台主機、排程器或通知管道的工作應標示在一起。這會讓共同 failure domain 更容易被看見，也能協助判斷哪裡最需要獨立 monitor。
