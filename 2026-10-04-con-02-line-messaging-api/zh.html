前言

只看聊天畫面時，LINE Bot 似乎很簡單。使用者傳送訊息，Bot 回傳答案。但在這次交換背後，其實有不同的身分與訊息路徑。LINE 平台先接收使用者操作，再透過 HTTPS Webhook 將事件送到 Bot 伺服器。伺服器驗證事件、決定處理方式，然後呼叫 Messaging API。

最重要的設計選擇通常不只是訊息內容，而是這則訊息屬於目前事件的回覆，還是服務對已知目的地發起的新推播。身分模型也很重要。LINE 使用者 ID 不是可以跨越無關 provider 共用的全球帳號鍵。

在選擇 SDK 或建立大型對話框架以前，我會先理解這些界線。當界線清楚時，程式會更小，故障位置也更容易追查。

概觀

基本流程包含三個系統：使用者的 LINE App、LINE 平台，以及 Bot 伺服器。使用者不會直接呼叫 Bot 伺服器。LINE 先接收操作，再將 Webhook 事件傳送到已登錄的 Webhook URL。

Webhook 是輸入，不是最後的回覆通道。Bot 伺服器讀取事件後，還會另外向 LINE 傳送 API 請求。若要立即回應，就使用事件裡的 reply token。若服務稍後主動傳送，就使用 push 方法與 user ID 等目的地。

核心流程：先驗證 Webhook，再選擇回覆目前事件，或推播至已保存的目的地。

這個分離方式提供了清楚的心智模型。Webhook 描述事件。reply token 讓程式在該事件的情境中回覆。user ID 則代表 LINE provider 模型內的目的地。這些值不能互相替代。

Webhook 如何進入系統

支援的事件發生時，LINE 會送出 HTTP POST 請求。使用者訊息只是其中一種。加入好友、封鎖、加入群組、離開、postback 等事件也可能送達。事件物件會說明發生什麼事，並包含下一步需要的情境。

處理前先驗證

公開的 Webhook URL 可能收到來自 LINE 以外的請求。伺服器必須先驗證請求簽章，再信任內文。這項檢查用來確認請求經過 LINE 平台，而且內文在傳輸途中沒有被修改。只有驗證成功後，才應執行商業邏輯。

簽章驗證要使用實際收到的 raw request body。若先解析 JSON 再重新組合，即使資料看起來相同，位元組也可能改變。比較安全的流程是保留原始內文完成簽章檢查，成功後才解析。

快速回應，安全處理

LINE 建議非同步處理事件，避免後續 Webhook 請求被慢速工作阻塞。我會讓同步路徑保持精簡：接收、驗證、安全地記錄必要資訊，然後回傳成功狀態。耗時的資料庫工作或外部 API 呼叫，適合移出請求路徑。

處理 Webhook 時也要預期重複傳送。LINE 文件指出，同一個 Webhook 事件可能不只送達一次，並提供 webhook event ID 供程式偵測重複。處理器應讓重複執行不會破壞結果，也不應假設送達順序永遠等於事件發生順序。

回覆訊息與推播訊息

最常見的兩種傳送路徑，解決的是不同問題。

回覆

回覆與使用者操作直接相關。Webhook 包含 reply token，Bot 會將 token 放進回覆請求。當伺服器能直接回答目前事件時，這條路徑最合適，例如使用者提問、點擊 postback 動作，或加入 Official Account。

token 是事件情境，不是永久地址。我不會把它當成 user ID 保存，也不會用它設計延遲發送的活動。可以採用一個簡單規則：如果這則訊息是因為現在正在處理的事件而存在，優先考慮 reply。

推播

推播由服務發起，而不是由目前的 Webhook 直接發起。出貨通知、提醒，或長時間背景工作的結果，都適合這條路徑。依照支援的方法與情境，請求會指定使用者、群組聊天室或多人聊天室等目的地。

推播功能不能取代良好的同意機制與產品設計。伺服器擁有目的地，不表示每則通知都有價值。我會記錄為什麼收集這個目的地、使用者預期收到什麼，以及這段關係是否仍有效。

不要混用兩種契約

清楚的應用程式可以為發送工作設定明確 mode。reply 工作需要 reply token 與事件參照；push 工作需要目的地與商業理由。把差異清楚放進資料模型，可以避免程式把短暫的事件情境誤當成永久地址。

LINE 使用者 ID 代表什麼

LINE 使用者 ID 以 provider 為範圍。官方文件指出，即使是同一位 LINE 使用者，在不同 provider 下也會取得不同 user ID。同一 provider 底下，即使 channel type 不同，例如 LINE Login 與 Messaging API，該使用者仍會取得相同的 user ID。

這會影響資料庫設計。只保存 LINE user ID 的資料表，隱藏了一項重要前提。我會一併保存 provider 情境；若維運上需要，也保存 channel 情境；若已有帳號連結，還要連到本地應用程式的使用者。

這也會影響移轉規劃。channel 不能被視為可任意移動，而且識別碼意義永遠不變的容器。如果一項服務預計讓 LINE Login 與 Messaging API 對應同一批使用者，就應提早規劃 provider 結構。

顯示名稱不是穩定的關聯鍵。名稱可能變更，也不一定唯一。provider 範圍內的 user ID 適合辨識 LINE 端身分；如果服務要把它連到自己的會員資料，則適合使用明確的 account linking 流程。

討論

優點

  • 事件驅動界線能將 LINE 用戶端與應用程式邏輯分開。
  • reply token 讓即時回應路徑清楚可見。
  • push 方法支援服務主動通知與背景工作結果。
  • provider 範圍的 ID 能連接同一 provider 的 channel，又不會假裝它是全球身分。

缺點與風險

  • 實際識別碼比聊天介面呈現的更多。
  • Webhook 處理需要簽章驗證、重複防護與順序意識。
  • 若未先規劃身分就決定 provider 結構，日後整合會更困難。
  • 單一 API 請求成功，不代表完整使用者體驗正確。

測試時，我會檢查整條路徑。先從真正的 LINE 傳送操作，再確認預期的 Webhook 已到達、簽章通過、事件只處理一次，而且目標訊息確實出現在聊天畫面。管理介面與 endpoint 回應都是有用證據，但使用者真正接收訊息的 channel 才是最後檢查點。

結論

只要分開三個觀念，LINE Messaging API 就容易理解。Webhook 是傳到伺服器的事件。reply token 屬於目前事件。user ID 是 provider 範圍內的目的地，不是 LINE 全域身分。

從這個模型可以自然導出幾項工程規則：先驗證簽章，再將事件交給商業邏輯；讓 Webhook 重複執行仍安全；立即回應事件時使用 reply；服務主動傳送時使用 push；並在資料庫中表達 provider 範圍。

聊天介面可能隱藏這些界線，但可靠的 Bot 程式應讓界線清楚可見。

其他

下一步，我想建立一個小型參考服務，為每次發送記錄 event ID、實際 send mode、provider 情境與最後的傳送決策。我也想主動測試 Webhook 重送與順序顛倒，而不是等到網路問題出現才發現脆弱假設。

另一項值得嘗試的實驗，是在同一 provider 下連接 LINE Login 與 Messaging API channel，記錄哪些身分值可以直接關聯，以及哪些應用程式資料仍需要明確的 account linking。
