LINE Messaging API for Builders: Webhooks, Reply vs Push, and User IDs

In this blog, I will explain the small set of ideas that makes a LINE bot easier to design, debug, and operate.

Introduction

A LINE bot looks simple from the chat screen. A user sends a message, and the bot sends one back. Behind that exchange are several different identities and message paths. The LINE Platform receives the user action. It sends an HTTPS webhook to a bot server. The server verifies the event, decides what to do, and calls the Messaging API.

The most important design choice is usually not the text of the message. It is whether the message is a reply tied to the current event or a new push to a known destination. The identity model matters too. A LINE user ID is not a universal account key that can be copied across unrelated providers.

I find it useful to understand these boundaries before choosing an SDK or building a large conversation framework. When the boundary is clear, the code becomes smaller and failures become easier to locate.

Overview

The basic path has three systems: the user’s LINE app, the LINE Platform, and the bot server. The user does not call the bot server directly. LINE receives the action first and then sends a webhook event to the registered webhook URL.

The webhook is input, not the final response channel. The bot server reads the event and then sends a separate API request to LINE. For an immediate response, it uses the reply token from the event. For a message initiated later by the service, it uses a push method and a destination such as a user ID.

The core flow: verify the webhook first, then choose a reply tied to the event or a push to a stored destination.

This separation gives us a useful mental model. Webhooks describe events. Reply tokens authorize a response in the context of an event. User IDs identify destinations within LINE’s provider model. These values should not be treated as interchangeable.

How Webhooks Enter the System

LINE sends an HTTP POST request when supported events occur. A message from a user is one example. Follow, unfollow, join, leave, postback, and other event types can also arrive. The event object tells the server what happened and includes the context needed for the next action.

Verify before processing

A public webhook URL can receive requests from sources other than LINE. The server should verify the request signature before trusting the body. This check confirms that the request came through the LINE Platform and that the body was not changed in transit. Business logic should run only after that verification succeeds.

Verification must use the raw request body exactly as received. Parsing and rebuilding JSON before verification can change bytes without changing the apparent data. A safer request pipeline keeps the raw body for the signature check and parses it only after the check passes.

Acknowledge quickly and work safely

LINE recommends asynchronous processing so later webhook requests do not wait behind a slow event. I would keep the synchronous path narrow: receive, verify, record enough information safely, and return a successful status. Slow database work or external API calls are better handled away from the request path.

Webhook delivery also requires duplicate-safe processing. LINE documents that the same webhook event can be delivered more than once and provides a webhook event ID for duplicate detection. A handler should therefore make repeated processing harmless. It should also avoid assuming that arrival order always equals event order.

Reply Messages and Push Messages

The two common send paths solve different problems.

Reply

A reply is connected to a user action. The webhook includes a reply token, and the bot sends that token with the reply request. This path is a good fit when the server can answer the current event directly: a user asks a question, taps a postback action, or adds the Official Account.

The token is event context, not a durable address. I would not store it as if it were a user ID, and I would not design a delayed campaign around it. The practical rule is simple: if the message exists because of the event being processed now, reply is the natural first choice.

Push

A push starts from the service rather than from the current webhook. A shipping notice, a reminder, or the result of longer background work can fit this path. The request names a destination, such as a user, group chat, or multi-person chat, depending on the supported method and context.

Push is not a substitute for good consent and product design. The fact that a server has a destination does not mean every notification is useful. I would store why the destination was collected, what messages the user expects, and whether the relationship is still valid.

Do not mix the contracts

A clean application can represent outgoing work with an explicit mode. A reply job requires a reply token and an event reference. A push job requires a destination and a business reason. Making the distinction visible prevents accidental attempts to use an expired event context as a permanent address.

What a LINE User ID Identifies

A LINE user ID is scoped to a provider. The official documentation states that the same LINE user receives different user IDs under different providers. Channels under the same provider can receive the same user ID for that person, including different channel types such as LINE Login and Messaging API.

This affects database design. A table that stores only a bare LINE user ID hides an important assumption. I prefer a key that includes provider context, channel context where operationally useful, and the local application user when an account link exists.

It also affects migrations. Channels cannot simply be treated as movable containers whose identifiers remain universally meaningful. Provider structure should be planned early, especially when one service expects to connect LINE Login and a Messaging API channel for the same users.

A display name is not a stable join key. It can change and may not be unique. The provider-scoped user ID is better for LINE-side identity, while an explicit account-linking flow is better when the service needs to connect that identity to its own customer record.

Discussion

Benefits

  • The event-driven boundary keeps the LINE client separate from application logic.
  • Reply tokens make the immediate-response path explicit.
  • Push methods support service-initiated notifications and background results.
  • Provider-scoped IDs can connect channels under one provider without pretending to be global identities.

Drawbacks

  • There are more identifiers than the chat interface suggests.
  • Webhook handling needs signature verification, duplicate protection, and order-aware logic.
  • A provider layout chosen without identity planning can make later integration harder.
  • A successful API request alone does not prove that the complete user experience is correct.

For testing, I would cover the full path. First, send a real action from LINE. Then confirm that the expected webhook arrived, its signature passed, the event was processed once, and the intended message appeared in the actual chat. Console settings and endpoint responses are useful evidence, but the user-facing channel is the final check.

Conclusion

The LINE Messaging API becomes easier to reason about when I separate three ideas. A webhook is an event delivered to my server. A reply token belongs to the current event. A user ID is a provider-scoped destination, not a universal LINE identity.

From that model, several engineering rules follow naturally: verify signatures before parsing events into business actions, make webhook work duplicate-safe, use replies for immediate event-driven responses, use push for service-initiated messages, and model provider scope in the database.

The chat UI may hide these boundaries, but reliable bot code should make them visible.

Other

Next, I want to build a small reference service that records the event ID, actual send mode, provider context, and final delivery decision for every outgoing message. I also want to test redelivery and out-of-order events deliberately instead of waiting for a network problem to reveal weak assumptions.

A second useful experiment would connect LINE Login and Messaging API channels under one provider, then document exactly which identity values can be joined and which application records still require explicit account linking.
