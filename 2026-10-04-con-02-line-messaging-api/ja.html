はじめに

チャット画面だけを見ると、LINE Bot はとても単純に見えます。ユーザーがメッセージを送り、Bot が返事をします。しかし、その裏側には複数の経路と識別子があります。LINE Platform がユーザー操作を受け取り、Bot サーバーへ HTTPS の Webhook を送ります。サーバーはイベントを検証し、処理を決め、Messaging API を呼び出します。

重要なのは文章だけではありません。その送信が、現在のイベントに結び付いた返信なのか、既知の宛先への新しいプッシュなのかを区別する必要があります。ID の考え方も大切です。LINE ユーザー ID は、関係のない provider 間で共通利用できる万能なアカウントキーではありません。

私は SDK や大きな会話フレームワークを選ぶ前に、まずこの境界を理解するのがよいと考えています。境界が明確なら、コードは小さくなり、障害箇所も追いやすくなります。

概要

基本の経路には、ユーザーの LINE アプリ、LINE Platform、Bot サーバーという三つのシステムがあります。ユーザーが Bot サーバーを直接呼ぶわけではありません。LINE が操作を受け取り、登録済み Webhook URL にイベントを送ります。

Webhook は入力であり、最終的な返信経路そのものではありません。Bot サーバーはイベントを読み、その後に LINE へ別の API リクエストを送ります。その場で返答するならイベント内の reply token を使います。サービス側から後で送るなら、push の送信方法と user ID などの宛先を使います。

基本の流れ：最初に Webhook を検証し、イベントへの返信か保存済み宛先へのプッシュかを選びます。

この分離から、分かりやすいモデルが得られます。Webhook はイベントを表します。reply token は、そのイベントの文脈で返信するために使います。user ID は LINE の provider モデル内の宛先を表します。これらは交換可能な値ではありません。

Webhook が届く仕組み

対応するイベントが発生すると、LINE は HTTP POST リクエストを送ります。ユーザーのメッセージは一例です。友だち追加、ブロック、グループ参加、退出、postback などのイベントも届きます。イベントオブジェクトには、何が起きたかと、次の動作に必要な文脈が含まれます。

処理前に検証します

公開 Webhook URL には LINE 以外からもリクエストが届く可能性があります。本文を信用する前に署名を検証します。これにより、リクエストが LINE Platform を経由し、転送中に本文が変更されていないことを確認できます。業務処理は検証成功後にだけ実行します。

署名検証には、受信したままの raw request body を使う必要があります。先に JSON を解析して組み立て直すと、見た目のデータが同じでもバイト列が変わることがあります。raw body で検証し、成功してから解析する順序が安全です。

すばやく応答し、安全に処理します

LINE は、後続リクエストが遅い処理を待たないよう、イベントの非同期処理を推奨しています。同期経路は、受信、検証、必要情報の安全な記録、成功ステータスの返却までに絞るのがよいでしょう。時間のかかる資料庫処理や外部 API は、リクエスト経路から分離します。

Webhook は重複を前提に扱う必要もあります。公式資料では、同じイベントが複数回配信される可能性があり、重複検出用の webhook event ID が提供されています。繰り返し処理されても結果が壊れない設計が必要です。また、受信順序が常に発生順序と一致するとは限りません。

返信メッセージとプッシュメッセージ

よく使う二つの送信経路は、異なる問題を解決します。

返信

返信はユーザー操作と結び付いています。Webhook に reply token が含まれ、Bot は返信リクエストにその token を指定します。ユーザーの質問、postback 操作、友だち追加など、現在のイベントへ直接応答できる場合に適しています。

token はイベントの文脈であり、永続的な住所ではありません。user ID のように保存したり、遅延キャンペーンの基盤にしたりすべきではありません。「今処理しているイベントが理由で送るメッセージ」なら、まず reply を検討するという単純な規則が役立ちます。

プッシュ

プッシュは現在の Webhook ではなく、サービス側から始まります。発送通知、リマインダー、時間のかかるバックグラウンド処理の結果などに向いています。利用する方法と文脈に応じて、ユーザー、グループチャット、複数人チャットなどの宛先を指定します。

プッシュ機能があっても、同意やプロダクト設計が不要になるわけではありません。サーバーが宛先を持っていても、すべての通知が有益とは限りません。なぜ宛先を保存したか、ユーザーが何を期待しているか、関係が現在も有効かを管理したいところです。

契約を混ぜません

送信ジョブに明示的な mode を持たせると設計が明確になります。reply ジョブには reply token とイベント参照が必要です。push ジョブには宛先と業務上の理由が必要です。区別を型や資料庫に表すことで、一時的なイベント文脈を永続的な宛先として使う事故を防げます。

LINE ユーザー ID が示すもの

LINE ユーザー ID は provider 単位で発行されます。公式資料によれば、同じ LINE ユーザーでも provider が違えば別の user ID になります。同じ provider 配下なら、LINE Login と Messaging API のように channel type が異なっても、同じ人に同じ user ID が発行されます。

これは資料庫設計に影響します。user ID だけを保存する表は、大切な前提を隠します。私は provider の文脈、運用上必要なら channel の文脈、アカウント連携があるなら自社アプリの user を一緒に管理したいと考えます。

移行にも関係します。channel を、どこへでも移せて識別子の意味も変わらない容器だとは考えられません。同じユーザーに LINE Login と Messaging API をつなぐ予定があるなら、provider 構成を早い段階で設計すべきです。

表示名は安定した結合キーではありません。変更されることがあり、一意とも限りません。LINE 側の識別には provider 単位の user ID を使い、自社の会員記録と結び付ける必要がある場合は、明示的な account linking を使う方が安全です。

考察

利点

  • イベント駆動の境界により、LINE client とアプリ処理を分離できます。
  • reply token によって即時返信の経路が明確になります。
  • push はサービス起点の通知やバックグラウンド処理結果に対応します。
  • provider 単位の ID は、世界共通 ID と誤解させずに同一 provider 内の channel を接続できます。

注意点

  • チャット画面から想像するより多くの識別子があります。
  • Webhook には署名検証、重複対策、順序を意識した処理が必要です。
  • ID 設計なしに provider 構成を決めると、後の統合が難しくなります。
  • API リクエストの成功だけでは、ユーザー体験全体の正しさを証明できません。

テストでは経路全体を確認したいです。まず実際の LINE から操作します。期待する Webhook が届いたか、署名が通ったか、イベントが一度だけ処理されたか、意図したメッセージが実際のチャットに表示されたかを確認します。管理画面や endpoint の応答も証拠になりますが、最後の確認場所はユーザーが使う channel です。

まとめ

三つの概念を分けると、LINE Messaging API は理解しやすくなります。Webhook はサーバーへ届くイベントです。reply token は現在のイベントに属します。user ID は provider 単位の宛先であり、LINE 全体の共通 ID ではありません。

このモデルから、自然に設計ルールが導けます。業務処理の前に署名を検証し、Webhook を重複しても安全に処理し、イベントへの即時応答には reply、サービス起点の送信には push を使い、資料庫には provider の範囲を表します。

チャット UI は境界を隠しますが、信頼できる Bot コードでは境界を明示すべきです。

今後

次は、すべての送信について event ID、実際の送信 mode、provider 文脈、最終判断を記録する小さな参考サービスを作りたいです。ネットワーク障害を待つのではなく、Webhook の再配信と順序逆転も意図的にテストしたいと考えています。

もう一つの実験として、同じ provider 配下に LINE Login と Messaging API channel を用意し、どの識別子を結合できるか、どの自社記録には明示的な account linking が必要かを整理したいです。
