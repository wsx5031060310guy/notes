Background Jobs on macOS: launchd and Privacy Permissions

A scheduled command can work in Terminal and still fail under launchd because scheduling and file access are two separate systems.

Introduction

In this blog, I will explain how I think about scheduled background work on macOS. The scheduler is launchd. The access-control layer is the macOS privacy system. A reliable job has to satisfy both.

This distinction matters because an interactive shell is not the same execution context as a background process. My Terminal app may already have permission to read a folder. A tool launched by launchd may not have the same permission. The command can be correct, the schedule can fire, and the job can still be unable to read its input.

The useful question is therefore not only, “Did launchd start the job?” I also need to ask, “Which executable tried to open the file, and was that executable allowed to do it?”

Overview

Apple describes launchd as the preferred way to start per-user background processes. These processes are called user agents. A user agent belongs to a logged-in user and runs only while that user is logged in. System-level daemons have a different scope and location.

A launchd job is described by a property list, usually called a plist. The configuration gives the job a unique label and provides the program arguments. It can also describe when the job should run and where standard output and standard error should go.

For a calendar schedule, a job can use StartCalendarInterval. The schedule is only one part of the design. The job also needs absolute paths, predictable working data, useful logs, and permission to reach every required file.

Proposed design: separate the scheduling path from the protected-folder permission check.

How a Launch Agent Is Defined

Use a small plist

I prefer a plist that does as little as possible. It should identify the job, call one stable executable or script, define the schedule, and send output to known log files. The business logic belongs in the script, not in a long configuration value.

A per-user agent is normally placed in the user’s Library/LaunchAgents directory. Its Label should be unique. ProgramArguments should hold the executable and each argument as separate values. This avoids depending on shell parsing that may not happen at all.

Use explicit paths

A background job should not assume the same PATH, current directory, aliases, or shell setup that I see in Terminal. I use absolute paths for the executable, script, input, output, and logs. If the script needs a working directory, I set it deliberately or change to it inside the script.

Keep evidence

Standard output and standard error should be written somewhere I can inspect. An exit code tells me that something failed. The error text tells me whether the cause was a missing command, a bad path, invalid input, or denied access. A schedule without durable logs is difficult to debug.

Why Privacy Permissions Change the Result

macOS protects user data through privacy controls. Apple lists Desktop, Documents, Downloads, iCloud Drive, network volumes, and removable volumes among locations covered by file-access controls. Access can depend on the app or process that requests it.

This explains a common surprise. I run a script manually and it succeeds. Later, launchd starts the same script and it fails at the first protected file. The script text did not change. The responsible process and its authorization context did.

Files & Folders permission grants access to specific locations. Full Disk Access is broader. Apple describes it as access to all files on the computer, including data from other apps, backup data, and certain administrative settings. That makes it powerful, but it also makes it a poor default for every automation tool.

The setting is managed in System Settings under Privacy & Security. The important detail is to authorize the specific tool that needs access. Granting permission to Terminal does not automatically prove that a background interpreter, command-line tool, or wrapper has the same access.

Demo: A Safer Design

Step 1: choose an ordinary workspace

I would keep automation scripts, temporary files, and logs outside protected personal folders when the job does not need those folders. This reduces permission prompts and narrows the amount of private data the job can reach.

Step 2: isolate the protected input

If the job must read a protected location, I would make that dependency explicit. I would avoid giving broad access to unrelated launchers. I would identify the actual executable that opens the file and grant only the access the workflow requires.

Step 3: test in the real context

Running the script in Terminal is a useful unit check, but it is not the final test. I would load the agent, trigger it through launchd, then inspect both output streams and the expected side effect. The final check should verify the file, record, or message that the job was supposed to create.

Step 4: fail clearly

The script should check that required input is readable before doing expensive work. If access is denied, it should stop with a direct message that names the path category and the executable that needs review. It should not quietly treat missing input as an empty result.

Benefits and Drawbacks

Benefits

  • launchd gives macOS one managed place for user agents and daemons.
  • A short plist makes the schedule and command easy to review.
  • Explicit log paths preserve evidence from unattended runs.
  • Least-privilege file placement reduces unnecessary access to personal data.

Drawbacks

  • The interactive shell and launchd environment can behave differently.
  • Privacy failures may look like ordinary file-not-found or permission errors.
  • Full Disk Access can solve an access problem while granting much more authority than the job needs.
  • A user agent depends on the user session, so it is not a replacement for every system service.

Discussion

I see launchd and privacy controls as complementary. launchd answers when and how a process starts. Privacy controls answer what data that process may reach. Neither layer can replace the other.

The safest troubleshooting order is simple. First, confirm that launchd loaded and started the intended job. Second, inspect standard error. Third, check absolute paths and the runtime environment. Fourth, review privacy permission for the executable that actually touches the protected data. Finally, verify the real output, not only the process status.

I would not begin by granting Full Disk Access. I would first move non-sensitive working files out of protected folders and reduce the job’s data requirements. Broad access should be a deliberate exception, not the standard repair.

Conclusion

A background job on macOS can be scheduled correctly and still be blocked from its data. Reliable automation needs a small launchd definition, explicit paths, durable logs, a real-context test, and the narrowest practical permission.

The key lesson is to debug the two systems separately. Confirm that the scheduler ran. Then confirm that the responsible executable was allowed to read and write what the job needed.

Other
