One Full-Width Parenthesis Made My Bash Script Crash Exactly When It Mattered

In this blog, I will describe how punctuation next to a Bash variable broke a scheduled script only when its warning path finally ran.

Introduction

I had a scheduled shell script that ran with set -u in a UTF-8 locale. Its messages were written in Chinese. Most runs completed normally, so the script looked stable.

Three messages in its error branches used a line shaped like this: echo "今天（$DATE）…". The full-width parenthesis looked harmless. It was normal Chinese punctuation, and it was inside a quoted string. Yet when one of those branches ran, Bash stopped with an unbound variable error.

The awkward part was the timing. Those lines were not on the normal path. The script failed on two days in October, exactly when it needed to explain that something else was wrong. On one of those days, the expected input was missing. Instead of printing that warning, the warning itself crashed.

The script that usually worked

Background

I used set -u so that an unset variable would stop the script. This is useful because a typo in a variable name should not quietly become an empty string. If a script expects DATE, continuing without it can produce a misleading file name, query, or message.

The script also ran in a UTF-8 locale and printed Chinese status text. Neither choice was unusual by itself. The problem appeared at the boundary between Bash variable parsing and a non-ASCII character placed immediately after the variable name.

The risky line was easy to read as a human. I saw $DATE, followed by a closing full-width parenthesis. Bash did not separate those bytes in the way I expected. It read the first byte of that parenthesis as part of the variable reference. Under set -u, the resulting name was unset, so the shell stopped.

The error branch reached a Chinese message, Bash misread the variable boundary, and the warning path crashed.

Why the failure was confusing

The happy path hid the bad lines

There were three affected lines, and every one of them was in an error branch. A normal run never evaluated them. That meant repeated successful runs did not test the code that explained failures.

This is a common weakness in operational scripts. The main command may work every day, while cleanup, warning, or recovery code remains untouched. The first real test of that code arrives during an incident. If the reporting path has its own bug, the script can hide the event that activated it.

That is what happened here. The missing input was the condition I needed to understand. The shell error pointed at a strange variable name instead. It turned a useful warning into a parser puzzle.

The text looked correct

The line did not look like a typo. The punctuation was valid for the sentence, the quote marks were balanced, and the variable name itself was correct. Reading the source visually encouraged me to treat the parenthesis as ordinary text.

The error message was the better clue. It showed that Bash believed the variable name continued into the following bytes. Once I treated this as a variable-boundary problem instead of a locale or display problem, the fix became small.

The fix

Use braces at the boundary

I changed the variable to ${DATE} wherever it touched non-ASCII text. The repaired line has the shape echo "今天（${DATE}）…". Braces tell Bash exactly where the parameter name ends. The punctuation then remains part of the surrounding string.

This is clearer even when the next character is ASCII. For example, ${FILE}_backup says that the variable is FILE, while $FILE_backup asks Bash for a different variable named FILE_backup. Braces remove the guess.

I also scanned shell scripts for an unbraced variable followed by a non-ASCII byte:

LC_ALL=C grep -nE '\$[A-Za-z_][A-Za-z0-9_]*[^ -~]' *.sh

With LC_ALL=C, the scan treats the input byte by byte. The expression looks for a dollar sign, a shell-style variable name, and then a character outside printable ASCII. It is a focused check for this boundary pattern. It is not a full shell parser, so I still review every match before changing it.

Discussion

Benefits of set -u

I still want set -u. It turned an ambiguous string expansion into a visible failure. Without it, a malformed reference could produce empty or incorrect output and let the script continue. A hard failure is easier to investigate than a quiet lie.

The setting also pushes me toward explicit variable boundaries. That makes maintenance safer when messages mix code identifiers with Chinese, Japanese, or other text.

Drawbacks of relying on the normal path

A scheduled job can run successfully many times without exercising its failure messages. Success history therefore tells me little about branches that only run when an input is absent or a command fails.

A better test should invoke those branches on purpose. For this script, one useful case would omit the expected input and verify that the warning appears without a second shell error. Another would cover each of the other two error lines. These are recommendations for the next test pass, not tests I had already added.

Code and prose share a boundary

Localized shell messages mix two grammars. The reader sees a sentence. Bash first sees parameter expansion rules. Quoting protects spaces and many special characters, but it does not always communicate the intended end of an unbraced parameter name. Braces make that boundary explicit.

I now treat a variable that touches surrounding text as a small review signal. The safest form is usually ${NAME}, especially beside non-ASCII punctuation. It costs two characters and saves time when an unusual branch finally runs.

Conclusion

The script did not fail because Chinese text is unsafe in Bash. It failed because an unbraced variable touched a full-width character and Bash read the boundary differently from me. set -u then stopped the script.

The fix was to write ${DATE}, scan for similar boundaries, and pay attention to code that only runs during failures. The broader lesson for me is simple: an error message is executable code too. It needs a real test before the day I depend on it.

Other

I want to add cases that enter every warning branch and assert the visible message. I also want to keep the byte-oriented scan as a lightweight review check, while remembering that it can only find candidates. A shell-aware linter or a direct branch test would provide stronger evidence.

I also want failure notifications to preserve the original cause. If warning code fails, the report should still make the missing input or failed command visible. That design is not in the current fix, but it is the next reliability improvement I would evaluate.
