CI 顯示綠燈，但有 973 項測試從未在其中執行

這篇文章要說明，一個顯示綠燈的 pull request，如何掩蓋 973 項測試其實從未在 CI 執行的事實。

背景

我開了一個 pull request，看到所有檢查都轉為綠燈。這個狀態看起來令人放心：程式碼通過 Python 語法檢查，預覽部署也順利完成，頁面上沒有任何紅色標記。

但檢查清單裡並沒有專案的測試套件。專案共有 973 項測試，而且一直都只在一台開發者電腦上執行。Pull request 之所以顯示綠燈，只是因為現有的檢查都通過了；這並不表示應用程式的行為已在 CI 中接受測試。

把這件事寫下來之後，差別似乎很明顯。但面對熟悉的綠燈狀態時，卻不一定會立刻察覺。顏色只概括結果，不會說明結果涵蓋的範圍。真正提供範圍資訊的，是顏色旁邊的檢查名稱。

綠燈真正代表什麼

這個 pull request 有兩項實用的檢查。Python 語法檢查可以找出無效的 Python 語法；預覽部署則可以確認預覽版本的建置與部署流程是否完成。兩者都有價值，但都沒有執行測試套件。

我在心裡把「所有檢查都通過」擴大解讀成「這項變更已經過測試」，然而系統回報的並不是這件事。它只表示所有已設定的檢查都通過。缺少的測試工作不可能失敗，也不可能提供任何佐證。

測試數量越多，這個缺口越值得注意。專案裡已有 973 個測試案例，涵蓋了大量預期行為，但它們的保護範圍只到那台一直用來執行測試的開發者電腦為止。儲存庫當時還無法證明，一個乾淨的 CI runner 也能執行這些測試。

第一個教訓是逐一閱讀每項必要檢查的名稱。「語法」不等於「測試」，「預覽」也不等於「測試」。只有在我知道一組綠燈裡實際包含哪些工作時，這組狀態才有意義。

加入缺少的測試工作

我把測試套件加入 GitHub Actions。這不只是把既有的本機指令搬進 YAML 檔案而已。託管的 runner 從不同的環境開始執行，也因此揭露了那台開發者電腦上原本看不見的假設。

實際過程從兩項未含測試的綠燈檢查，推進到包含獨立安裝指令與擴充套件版本檢查的測試工作。

因此，最初幾次 CI 執行即使沒有得到完全通過的測試結果，仍然很有用。它們指出了專案對本機狀態、本機套件版本與 shell 行為的依賴。這些失敗不是隨機發生的 CI 問題，而是關於可攜性的資訊。

要開始釐清問題，我不需要大幅重新設計 CI。我需要的是讓測試指令在全新環境中執行，並讓設定步驟如實回報失敗。

三項環境差異

資料庫位址不同

資料庫安全檢查看到的是透過 TCP 連線的「::1/128」，而不是它預期的位址。這項檢查肩負重要任務：防止測試誤用不該使用的資料庫。在開發者電腦上，它對位址的假設成立；到了 runner，連線卻解析成不同的結果。

正確做法不是移除安全檢查。這項不一致反而證明，規則綁定了特定環境的網路表示方式。CI 讓這個隱藏假設浮上檯面。安全規則仍須保護資料庫，但應根據實際連線情境進行判斷，而不是只比對一個記住的位址。

套件提供的擴充套件版本太舊

Ubuntu 的 pgvector 套件提供 0.6 版，但測試需要該套件沒有提供的較新功能。本機開發環境已具備那些功能，所以先前沒有出現這個相依性缺口。

這是自動化流程中常見的界線。依名稱安裝套件，只能證明某個東西已安裝，無法證明安裝的版本具備應用程式所需的能力。測試實際使用到這些功能後，runner 才讓需求變得清楚。

從原始碼建置時選到了不存在的編譯器

接著改從原始碼建置 pgvector，流程卻嘗試使用 runner 上不存在的 clang-19。這也是一項本機假設。從原始碼建置不只依賴原始碼，也依賴選用的編譯器與 runner 的工具鏈。

這三項差異都源自同一個改變：換到新環境執行既有測試。資料庫檢查、擴充套件與編譯器選擇，在同一台電腦上原本可以一起運作。CI 則把「在這裡能用」與「能在乾淨的 runner 重現」分開來看。

掩蓋失敗的 shell 步驟

最危險的問題不是無法取得某個套件，而是設定步驟在其中一部分失敗後，外觀看來仍然成功。

該步驟使用「make && sudo make install」。在實際觀察到的執行結果中，「make」失敗時工作並未失敗。也就是說，即使無法證明要求的擴充套件已正確建置並安裝，工作流程仍可能繼續。

我把每個指令改到各自獨立的一行，然後加入已安裝擴充套件的版本檢查。設定流程不再只依賴安裝指令最後呈現的結果；它必須顯示每項操作，並驗證測試實際會使用的產出。

這是一項目的明確的小改動。把指令拆成獨立行後，更容易在工作流程與紀錄中閱讀執行順序。版本檢查則回答了更重要的問題：runner 實際安裝的是哪個版本的擴充套件？

設定步驟成功，不代表環境正確。結束狀態碼不可或缺，但進一步驗證，才能填補「嘗試執行指令」與「應用程式實際取得的相依套件」之間的落差。

討論

優點

把 973 項測試放進 GitHub Actions 後，它們從本機佐證變成團隊共享的佐證。Pull request 現在可以在全新環境中檢驗應用程式行為，不再只依賴語法與部署檢查。

這些失敗也改善了設定流程。它們找出位址假設、套件能力缺口、編譯器不一致，以及未依預期回報失敗的 shell 步驟。CI 用一段可見且可重現的流程呈現每個問題，讓討論更容易聚焦。

缺點與限制

CI 測試工作會增加設定時間與維護成本。資料庫服務、擴充套件與建置工具都必須正確宣告。Runner 映像檔可能與開發者電腦不同，而套件儲存庫也不一定提供專案需要的功能。

即使加入測試工作，CI 也不會讓每次綠燈狀態自動變得完整。它的價值仍取決於執行了哪些測試、哪些指令可能被略過，以及代表了哪一種環境。原本的教訓依然適用：閱讀檢查名稱，並確認每項檢查實際做了什麼。

結論

這個 pull request 顯示綠燈，但綠燈只描述語法檢查與預覽部署，沒有涵蓋 973 項測試，因為當時沒有任何 CI 工作執行它們。

加入測試後，四項隱藏假設隨之浮現：安全檢查預期的資料庫位址、比測試需求更舊的 Ubuntu pgvector 套件、選用了不存在編譯器的原始碼建置流程，以及建置失敗時未停止工作的 shell 步驟。把指令分成獨立行，再檢查已安裝的擴充套件版本，讓設定流程更加明確。

我得到的主要教訓很簡單：不能只看 CI 的顏色。我應該逐一閱讀檢查名稱，確認測試套件確實存在，並驗證測試實際使用的環境。

其他

我希望往後審查 pull request 時，先從涵蓋範圍開始：執行了哪些檢查、涵蓋哪些行為，以及驗證了哪些相依套件。綠燈狀態應該是這段閱讀過程的終點，而不是起點。
