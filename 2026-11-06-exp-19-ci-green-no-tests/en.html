CI Was Green, but 973 Tests Had Never Run There

In this blog, I will describe how a green pull request hid the fact that 973 tests had never run in CI.

Background

I opened a pull request and saw every check turn green. The status looked reassuring. The code passed a Python syntax check, and the preview deployment completed. Nothing on the page was red.

But the check list did not include the project test suite. The project had 973 tests, and they had only ever run on one developer machine. The pull request was green because the checks that existed had passed. It did not mean that the application behavior had been tested in CI.

This distinction sounds obvious after I write it down. It was less obvious while looking at a familiar green status. A color summarizes outcomes. It does not explain the scope of those outcomes. The names beside the color contain that information.

What green actually meant

The pull request had two useful checks. The Python syntax check could catch invalid Python syntax. The preview deployment could show whether the preview build and deployment path completed. Both checks had value. Neither one ran the test suite.

I had mentally expanded “all checks passed” into “the change was tested.” That was not what the system reported. It only reported that all configured checks passed. A missing test job cannot fail. It also cannot provide evidence.

The number of tests made the gap more important, not less. There were 973 test cases already available. They represented a large body of expected behavior, but their protection stopped at the developer machine where they had always run. The repository did not yet prove that a clean CI runner could execute them.

The first lesson was to read the name of every required check. “Syntax” is not “tests.” “Preview” is not “tests.” A green group is meaningful only when I know what is inside the group.

Adding the missing test job

I added the test suite to GitHub Actions. This did more than move an existing local command into a YAML file. A hosted runner started from a different environment. That difference exposed assumptions that one developer machine had made invisible.

The observed path moved from two green checks with no tests to a test job with separate install commands and an extension version check.

The first CI runs were therefore useful even when they did not reach a clean test result. They showed where the project depended on local state, local package versions, and shell behavior. Those failures were not random CI problems. They were information about portability.

I did not need a large CI redesign to begin learning. I needed the test command to run in a fresh environment and the setup steps to report failure honestly.

Three environment differences

The database address was different

A database safety check saw “::1/128” over TCP instead of the address it expected. The check was doing an important job: it tried to prevent tests from using the wrong database. On the developer machine, its address assumption had held. On the runner, the connection resolved differently.

The correct response was not to remove the safety check. The mismatch showed that the rule was tied to one environment’s network representation. CI forced that hidden assumption into view. A safety rule still needs to protect the database, but it must evaluate the actual connection context rather than one remembered address.

The packaged extension was too old

The Ubuntu pgvector package supplied version 0.6. The tests needed features newer than that package provided. Local development had an environment where those features were available, so this dependency gap had not appeared there.

This is a common boundary in automation. Installing a package by name proves that something was installed. It does not prove that the installed version has the capabilities the application expects. The test runner made the required capability visible because the tests exercised it.

The source build chose a missing compiler

Building pgvector from source then tried to use clang-19, which was absent on the runner. This was another local assumption. A source build depends on more than source code. It also depends on the selected compiler and the runner’s toolchain.

These three differences came from one change: running the existing tests somewhere new. The database check, extension package, and compiler selection had all worked together on one machine. CI separated “works here” from “can be reproduced on a clean runner.”

A shell step that hid failure

The most dangerous problem was not an unavailable package. It was a setup step that appeared to succeed after part of it failed.

The step used “make && sudo make install.” In the observed run, the job did not fail when “make” failed. That meant the workflow could continue without proving that the requested extension had been built and installed correctly.

I changed each command to its own line. I then added a check for the installed extension version. The setup no longer depended only on the final appearance of an install command. It had to expose each operation and verify the artifact that the tests would use.

This was a small change with a clear purpose. Separate lines made the sequence easier to read in the workflow and logs. The version check answered the more important question: what extension did the runner actually install?

A successful setup step is not the same as a correct environment. Exit status is necessary, but verification closes the gap between an attempted command and the dependency the application receives.

Discussion

Benefits

Putting the 973 tests in GitHub Actions changed them from local evidence into shared evidence. A pull request could now exercise application behavior in a fresh environment instead of relying only on syntax and deployment checks.

The failures also improved the setup path. They identified an address assumption, a package capability gap, a compiler mismatch, and a shell step that did not fail as expected. Each issue was easier to discuss because CI reproduced it in one visible sequence.

Drawbacks and limits

A CI test job adds setup time and maintenance. Database services, extensions, and build tools must be declared accurately. Runner images can differ from a developer machine, and package repositories may not provide the capabilities a project needs.

CI also does not make every green status complete. Even after a test job exists, its value depends on which tests run, which commands can be skipped, and which environment is represented. The same lesson still applies: read the check names and inspect what each check does.

Conclusion

The pull request was green, but green described only a syntax check and a preview deployment. It did not describe the 973 tests because no CI job ran them.

Adding the tests revealed four hidden assumptions: a database address expected by a safety check, an Ubuntu pgvector package older than the tests needed, a source build that selected a missing compiler, and a shell step that did not stop the job when the build failed. Moving commands onto separate lines and checking the installed extension version made the setup more explicit.

My main lesson is simple. I should not read only the color of CI. I should read every check name, confirm that the test suite is present, and verify the environment that the tests actually use.

Other

I want future pull request reviews to begin with scope: which checks ran, which behavior they covered, and which dependencies they verified. A green status is the end of that reading process, not the beginning.
