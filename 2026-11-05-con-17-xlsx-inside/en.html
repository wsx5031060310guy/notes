What Is Inside an XLSX File, and Why a Cut-Off Save Breaks It

In this blog, I will open the XLSX box and explain why one interrupted save can make a whole workbook look unreadable.

Introduction

An XLSX file looks like one document in Finder or File Explorer. Internally, it is a package. The package contains several XML files and other resources inside a ZIP archive. Those parts describe the workbook, worksheets, strings, styles, and relationships between files.

This matters when a save is interrupted. A spreadsheet application may have written much of the new content but not completed the archive. The file can then fail with a message such as “File is not a zip file.” That message sounds as if every cell has disappeared. Sometimes the useful XML parts are still present. The package around them is what failed.

I do not treat that as a promise of recovery. A damaged archive may contain complete parts, partial parts, or no usable parts. The first job is to preserve the original and inspect what remains.

Overview

Office Open XML is the document format family behind XLSX. ECMA-376 defines its vocabularies, document representation, and packaging. The packaging rules let one logical document contain many named parts.

A typical workbook can contain a workbook definition, one XML part per worksheet, style information, relationships, and content-type declarations. It may also contain shared strings, drawings, charts, comments, and other parts. The exact set depends on the workbook.

An XLSX reader needs both readable package parts and enough ZIP structure to locate them.

The diagram is intentionally simple. XLSX is not one long XML document. It is a group of parts, and the ZIP layer gives readers a directory of those parts.

The ZIP layer

A ZIP archive stores entries such as files and folders. Python’s zipfile module can list entries, read them, and test whether a file looks like a valid ZIP archive. When the structure is valid, ZipFile gives each member a name and metadata through ZipInfo.

ZIP readers normally depend on the central directory near the end of the archive. That directory tells the reader which entries exist and where to find them. A final record points to the central directory. If a write stops before those records are complete, a normal reader may not know how to navigate the archive even when earlier local file records and compressed data remain on disk.

This explains the confusing symptom. The operating system can see a large file. A hex viewer may show XML names and readable text. Yet Excel, openpyxl, or zipfile may reject it because the package index is missing or inconsistent.

Renaming the file from .xlsx to .zip does not repair anything. The rename only makes the real format easier to recognize. A copy can be inspected with archive tools, while the original should remain untouched.

The XML parts

The root file [Content_Types].xml tells consumers which content types appear in the package. Relationship files connect parts. The workbook part identifies sheets and uses relationships to point toward their worksheet parts. Worksheet XML contains rows, cells, formulas, and references to values.

Text needs special attention. Some workbooks use a shared string table. In that design, a cell can store an index, and the actual text lives in a separate sharedStrings.xml part. Recovery then needs both the worksheet and the matching string table. If the index survives but the string table does not, the cell’s text cannot be reconstructed from that index alone.

Other workbooks use inline strings. The text is stored directly inside the cell element in the worksheet XML. Inline strings can make a worksheet more self-contained during recovery, although formulas, formatting, relationships, and other workbook behavior still depend on other parts.

Styles are separate too. A recovered cell value does not guarantee that its date, currency, percentage, or visual formatting will return correctly. The number in the cell and the style that tells an application how to display it are different pieces of information.

Why a cut-off save breaks the package

Saving a workbook is not the same as appending a plain text line. The writer creates or replaces package parts, writes ZIP entry data, and finishes the archive metadata. If the process stops during that sequence, the result depends on the exact interruption point.

An early interruption may leave a short file with little useful content. A later interruption may leave many complete XML entries but an incomplete central directory. Another failure may preserve the directory while truncating one worksheet entry. These cases look similar to a user because the workbook will not open, but the recovery options differ.

Writing directly over the only good copy increases the risk. A safer design writes a new workbook to a temporary file in the same directory, completes and validates it, then replaces the target. This does not make every storage failure impossible. It does keep an interrupted write from immediately destroying the last complete file in the common case.

Recovery with Python

I would start by copying the damaged file and working only on the copy. Then I would ask zipfile.is_zipfile whether Python recognizes it. If it does, I would open it with ZipFile, list the members, and run the archive test method. That separates a package that opens but has a damaged member from one whose ZIP structure cannot be opened at all.

If the archive opens, I would inspect [Content_Types].xml, the workbook relationships, worksheet parts, and the string representation. I would not begin by loading it into openpyxl and saving it again. openpyxl is useful for valid or sufficiently valid workbooks, but a save creates a new interpretation of the workbook. It is not a forensic copy operation.

If zipfile rejects the package, recovery becomes a lower-level task. An archive repair tool may rebuild directory information from surviving local records. After repair, I would extract the package into a new directory and parse XML defensively. I would expect missing parts and broken relationships. I would also treat formulas, external links, macros, images, and styles as separate recovery questions rather than assuming that recovered cell values mean the workbook is complete.

For data recovery, a small script can walk worksheet rows and resolve either inline strings or shared-string indexes. The script should log every skipped cell and every missing dependency. It should write recovered data to a new file. It should never overwrite the damaged source.

Discussion

Benefits of understanding the package

The package model turns a vague “Excel file is broken” problem into smaller checks. Can the ZIP directory be read? Which members exist? Does the workbook point to the worksheets? Are strings inline or shared? Are cell values intact even if styles are gone?

It also helps with normal engineering. A program that creates XLSX files can validate the completed temporary file before replacement. Tests can interrupt a save and confirm that the previous workbook remains readable.

Drawbacks and limits

XML recovery can preserve data while losing behavior. A workbook may depend on formulas, named ranges, charts, links, validation rules, or formatting. Reading visible cell values is only one layer.

There is also a security concern. A damaged or untrusted workbook is still untrusted input. Python’s zipfile documentation warns about resource limits during decompression, and openpyxl documents XML-related risks. Recovery tooling should limit file sizes, extracted paths, entry counts, and memory use. It should not blindly extract archive names into arbitrary paths.

Conclusion

An XLSX file is a ZIP package of connected parts. Worksheet data, shared strings, styles, relationships, and content declarations each have a role. A cut-off save can break the directory that ties the archive together even when some XML remains.

The practical response is simple: preserve the source, inspect the ZIP layer, identify surviving parts, and recover into a new file. For prevention, write to a temporary file and replace the target only after the new package is complete and readable.
