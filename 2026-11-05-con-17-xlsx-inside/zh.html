XLSX 檔案裡有什麼，以及儲存中斷為何會破壞整份檔案

這篇文章會拆開 XLSX 的內部結構，說明為什麼一次未完成的儲存，可能讓整份活頁簿看起來無法讀取。

前言

XLSX 在 Finder 或 File Explorer 裡看起來是一份文件，但它的內部其實是一個封裝。ZIP 壓縮檔裡放了多個 XML 檔案與其他資源，分別描述活頁簿、工作表、字串、樣式，以及檔案之間的關聯。

當儲存過程被中斷時，這個結構就很重要。試算表程式可能已經寫入許多新內容，卻來不及完成整個壓縮檔。檔案之後可能顯示「File is not a zip file」。這句話很容易讓人以為所有儲存格都消失了。有時真正壞掉的是外層封裝，裡面的 XML 元件仍有一部分完整存在。

這不代表一定能復原。損壞的壓縮檔可能留下完整元件、不完整元件，也可能沒有可用資料。第一步應該是保留原始檔，只在複本上進行檢查。

概觀

Office Open XML 是包含 XLSX 在內的文件格式家族。ECMA-376 定義了它的詞彙、文件表示方式與封裝。這套封裝規則讓一份邏輯文件可以包含許多具名元件。

一般活頁簿可能包含活頁簿定義、每張工作表各自的 XML、樣式資訊、關聯檔，以及內容類型宣告。它也可能有共享字串、圖片、圖表、註解等元件。實際組合會依活頁簿內容而不同。

XLSX 讀取器需要可讀的封裝元件，也需要足夠的 ZIP 結構來找到它們。

這張圖刻意簡化了細節。XLSX 不是一份很長的 XML，而是一組元件，再由 ZIP 層提供元件目錄。

ZIP 層

ZIP 壓縮檔會儲存許多項目，例如檔案與資料夾。Python 的 zipfile 模組可以列出、讀取、寫入與附加這些項目。當結構有效時，ZipFile 與 ZipInfo 能提供項目名稱和中繼資料。

一般 ZIP 讀取器會依賴壓縮檔尾端附近的中央目錄。中央目錄記錄有哪些項目，以及它們位於哪裡。最後還有一筆紀錄指向中央目錄。如果寫入在這些紀錄完成前停止，即使前段的本機檔案紀錄和壓縮資料仍在磁碟上，一般讀取器也可能不知道該如何瀏覽整份壓縮檔。

這會產生很困惑的症狀。作業系統看得到一個很大的檔案，十六進位檢視器也可能看得到 XML 名稱與可讀文字，但 Excel、openpyxl 或 zipfile 仍拒絕開啟。原因可能是封裝索引遺失，或索引與內容不一致。

把副檔名從 .xlsx 改成 .zip 不會修好檔案。改名只是讓真實格式更容易辨認。我會在複本上使用壓縮檔工具檢查，並保持原始檔不變。

XML 元件

根目錄的 [Content_Types].xml 會告訴讀取程式，封裝裡有哪些內容類型。關聯檔負責連接各個元件。活頁簿元件識別工作表，並透過關聯指向工作表 XML。工作表 XML 則包含列、儲存格、公式與值的參照。

文字的儲存方式需要特別注意。有些活頁簿使用共享字串表。這種設計下，儲存格裡可能只保存一個索引，真正的文字放在 sharedStrings.xml。復原時必須同時擁有工作表與相符的字串表。如果只剩索引而字串表已遺失，無法只靠那個數字還原原文。

其他活頁簿會使用 inline strings，直接把文字放在工作表 XML 的儲存格元素中。這會讓工作表在資料復原時比較獨立。不過公式、格式、關聯與其他活頁簿行為，仍可能依賴其他元件。

樣式也是分開儲存。找回儲存格數值，不代表日期、貨幣、百分比或視覺格式會正確回來。數值本身，以及告訴程式如何顯示它的樣式，是兩份不同資訊。

儲存中斷為何會破壞封裝

儲存活頁簿不是在純文字檔尾端新增一列。寫入程式會建立或替換封裝元件、寫入 ZIP 項目資料，最後完成壓縮檔的中繼資料。程序在不同時間點停止，留下的狀態也不同。

如果很早就中斷，可能只剩一個很短、幾乎沒有可用內容的檔案。如果較晚中斷，許多 XML 項目可能完整，但中央目錄尚未完成。另一種情況是目錄仍可讀，某張工作表卻在中間被截斷。使用者看到的都是「打不開」，復原選項卻不一樣。

直接覆寫唯一的正常版本會增加風險。較安全的設計是先在相同資料夾建立暫存檔，完成新的活頁簿並驗證可讀，再取代目標檔。這無法排除所有儲存裝置故障，但在常見的寫入中斷情況下，可以避免立即破壞最後一份完整檔案。

使用 Python 復原

我會先複製損壞檔案，之後只操作複本。接著用 zipfile.is_zipfile 檢查 Python 是否把它辨識為有效 ZIP。如果可以，再用 ZipFile 開啟、列出項目並執行壓縮檔測試。這能區分「可以開啟，但某個項目損壞」和「ZIP 結構完全無法開啟」兩種狀況。

如果壓縮檔可以開啟，我會檢查 [Content_Types].xml、活頁簿關聯、工作表元件，以及字串的表示方式。我不會一開始就用 openpyxl 載入並存回原檔。openpyxl 很適合有效或足夠完整的活頁簿，但儲存會建立一份經過重新解讀的新活頁簿，不是鑑識用途的原樣複製。

如果 zipfile 拒絕封裝，就需要較低階的復原。壓縮檔修復工具有時能從仍存在的本機紀錄重建目錄。修復後，我會把封裝解壓到新資料夾，並假設會遇到遺失元件與中斷關聯，再以防禦方式解析 XML。我也會把公式、外部連結、巨集、圖片和樣式視為不同的復原問題，不會因為找回儲存格數值就認定整份活頁簿已完整。

若只要復原資料，可以用小型程式逐列讀取工作表，再解析 inline strings 或共享字串索引。程式應記錄每個略過的儲存格與缺少的相依元件，並把復原結果寫到新檔案，絕對不要覆寫損壞來源。

討論

理解封裝的好處

封裝模型能把模糊的「Excel 檔案壞了」拆成幾個小檢查。ZIP 目錄是否可讀？有哪些項目？活頁簿是否能指到工作表？字串是共享還是行內？即使樣式遺失，儲存格值是否仍在？

這也有助於一般開發。產生 XLSX 的程式可以先驗證完成的暫存檔，再進行取代。測試也能模擬儲存中斷，確認上一版活頁簿仍然可讀。

缺點與限制

XML 復原可能保住資料，卻失去行為。活頁簿可能依賴公式、命名範圍、圖表、連結、資料驗證或格式。讀到畫面上的儲存格值只代表其中一層。

還有安全問題。損壞或來源不明的活頁簿，仍是不受信任的輸入。Python zipfile 文件提醒解壓縮時的資源限制，openpyxl 也記載 XML 相關風險。復原工具應限制檔案大小、解壓路徑、項目數與記憶體用量，也不應盲目把壓縮檔內的名稱解壓到任意路徑。

結論

XLSX 是由多個相連元件組成的 ZIP 封裝。工作表資料、共享字串、樣式、關聯與內容宣告各有用途。儲存被截斷時，即使部分 XML 還在，負責串起整份壓縮檔的目錄也可能已損壞。

實務上的處理方式很直接：保存來源、檢查 ZIP 層、確認仍存在的元件，再把資料復原到新檔案。預防方面，應先寫入暫存檔，確認新封裝完整且可讀後，才取代目標檔。
