41 筆標案名稱變成亂碼，搜尋卻只顯示查無結果

這篇文章要說明一段看似寬容的解析 fallback，如何在爬蟲持續正常執行時，悄悄破壞中文標案名稱。

揭露：本文以我自己的專案筆記為基礎，由 AI 協助草擬，發布前由我本人審閱。

背景

我維護一個公開採購網站的爬蟲。其中一段程式會從 JavaScript 字串常值解析標案名稱。多數名稱是中文，而使用者會拿來源網站看到的文字搜尋，所以爬蟲必須完整保留原文。

輸入看起來可以交給 JSON 解析，但有些字串結尾帶著原始 tab 控制字元。strict 模式的 JSON 不接受字串裡的控制字元，因此一般解析器會拒絕這些值。

程式原本有一條 fallback。它先把值編碼成 UTF-8 bytes，再用 Python 的 unicode_escape codec 解碼。原意只是容忍有問題的字元，結果卻連正常中文也一起改掉。

亂碼如何產生

問題路徑是 value.encode('utf-8').decode('unicode_escape')。若輸入只有反斜線 escape，看起來似乎合理；但同一個值還有一般非 ASCII 文字時，這個做法並不安全。

UTF-8 會把每個中文字表示成多個 bytes。unicode_escape 不會把它們重新組回 UTF-8 文字，而是以類似 Latin-1 的方式看待這些 bytes，同時解讀 escape sequence。結果不是只修改結尾的 tab，而是整個中文名稱都變成亂碼。

失敗路徑：一個原始 tab，讓原本正常的中文名稱進入錯誤 decoder。

這種錯誤很危險，因為例外看起來已經被處理。爬蟲沒有停止，資料庫仍收到一筆紀錄，欄位也不是空值。從營運狀態看起來一切正常，但資料內容已經錯了。

這次共有 155,440 筆紀錄，其中 41 筆受到影響。大約兩個月內，每週都會出現新的損壞名稱。比例雖小，但每一筆受影響資料都失去了使用者用來發現標案的主要欄位。

搜尋為何掩蓋問題

如果爬蟲直接崩潰，反而更容易發現。失敗執行會留下錯誤；搜尋文字被破壞，留下的只是一個「找不到」。

使用者用正確中文名稱搜尋時，資料庫裡存的是另一套錯誤字元。查詢回傳零筆。這和標案本來就不存在的結果完全一樣。爬蟲成功新增了 row，搜尋端點也成功回傳空結果，因此沒有任何 alert。

這說明資料品質檢查不能等同服務健康檢查。請求成功，只能證明服務有回應，不能證明文字通過解析後仍然正確。資料庫有 row，也不能證明名稱仍可閱讀、可搜尋。

後來的空白清理讓復原更難。清理程式又替換了亂碼文字裡的 0x85 與 0xA0 bytes。因此有些名稱無法再用 encode('latin-1').decode('utf-8') 反轉回原文，因為資料已被改過兩次。

診斷與復原

真正有用的線索不是 exception，而是壞掉名稱的外觀。UTF-8 bytes 被錯誤字元對照解讀時，通常會出現重複字元和像標點的片段。我把其中一個值沿著解析流程往回追，fallback 便成為明顯原因。

修正方式是對這份輸入使用 json.loads(..., strict=False)。Python JSON decoder 因而能接受字串內的控制字元，不需要把完整值送進無關的文字 codec。我也加上一個只改寫 escape sequence、保留非 ASCII 原文的 fallback。

修好程式只完成一半，已儲存的名稱也要復原。由於部分亂碼又被後續清理修改，直接反轉並不可靠。我改從保存的原始頁面重新解析名稱。那些頁面是最接近原始來源的副本。

實際完成的復原：安全解析原文、重建受影響名稱，再更新爬蟲資料庫。

我不只更新下游搜尋資料，也把修正套用到爬蟲自己的資料庫。若只修搜尋端，下一次夜間匯入可能再次用舊亂碼覆蓋正確名稱。

討論

Fallback 不只要維持可用性

原本的 fallback 讓 pipeline 繼續跑，卻破壞解析器最重要的契約：保留來源文字。評估錯誤處理時，不該只問它有沒有避免 exception，而要問錯誤發生後仍能保證什麼。

處理文字時，bytes 與文字的界線必須清楚。Bytes 應該只在已知 encoding 下轉成文字一次。之後若要處理 escape，只應修改真正的 escape 語法，不該把完整 Unicode 值再送進 byte-oriented codec。

罕見路徑也需要真實樣本

問題只影響 155,440 筆中的 41 筆，隨機抽查很可能一筆都碰不到。Fallback 測試應同時放入中文、觸發 fallback 的控制字元，並確認其餘每個字都保持不變。

空搜尋結果有多種意思

零筆可能完全正確，也可能代表索引資料已損壞。我想新增資料品質檢查，計算新出現的亂碼名稱，並比較可搜尋名稱和原始來源。這是下一步計畫，不是本次已完成的修正。

保留可供復原的原始輸入

保存的原始頁面讓精確復原成為可能。若沒有它們，部分經過第二次清理的名稱無法安全重建。保留來源資料會有儲存與隱私成本，應明確訂定政策；這次既有副本就是可靠的復原來源。

結論

爬蟲沒有明顯失敗。它透過 fallback 接受一個不合法控制字元，卻順便破壞字串其他內容。41 筆標案名稱變成亂碼，而正常搜尋行為把損壞偽裝成普通的空結果。

修正方式是使用 strict=False 解析這份輸入，避免非 ASCII 文字進入 escape decode 路徑，並從保存的原始頁面重建名稱。我也修正爬蟲資料庫，防止夜間匯入把壞資料寫回去。

我的主要心得很簡單：fallback 有回傳值，不代表 fallback 成功。對 parser 而言，成功的意思是保留原始文字的意義。

其他

我想建立一組小型 regression corpus，收錄原始 tab、escape、中英文與混合字串。我也想在資料進入搜尋前，檢查新名稱是否帶有常見亂碼模式。

更好的設計會記錄每個值走過哪一條解析路徑。這樣 fallback 使用情況就能被量測，也能在新案例累積數週之前先人工檢查。
