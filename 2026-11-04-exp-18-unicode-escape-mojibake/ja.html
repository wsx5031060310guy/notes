41件の入札案件名が文字化けし、検索は何も見つけられなかった

このブログでは、寛容に見えたパース処理のフォールバックが、中国語の入札案件名を静かに壊した経緯を説明します。

本記事は、私自身のプロジェクトメモをもとに AI の支援を受けて下書きし、公開前に私が確認しています。

背景

私は公共調達サイトを対象にしたクローラーを運用しています。クローラーの一部は、JavaScript の文字列リテラルから入札案件名を取り出します。名称の多くは中国語です。利用者は元サイトで見た単語を使って検索するため、文字列を正確に保存する必要があります。

入力は JSON で読めそうな形式でした。しかし、一部の文字列の末尾に生のタブ文字が入っていました。strict モードの JSON では、文字列内の制御文字は許可されません。そのため通常のパーサーは値を拒否しました。

コードにはフォールバックがありました。値を UTF-8 のバイト列に変換し、Python の unicode_escape コーデックでデコードしていました。狙いは不正な文字だけを許容することでしたが、実際には中国語本文まで変換してしまいました。

文字化けが起きた流れ

問題の処理は value.encode('utf-8').decode('unicode_escape') です。入力がバックスラッシュによるエスケープだけなら、もっともらしく見えます。しかし、通常の非 ASCII 文字が同じ値に含まれる場合は安全ではありません。

UTF-8 では、中国語の各文字が複数のバイトになります。unicode_escape は、そのバイト列を UTF-8 の文字へ戻しません。エスケープを解釈しながら、バイトを Latin-1 のように扱います。その結果、末尾のタブだけでなく、案件名全体が文字化けしました。

障害の流れ：1つの生タブにより、正常な中国語まで誤ったデコーダーへ送られました。

この形の不具合は気づきにくいです。例外は処理済みに見え、クローラーは停止しません。レコードはデータベースに入り、項目も空ではありません。運用上は正常に見えても、中身は壊れています。

影響を受けたのは 155,440 件中 41 件でした。約2か月にわたり、毎週新しい文字化けが増えていました。割合は小さくても、該当レコードでは発見に必要な名前が失われていました。

検索が問題を隠した理由

クラッシュなら、もっと早く気づけたはずです。失敗した処理にはエラーが残ります。一方、検索用の文字列が壊れると、残るのは「見つからない」という状態だけです。

正しい中国語の案件名で検索しても、データベースには別の文字列が保存されています。検索結果はゼロです。これは、案件そのものが存在しない場合と同じ見え方でした。クローラーは行を作成し、検索 API も正常な空結果を返したため、アラートは出ませんでした。

サービスの正常性とデータ品質は別に確認する必要があります。リクエスト成功は応答を証明しますが、文字列が無傷であることは証明しません。行数がゼロでないことも、名称が読めて検索できることまでは保証しません。

後続の空白整理も復旧を難しくしました。すでに文字化けした文章の中で、0x85 と 0xA0 に当たるバイトまで置換されました。そのため、一部の名称は encode('latin-1').decode('utf-8') で元に戻せなくなりました。情報が二度変更されていたからです。

調査と復旧

手掛かりは例外ではなく、壊れた名称の見た目でした。文字化けには、UTF-8 のバイトを別の文字対応で読んだとき特有の繰り返しや記号が現れます。1件の値をパーサーまで追跡すると、フォールバック処理が原因だと分かりました。

修正では、この入力に json.loads(..., strict=False) を使いました。これにより、文字列内の制御文字を受け入れつつ、値全体を別のテキストコーデックへ渡さずに済みます。また、非 ASCII 文字をそのまま保ち、必要なエスケープだけを書き換えるフォールバックに変更しました。

コードの修正だけでは不十分です。保存済みの名称も直す必要があります。後続処理で再度変更された値があるため、文字化けの逆変換は信頼できません。そこで保存してあった生ページから名称を再パースしました。元データに最も近いコピーを使った復旧です。

実施した復旧：元テキストを安全に解析し、名称を再構築してクローラーのデータベースを更新しました。

下流の検索データだけでなく、クローラー自身のデータベースにも修正を適用しました。検索側だけを直すと、次回の夜間インポートが古い文字化け値を再び上書きする可能性があったためです。

考察

フォールバックは稼働だけでなく意味を守る必要があります

今回の処理はパイプラインを止めませんでしたが、元の文字列を保つという主な契約を破りました。例外を避けたかではなく、エラー後に何を保証できるかで評価すべきです。

まれな経路には実際のサンプルが必要です

影響は 155,440 件中 41 件だけでした。ランダム確認では全部を見逃す可能性があります。テストには、中国語、生のタブ、フォールバックを起動する条件、そして他の文字が変わらないことの確認が必要です。

空の検索結果には複数の意味があります

結果ゼロは正しい場合もあれば、索引データ破損の兆候でもあります。今後は、新しい文字化け名を数える品質チェックと、生データとの比較を追加したいです。これは今回完了した修正ではなく、次の計画です。

復旧に備えて元入力を残します

保存済みの生ページがあったため、正確に再構築できました。保持には容量やプライバシーの検討が必要ですが、今回の既存コピーは信頼できる復旧元でした。

まとめ

クローラーは大きな音を立てて失敗しませんでした。1つの不正な制御文字を処理するフォールバックが、文字列の残りまで壊しました。41件の案件名が文字化けし、検索はそれを普通の空結果として隠しました。

修正は strict=False で入力を解析し、非 ASCII 文字をエスケープデコード経路から外し、保存済みの生ページから名称を再構築することでした。夜間インポートで再発しないよう、クローラー側のデータベースも直しました。

値を返しただけでは、フォールバック成功とは言えません。パーサーの場合、成功とは元の文字列の意味を保つことです。

今後

生タブ、エスケープ、中国語、混在文字列を含む小さな回帰テスト用コーパスを作りたいです。また、検索に入る前に典型的な文字化けを検出するチェックも追加したいです。

よりよい設計では、各値をどの解析経路が処理したか記録します。そうすれば、フォールバック利用を見える化し、何週間も蓄積する前に新しい事例を確認できます。
