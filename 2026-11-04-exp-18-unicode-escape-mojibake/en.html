41 Tender Names Became Mojibake, and Search Found Nothing

In this blog, I will describe how a permissive parsing fallback quietly damaged Chinese tender names while the crawler kept running.

Disclosure: I drafted this post with AI assistance from my own project notes, and I review it before publishing.

Background

I run a crawler for a public procurement website. One part of the crawler reads tender names from JavaScript string literals. Most names are Chinese text. The crawler needs to preserve that text exactly because people search for tenders by the words they saw on the source website.

The input looked like data that JSON could parse, but some strings ended with a raw tab character. A raw control character is not valid inside a strict JSON string. The normal parser therefore rejected those values.

The code had a fallback. It took the value, encoded it as UTF-8 bytes, and decoded those bytes with Python's unicode_escape codec. The intention was narrow: tolerate the bad character and recover the string. The effect was much wider. It changed the Chinese text itself.

How the corruption happened

The broken path was conceptually simple. Strict parsing failed on the raw tab. The fallback then ran value.encode('utf-8').decode('unicode_escape'). That expression looks reasonable if the input contains backslash escapes. It is unsafe when the same value also contains ordinary non-ASCII text.

The UTF-8 encoder represents each Chinese character as several bytes. The unicode_escape decoder does not reconstruct those bytes as UTF-8 text. It treats the bytes as Latin-1-like input while interpreting escape sequences. As a result, the whole Chinese name becomes mojibake. The fallback did not merely remove or alter the tab at the end.

The failure path: one raw tab sent an otherwise valid Chinese name through the wrong decoder.

This is a dangerous shape of bug because the exception appears to be handled. The crawler does not stop. A record still reaches the database. The field is not empty. From an operational view, the run can look normal while the stored data is wrong.

In this case, 41 of 155,440 records were affected. New damaged names appeared every week for about two months. The percentage was small, but each affected record had lost the field users needed for discovery.

Why search hid the problem

A crash would have been easier to notice. A failed run leaves an error. Corrupted search text leaves absence.

When someone searched with the correct Chinese tender name, the database contained a different byte-to-character interpretation. The query found nothing. That result looked exactly like a tender that did not exist. There was no alert because the crawler had produced a row and the search endpoint had produced a valid empty result.

This is why data quality needs checks that are different from service health checks. A successful request proves that the service answered. It does not prove that text survived parsing. A non-empty database proves that rows were inserted. It does not prove that their names are readable or searchable.

The later cleanup made recovery harder. A whitespace normalization step replaced bytes 0x85 and 0xA0 inside the already garbled text. For some records, the usual reversal, encode('latin-1').decode('utf-8'), could no longer recreate the original name. Information had been changed twice.

Diagnosis and recovery

The useful clue was not an exception. It was the visual pattern in the bad names. Mojibake often has repeated characters and punctuation-like fragments because UTF-8 bytes have been interpreted under the wrong character mapping. Once I traced one damaged value back through the parser, the fallback stood out.

The parser fix used json.loads(..., strict=False) for this input. Python's JSON decoder can then accept control characters in strings without sending the entire value through an unrelated text codec. I also added a fallback that rewrites only escape sequences and leaves non-ASCII text untouched.

Repairing the code was only half of the work. The stored names also needed repair. Since some damaged values had gone through the later whitespace cleanup, reversing the mojibake was not reliable. I re-parsed the names from saved raw pages instead. Those pages were the closest available copy of the original source.

The implemented recovery: parse the original text safely, rebuild affected names, and update the crawler database.

I applied the repair to the crawler's own database as well as the downstream data. That detail mattered. If I had repaired only the visible search database, the next nightly import could have copied the old damaged value back over the correction.

Discussion

A fallback must preserve more than availability

The fallback kept the pipeline moving, but it violated the parser's main contract: preserve the source text. Error handling should be judged by what it guarantees after the error, not by whether it avoids an exception.

For text processing, the encoding boundary must be explicit. Bytes become text once under a known encoding. After that, escape decoding should operate only on the escape syntax that needs attention. Passing a full Unicode value through a byte-oriented escape codec mixes two separate jobs.

Rare paths deserve real samples

The problem affected only 41 records out of 155,440. A random spot check could easily miss every one. The failing values shared a feature: a raw tab at the end. Tests for the fallback should include Chinese text, the control character that triggers the fallback, and a check that every other character remains unchanged.

Empty search results are ambiguous

An empty result can be correct, or it can be evidence of damaged indexing data. I want to add data-quality checks that count newly garbled names and compare searchable names with the raw source. This is a plan, not part of the completed fix described here.

Keep raw input when repair may matter

The saved raw pages made an exact recovery possible. Without them, some names could not be safely reconstructed after the second cleanup step. Retaining source material has storage and privacy costs, so the retention policy should be deliberate. For this incident, the existing copies were the reliable recovery source.

Conclusion

The crawler did not fail loudly. It accepted a bad control character through a fallback that corrupted the rest of the string. Forty-one tender names became mojibake, and normal search behavior hid the damage as an ordinary empty result.

The fix was to parse this input with strict=False, keep non-ASCII text out of the escape-decoding path, and rebuild names from saved raw pages. I also repaired the crawler database so the nightly import would not restore the bad values.

My main lesson is simple: a fallback that returns a value is not necessarily a successful fallback. For parsers, success means preserving the meaning of the original text.

Other

I want to add a small corpus of troublesome source strings to regression tests. It should include raw tabs, escaped characters, Chinese names, and mixed text. I also want a check that flags newly stored names with common mojibake patterns before they reach search.

A better design would record which parsing path handled each value. That would make fallback use measurable instead of invisible. It would also let me review new fallback cases before they accumulate for weeks.
