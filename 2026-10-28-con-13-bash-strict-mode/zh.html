Bash 嚴格模式：set -euo pipefail 能抓到什麼，又漏掉什麼

這篇文章會說明 set -euo pipefail 如何改變 Bash 的行為、保護範圍到哪裡，以及可靠的腳本仍然需要哪些明確檢查。

前言

Shell 腳本常在開頭放入一行簡短設定：

set -euo pipefail

大家常把它稱為「嚴格模式」，但 Bash 並沒有用這個正式名稱定義一項功能。這一行其實啟用了三種彼此獨立的行為。-e 是 errexit，-u 是 nounset，而 set -o pipefail 會改變 pipeline 回報結束狀態的方式。它們能抓到一些很有用的錯誤，卻不會把 Bash 變成每個錯誤都自動成為例外的語言。

關鍵在於 Bash 回應的是結束狀態與展開規則，而不是人類的意圖。命令可能產生錯誤結果，卻仍回傳零。失敗也可能位於 -e 刻意忽略的語法情境。預設值還可能掩蓋遺漏的設定。嚴格模式是護欄，不是腳本正確性的證明。

概觀

把這一行拆成三個開關，比把它當成一段咒語更容易理解。

每個開關處理不同訊號：命令狀態、未設定變數的展開，或 pipeline 狀態。

  • set -e 可能在簡單命令或複合命令回傳非零狀態時離開，但有手冊明定的例外。
  • set -u 把未設定參數的展開視為錯誤；特殊參數另有手冊明定的處理方式。
  • set -o pipefail 讓 pipeline 中任一命令失敗時能回報失敗，而不是像預設行為一樣只採用最後一個命令的狀態。

許多腳本都會透過變數與 pipeline 傳遞資料，所以這三個選項一起使用很有效。不過，每個選項都有邊界。可靠的腳本會把這些邊界寫清楚，而不是假設開頭那一行可以處理所有控制流程。

set -e 做了什麼

啟用 -e 後，當 pipeline、list 或 compound command 回傳非零狀態時，Bash 會離開，但手冊定義了幾個例外。這些例外有其必要性，因為 shell 語法會把命令的結束狀態當成布林值使用。

放在 if 後面作為條件的命令，本來就預期可能成功或失敗。Bash 必須檢查該狀態來選擇分支，所以不會只因條件為假就讓 -e 結束腳本。相同道理也適用於 while 與 until 的條件命令。

&& 與 || list 是另一個重要例外。在 prepare && deploy 中，prepare 失敗會決定是否執行 deploy。在 load_cache || rebuild_cache 中，第一個命令失敗會選擇備援流程。因此，除了最後一個 && 或 || 後方的命令外，Bash 不會對這些 list 裡的命令套用 -e。pipeline 中不是最後一個的命令也不適用基本的 -e 規則；使用 ! 反轉的狀態則會被當成控制流程。

這表示「命令失敗」不等於「腳本離開」。語法情境很重要。如果某個失敗一定要終止操作，就應直接檢查，並用清楚的訊息 return 或 exit。不要只是為了少寫幾行，就把命令全部重排成 && 鏈。

set -u 做了什麼

啟用 -u 後，展開未設定變數通常會成為錯誤。它可以提早抓到拼錯的名稱和遺漏的輸入。若未啟用，未設定變數通常會展開成空字串，讓路徑、命令參數或設定值朝錯誤方向前進。

大括號可以明確界定變數名稱。當值後方還有其他字元時，請寫成 ${VAR}。例如 ${name}_backup 會展開參數 name，再加上後綴。若寫成 $name_backup，Bash 會尋找另一個名為 name_backup 的參數。不是大括號啟用了 -u；它的作用是避免模糊或非預期的參數名稱，也讓審查更安全。

有時缺少值時確實可以使用合理的預設值。Bash 的參數展開提供 ${VAR:-default}。有冒號的形式會在 VAR 未設定或設為空字串時使用預設值。相較之下，${VAR-default} 只在參數未設定時使用預設值。當空字串本身代表一個刻意選擇時，這項差異很重要。

預設值應該表達政策，而不是消除所有錯誤。顯示名稱或許可以有無害的備用值；輸出目錄、憑證名稱或環境選擇則可能必須明確要求。若缺少值時繼續執行並不安全，Bash 也提供 ${VAR:?message} 這種錯誤形式。

pipefail 做了什麼

在預設情況下，pipeline 的結束狀態是最後一個命令的狀態。假如 generate_report 失敗，但接收其輸出的 formatter 成功離開，整條 pipeline 仍可能回報成功。這會掩蓋產生不完整或空白輸入的命令。

啟用 pipefail 後，pipeline 狀態會是最右側、以非零狀態離開之命令的值；若所有命令都成功，狀態就是零。它不會把命令改成逐一執行，也不會用文字指出失敗原因。它改變的是外層 shell 邏輯收到的最終狀態。

沒有 pipefail 時由最後一個命令決定；啟用後，非零狀態可以保留到整條 pipeline 的結果。

同時啟用 -e 與 pipefail 時，沒有被處理的 pipeline 失敗可以停止腳本。不過，-e 的語法例外仍然存在。例如，作為 if 條件的 pipeline 正在被刻意測試，因此不會自動終止腳本。

示範

實際腳本可以在靠近開頭的位置啟用選項，再把預期中的失敗明確寫出來。

啟用 set -euo pipefail。用 ${OUTPUT_DIR:?OUTPUT_DIR is required} 讀取必要的輸出目錄。用 ${FORMAT:-text} 讀取選填格式。把 producer 與 formatter 當成一條 pipeline 執行。將允許失敗的 probe 放進 if 敘述，並明確處理其 false 分支。

這個結構分開三種情況。必要設定會附帶實用訊息而失敗。選填設定會取得文件化的預設值。可能合理回傳非零狀態的 probe 會成為清楚可見的控制流程。主要 pipeline 則受惠於 pipefail，所以前段 producer 的失敗不會被最後一個 filter 的成功掩蓋。

偵錯 pipeline 時，請立刻保存狀態。Bash 透過 PIPESTATUS 陣列公開最近一條 foreground pipeline 中各命令的狀態。任何後續命令都可能像覆蓋 $? 一樣覆蓋這項資訊，所以必須在執行其他工作前檢查。

討論

嚴格模式擅長抓到什麼

它很適合把常見的機械性錯誤轉成明顯失敗，例如一般流程中未處理的非零命令、未設定變數的展開，或被 pipeline 最後一個成功命令掩蓋的前段失敗。因為 shell 的預設行為通常很寬鬆，這些檢查相當有價值。

它抓不到什麼

嚴格模式無法發現回傳零卻產生錯誤資料的命令。它不知道空白結果是否可疑，也不會驗證路徑的語意、遠端副作用是否真的發生，或檔案是否包含預期紀錄。這些檢查必須來自腳本的領域規則。

它也不會消除理解控制情境的必要性。if、while、until、&& 與 || 都會刻意消費結束狀態。函式、subshell、command substitution、trap 與 shell 選項繼承還會加入更多行為。腳本若依賴這些特性，就應針對它們測試。

如何測試

不要只測成功流程，也要測每一條失敗路徑。先讓必要變數未設定，再把它設成空字串。讓 pipeline 的第一個與中間命令分別失敗。在 if 條件，以及 && 或 || list 的兩側回傳非零狀態。確認最終結束狀態，以及呼叫端收到的清理結果或訊息。

用 bash -n 執行語法檢查，並使用 shell 分析工具取得額外警告，但仍要保留行為測試。語法與 lint 無法判斷成功命令是否產生了正確的業務結果。

優點與缺點

優點

  • 未設定變數會在接近展開位置的地方失敗。
  • pipeline 的失敗較不容易消失在最後一個成功命令後方。
  • 一般流程中未處理的命令失敗可以更早停止腳本。
  • 開頭的選項能向讀者傳達較嚴格的失敗政策。

缺點

  • -e 會受語法情境影響，也很容易被過度簡化。
  • 合法的空值或缺值需要刻意選擇參數展開方式。
  • 預期中的非零狀態必須寫成控制流程。
  • 既有腳本可能會暴露原本隱藏的假設，需要謹慎遷移。
  • 沒有任何選項能取代對輸出與副作用的驗證。

結論

set -euo pipefail 很實用，因為它在三個不同位置改變 Bash 寬鬆的預設行為。它可以在許多未處理的失敗時停止、拒絕未設定變數展開，並保留 pipeline 前段的失敗。對新的 Bash 腳本而言，這是一個很好的起點。

安全的結論不是「嚴格模式抓得到每個錯誤」，而是「嚴格模式讓幾種重要錯誤更難被忽略」。用大括號界定變數名稱，只在預設值真的有效時使用它，把預期中的失敗寫成明確分支，並測試 -e 不會離開的情境。腳本仍然需要檢查真正重要的結果。

其他

我想在重要腳本旁保留一份小型失敗矩陣：未設定輸入、空白輸入、producer 失敗、filter 失敗、false 條件，以及未成功的副作用。這能讓選項成為可測試的行為，而不是從另一支腳本複製來的一行文字。
