トークン節約用 CLI プロキシが失敗したビルドを成功に見せた話

便利な最適化が、失敗したコンパイラ実行を「エラーなし」と要約し、誤った信頼の源になりました。

本記事は、私自身のプロジェクトメモをもとに AI の支援を受けて下書きし、公開前に私が確認しています。

はじめに

このブログでは、トークン節約用の CLI プロキシが引き起こした失敗について説明します。このプロキシは、コマンドラインプログラムと AI コーディングエージェントの間に入り、長い出力を書き換えて圧縮してからエージェントに渡していました。

発想そのものには利点があります。ビルドログには同じ内容が何度も現れます。テストランナーが数千行を出力することもあります。AI エージェントが、進捗表示や繰り返される警告をすべて読む必要はありません。出力を短くすれば、使用するコンテキストを減らし、重要な行を見つけやすくできます。

しかし、圧縮された出力はコマンドそのものではありません。別のプログラムがコマンドを解釈した結果です。今回、この違いによってコンパイラの失敗が成功したように要約されました。

対象プロジェクトには node_modules がインストールされていませんでした。そのため TypeScript compiler は失敗するはずでした。ところが、プロキシ経由で実行すると、エージェントには「No errors found」と表示されました。エージェントはその文を信頼し、ビルドは成功したと報告しました。

コンパイラの不具合ではありません。観測経路の不具合です。実際のコマンド結果と、エージェントが見た結果が分離していました。

概要

元の流れには三つの部分がありました。最初に AI コーディングエージェントがコマンドを選びます。次にプロキシがコマンドの出力を取得し、圧縮します。最後にエージェントが圧縮後の文章から判断します。

失敗した経路：実際のコンパイラエラーが、エージェントの判定前に誤った成功要約へ変わりました。

弱点は圧縮そのものではありません。機械が読める成功シグナルを持つコマンドについて、生成された文章を最終結果として扱ったことです。

シェルコマンドには、すでに簡潔な契約があります。それがプロセスの exit code です。通常、成功したプロセスはゼロを返し、失敗したプロセスはゼロ以外を返します。ログは何が起きたかを説明しますが、処理が成功したかどうかは exit code が呼び出し側に伝えます。

プロキシは、その契約を一つの文章に置き換えてしまいました。文章は明快に見えましたが、内容は誤っていました。エージェントには書き換え後の出力しか見えなかったため、元のプロセスが失敗したという独立した証拠がありませんでした。

誤った成功判定が生まれた流れ

最適化が証拠を変えました

通常の出力フィルターは、意味を保ちながら不要な情報を削ります。要約処理はさらに踏み込みます。重要な行を判断し、メッセージをまとめ、結論を作る場合があります。その結論は新しいデータです。元のコマンドが正しく動作していても、要約側で誤りが入る可能性があります。

ここには二つの質問があります。ツールは何を返したのか。そして要約は何と言ったのか。二番目の答えしか記録しなければ、一次証拠が失われるため、デバッグは難しくなります。

今回は依存関係がないため TypeScript compiler が失敗しました。それでも要約はエラーがないと伝えました。AI エージェントは入力に従い、チェックを成功と判断しました。

なぜ信じやすかったのか

「No errors found」は短く、断定的です。きれいな type-check の後に開発者が期待する結果に似ています。警告にも、推測にも、不完全なログにも見えません。そのため、明らかに壊れた出力より危険でした。

また、依存関係がないという事実が見えなくなれば、エージェントがそれを推測する理由もありません。中間処理が捨てた証拠や誤って書き換えた証拠を、推論だけで復元することはできません。

ファイル書き込みにも同じ危険がありました

問題はビルドだけではありません。プロキシは、後で環境ファイルに書き込まれる grep の出力も変更しました。これはログの見え方だけでなく、生成される成果物自体を変える問題です。

ここには明確な境界があります。人が読むための出力は、状況によって要約できます。しかし、別のプログラムへの入力になる出力は正確でなければなりません。変換後の文章をファイルへリダイレクトすると、小さな編集が設定エラーになります。

修正

私は build、type-check、test コマンドの実行ルールを変更しました。これらのコマンドはプロキシを経由しません。プロセスの exit code を直接確認します。

ファイルへ書き込む出力にも同じルールを適用しました。それは説明ではなくデータなので、プロキシを迂回します。プロキシは人が読むログを整理できますが、機械同士のデータ経路には入りません。

修正後の設計では、状態と説明を分けます。exit code が正式な判定です。正確な詳細が必要な場合は raw output を使います。短い要約は確認の入口として利用できますが、ゼロ以外の終了値を成功に変えることはできません。

実装した修正：重要なチェックとファイル向け出力はプロキシを迂回し、実際の exit code で成否を決めます。

このルールは意図的に単純にしています。要約処理に、考えられるすべてのエラーを正しく分類させる必要はありません。コマンドラインツールが最初から提供しているインターフェースを使います。

利点と欠点

利点

  • build、type-check、test の結果が実際のプロセス状態に従います。
  • ファイルへ書くデータが知らないうちに書き換えられません。
  • 低リスクで人が読むコマンドについては、短いログを AI エージェントへ渡せます。
  • 信頼境界を説明しやすくなります。文章は解釈を助けますが、成功を定義しません。

欠点

  • 重要なコマンドの出力は圧縮されないため、使用するコンテキストが増える場合があります。
  • raw log には繰り返しが多く、エージェントが読み取りにくい場合があります。
  • 新しいビルドツールやテストツールを追加したら、コマンド分類も保守する必要があります。

検証の境界では、トークン節約より正確さが重要なので、このコストを受け入れます。間違った結論になるなら、小さいコンテキストに価値はありません。

考察

この出来事で、AI 向け開発ツールに対する考え方が変わりました。コマンド出力を書き換えるプロキシは、透明なパイプではありません。プログラムの一部です。固有の動作、edge case、failure mode があります。parser や adapter と同じように疑って確認する必要があります。

安全な設計では、構造化された判断のために構造化されたシグナルを残します。exit code は exit code のまま扱います。信頼できるインターフェースがあるなら、test count は test runner から取得します。変換自体が目的でない限り、ファイル内容は正確に保ちます。

要約には今も価値があります。繰り返される警告をまとめ、原因候補を強調し、raw details の前に概要を示せます。ただし要約は要約として明示すべきです。元の結果になりすましてはいけません。

agent evaluation にも同じ教訓があります。最終回答が正しく聞こえるかだけでは不十分です。その回答の根拠となる証拠が、実行経路で保たれている必要があります。そうでなければ、流暢なエージェントが上流で混入した誤りを自信を持って繰り返します。

まとめ

プロキシはトークン節約のために作られ、実際に出力を短くしました。しかし同時に、失敗したコンパイラ実行を成功したように見せました。エージェントはビルドを検証していたのではなく、別のプログラムが作った文章を検証していました。

修正では本来の契約を戻しました。build、type-check、test はプロキシを迂回し、プロセスの exit code を直接使います。ファイルへ渡す出力も書き換え経路の外に置きます。

最大の教訓は単純です。出力を要約するものは、間違う可能性がある第二のプログラムです。exit code が契約であり、文章は契約ではありません。

今後

次は境界をさらに見えるようにしたいです。改善案として、変換済みの出力には明確なラベルを付け、raw log のパスまたはリンクを残します。また、表示専用の出力、検証用の出力、ファイルへ渡すデータを区別する command policy も検討したいです。

プロキシ自体のテストも追加したいです。静かな出力でゼロ以外を返すコマンド、依存関係不足による compiler failure、ファイルへリダイレクトする正確な出力などが候補です。これらは今後の計画であり、実装済みの機能ではありません。
