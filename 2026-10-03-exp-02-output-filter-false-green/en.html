A Token-Saving CLI Proxy Made My Failing Build Look Green

A useful optimization became a false source of truth when it summarized a failed compiler run as “No errors found.”

Introduction

In this blog, I will describe a failure caused by a token-saving CLI proxy. The proxy sat between command-line programs and an AI coding agent. Its job was simple: rewrite and compress long output before the agent read it.

This idea is attractive. Build logs can be repetitive. Test runners can print thousands of lines. An AI agent does not always need every progress message or repeated warning. Shorter output can reduce the context used by the agent and make the important lines easier to find.

But compressed output is not the command itself. It is a second program’s interpretation of that command. In my case, this distinction turned a compiler failure into a successful-looking summary.

The project did not have node_modules installed. Running the TypeScript compiler should therefore fail. When the compiler ran through the proxy, the agent received the sentence “No errors found.” The agent trusted that sentence and reported that the build passed.

No compiler bug was involved. The failure was in the observation path. The real command and the agent’s view of the command had separated.

Overview

The original flow had three parts. First, the AI coding agent selected a command. Second, the proxy executed or observed that command and compressed its output. Third, the agent made a decision from the compressed text.

The failed path: a real compiler error became a false green summary before the agent evaluated it.

The weak point was not compression by itself. The weak point was treating generated prose as the final result for a command with a machine-readable success signal.

Shell commands already have a compact contract: the process exit code. A successful process normally returns zero. A failed process returns a non-zero value. Logs explain what happened, but the exit code tells the caller whether the process completed successfully.

The proxy replaced that contract with a sentence. The sentence looked clear, but it was wrong. Because the agent saw only the rewritten output, it had no independent evidence that the underlying process had failed.

How the False Green Happened

The optimization changed the evidence

A normal output filter removes noise while preserving meaning. A summarizer goes further. It decides which lines matter, groups messages, and may produce a conclusion. That conclusion becomes new data. It can contain an error even when the original command behaved correctly.

This creates two separate questions. What did the tool return? What did the summary say? If the system records only the second answer, debugging becomes difficult because the primary evidence is gone.

In this case, the missing dependencies were enough to make the TypeScript compiler fail. The summary still said there were no errors. The AI agent then did what its input encouraged it to do: it treated the check as green.

Why the result was convincing

“No errors found” is short and confident. It resembles the result a developer expects after a clean type-check. It does not look like a warning, an uncertain guess, or an incomplete log. That makes it more dangerous than an obviously broken output stream.

The agent also had no reason to infer that dependencies were missing if that fact was removed from its view. Reasoning cannot recover evidence that an intermediary discarded or rewrote incorrectly.

The same risk affected file writes

The problem was not limited to builds. The proxy also altered grep output that was later written into an environment file. That changed the artifact itself, not merely the way a human or agent viewed a log.

This is an important boundary. Output intended for reading may sometimes be summarized. Output intended to become another program’s input must remain exact. Once transformed text is redirected into a file, small editorial changes can become configuration errors.

The Fix

I changed the execution rule for build, type-check, and test commands. These commands bypass the proxy. Their process exit codes are checked directly.

The same rule applies to output that will be written to a file. That output also bypasses the proxy, because it is data rather than commentary. The proxy is allowed to help with human-facing logs, but it does not sit inside a machine-to-machine data path.

The corrected design separates status from explanation. The exit code is authoritative. Raw output remains available when exact details matter. A compact summary can still be useful for navigation, but it cannot turn a non-zero exit into success.

The implemented fix: critical checks and file-bound output bypass the proxy, while the real exit code controls pass or fail.

This rule is deliberately simple. It does not ask a summarizer to classify every possible error correctly. It uses the interface that command-line tools already provide.

Benefits and Drawbacks

Benefits

  • Build, type-check, and test results now follow the real process status.
  • Data written to files is not silently rewritten.
  • The AI agent can still receive shorter logs for lower-risk, human-facing commands.
  • The trust boundary is easier to explain: prose helps interpretation, but it does not define success.

Drawbacks

  • Critical commands may use more context because their output is not compressed by the proxy.
  • Raw logs can contain repetitive details that are harder for an agent to scan.
  • The command classification must be maintained when new build or test tools are added.

I accept these costs because correctness matters more than token savings at a verification boundary. A smaller context is not useful if the system reaches the wrong conclusion.

Discussion

This incident changed how I think about AI-facing developer tools. A proxy that rewrites command output is not a transparent pipe. It is part of the program. It has behavior, edge cases, and failure modes. It deserves the same suspicion as any parser or adapter.

The safest design is to preserve structured signals for structured decisions. Exit codes should remain exit codes. Test counts should come from a test runner’s reliable interface when available. File content should stay byte-for-byte faithful unless transformation is the explicit purpose of the command.

Summaries still have value. They can identify repeated warnings, highlight likely causes, or present a short overview before raw details. But a summary should be labeled as a summary. It should not impersonate the underlying result.

There is also a broader lesson for agent evaluation. Checking whether the final response sounds correct is not enough. The execution path must preserve the evidence used to produce that response. Otherwise, a fluent agent may confidently repeat an error introduced upstream.

Conclusion

The proxy was designed to save tokens, and it did. It also made a failing compiler run look successful. The agent was not verifying the build anymore; it was verifying a sentence produced by another program.

The fix was to restore the real contract. Build, type-check, and test commands bypass the proxy and use the process exit code directly. Output destined for a file also stays outside the rewriting path.

My main lesson is simple: anything that summarizes output is a second program that can be wrong. Exit codes are the contract. Prose is not.

Other

Next, I want to make the boundary more visible. A better design would label transformed output clearly and retain a link or path to the raw log. I also want command policies that distinguish display-only output from verification output and file-bound data.

I would also like to add tests for the proxy itself. Useful cases would include a command that returns a non-zero exit code with quiet output, a compiler failure caused by missing dependencies, and exact output redirected into a file. These are plans, not features I have completed.
