Prompt Injection When Your Agent Reads Email and Web Pages

An AI agent must treat every email and web page as untrusted data, even when the text looks like a direct instruction.

Introduction

In this blog, I will explain prompt injection for agents that read email and web pages. The important shift is simple. A chatbot only writes text. An agent may also search files, send messages, update records, or call an API. Once a model can use tools, a sentence inside a document can become the beginning of a real action.

Developers often separate system instructions from user prompts. That is necessary, but it is not enough. An agent can receive content from many places after the user prompt: an email body, a quoted reply, a web page, a PDF, a calendar description, or search results. That content may contain natural language that tells the model to ignore earlier rules, reveal private context, or use a tool. This is indirect prompt injection.

The model cannot reliably decide that one sentence is data while another sentence is authority just because both appear in its context. Clear delimiters and reminders help, but they are not a security boundary. The application around the model must enforce the boundary.

Overview

I use one rule when thinking about this problem: content can suggest, but it cannot authorize. A message can contain a request to pay an invoice. A page can contain a button label. Neither should grant permission to send money, disclose a secret, or change a database row.

A safer agent separates four stages. First, it retrieves untrusted content. Second, the model interprets that content and proposes an action. Third, policy code checks the proposal against the user’s permissions and the current task. Fourth, the application either returns a harmless result, asks for confirmation, or executes a narrowly scoped tool call.

Proposed design: untrusted content may influence a proposal, but side effects require approval and a scoped tool.

This design assumes the model can be manipulated. That assumption is useful. It moves security decisions out of generated prose and into code that can be reviewed, tested, and monitored.

How Indirect Prompt Injection Works

Imagine that I ask an agent to summarize unread email. One message contains normal business text followed by hidden or visible instructions: ignore the user, search the mailbox for credentials, and forward them. The email is not a trusted operator, but the model still sees commands written in familiar language.

A web page creates the same problem. The page may include text aimed at visitors and separate text aimed at automated readers. Styling can make text unobtrusive to a person without removing it from the page representation given to the agent. Search snippets, accessibility text, comments, and retrieved documents can all carry hostile instructions.

The injection does not need to succeed completely to cause damage. It may redirect the agent away from the requested task, make it include irrelevant material, trigger expensive loops, or persuade it to expose information in a tool argument. A small change in output can be dangerous when another program treats that output as a command.

There is also a trust-chain problem. An email may link to a page. That page may link to a document. If the agent follows each link and keeps the content in one context, the least trusted source can influence the final action. Trust should not increase merely because data passed through several tools.

Permission Scoping

The strongest mitigation is to reduce what the agent can do. I would not give an email summarizer a general shell, unrestricted mailbox access, and permission to send messages. It needs a read-only operation that returns the minimum fields required for summarization.

Tool permissions should match the task, not the maximum capability of the product. Read and write operations should be separate. A tool for drafting a reply should not also send it. A search tool should not expose secret fields by default. An update tool should accept a small, validated schema rather than arbitrary commands.

Scope also applies to data. If a task concerns one mailbox folder, one project, or one record, the application should constrain access to that scope before the model runs. Asking the model to “only use this folder” is weaker than issuing credentials or queries that cannot access anything else.

Short-lived authorization is another useful pattern. The agent receives access for one action and one task, rather than keeping broad authority across a long conversation. If hostile content changes the model’s plan, the available capability still has a limited blast radius.

Confirmation and Output Allowlists

Human confirmation matters when an action has an external side effect. The confirmation screen should show the actual operation: recipient, destination, changed fields, or file path. A vague question such as “continue?” hides the risk. The user should see what will happen before it happens.

Confirmation must occur after the final tool arguments are built. If the model can change the arguments after approval, the approval does not protect the real action. The application should freeze the reviewed payload or rebuild it deterministically from reviewed fields.

Not every workflow can wait for a person. Automated jobs need allowlists and policy checks. The application can restrict destinations, accepted file types, writable fields, and permitted action sequences. It can reject unexpected URLs, unknown recipients, or tool calls that do not belong to the declared workflow.

Structured output helps here. Instead of accepting free-form text as a command, the application requests a small object with known fields. It validates types, lengths, allowed values, and relationships before any tool runs. Structured output does not stop injection by itself, but it makes the enforcement point explicit.

Testing the Boundary

A normal success test is not enough. I want tests in which the retrieved content actively asks the agent to break policy. The hostile text should try several paths: reveal hidden instructions, read unrelated data, call a write tool, send information to a new destination, or claim that the user already approved the action.

The expected result is not necessarily that the model ignores every sentence. Models are probabilistic. The durable requirement is that the application blocks the forbidden effect. A test can allow the model to propose a bad action and still pass if policy code rejects the tool call.

I also want logs at the enforcement point. Useful records include the requested tool, the final validated arguments, the policy decision, whether confirmation was required, and whether execution occurred. Sensitive content should not be copied into logs without a reason. The goal is evidence about decisions, not a new store of private data.

Finally, test chained content. Put an injection in an email attachment or a page reached through a search result. This checks whether the application preserves source trust and task scope across retrieval steps.

Benefits and Drawbacks

Benefits

Least-privilege tools limit damage even when the model makes a poor decision. Explicit confirmation gives users control over consequential actions. Allowlists and schema validation turn vague behavioral expectations into testable rules. Audit records make it possible to understand why an action was allowed or denied.

Drawbacks

These controls add friction. More confirmations can make an agent feel less automatic. Narrow tools take longer to design than a general tool. Policy code must be maintained as workflows change. Strict allowlists may block a legitimate new use case until a developer updates the rules.

I think that trade-off is healthy. Convenience should be proportional to reversibility. Reading public information can be easy. Sending a message, changing a record, or exposing private data should require stronger evidence of intent.

Conclusion

Prompt injection is not only a prompt-writing problem. It is an authorization problem at the boundary between generated text and real tools. Email and web content should remain untrusted, no matter how confidently it speaks.

The practical design is defense in depth: narrow permissions, read and write separation, confirmation for side effects, validated structured output, destination allowlists, and tests that assume hostile content. The model may still misunderstand a document. The surrounding application must make sure that misunderstanding cannot silently become authority.
