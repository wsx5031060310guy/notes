當 AI Agent 讀取電子郵件與網頁：Prompt Injection 風險

AI Agent 必須把每封電子郵件與每個網頁都視為不受信任的資料，即使其中的文字看起來像直接指令。

前言

這篇文章要說明讀取電子郵件與網頁的 AI Agent，為何會面對 Prompt Injection。關鍵變化很簡單。Chatbot 只會產生文字；Agent 卻可能搜尋檔案、傳送訊息、更新紀錄或呼叫 API。當模型可以使用工具時，文件裡的一句話就可能成為真實操作的起點。

開發者通常會把 system instruction 與 user prompt 分開。這是必要措施，但還不夠。Agent 接收使用者要求後，還會取得郵件本文、引用回覆、網頁、PDF、行事曆說明或搜尋結果。這些內容可能寫著要求模型忽略先前規則、洩漏私人資訊或使用工具的自然語言指令。這就是間接 Prompt Injection。

當不同來源的句子進入同一個 context，不能只靠模型穩定判斷哪一句是資料、哪一句有指揮權。清楚的分隔符號與提醒確實有幫助，但它們不是安全邊界。真正的邊界必須由模型外圍的應用程式強制執行。

概觀

我用一項原則理解這個問題：內容可以提出建議，但不能授予權限。郵件可以寫著請支付發票，網頁可以顯示按鈕文字，但它們都不該因此取得匯款、公開機密或修改資料庫紀錄的權限。

較安全的 Agent 會把流程分成四個階段。第一，取得不受信任的內容。第二，由模型解讀內容並提出操作。第三，以 policy code 依照使用者權限與目前任務檢查提案。第四，應用程式回傳無害結果、要求確認，或執行權限範圍明確的工具呼叫。

建議的設計：不受信任內容可以影響操作提案，但有副作用的操作必須經過確認，並使用限權工具。

這種設計直接假設模型可能遭到操控。這是一項有用的假設，因為它把安全判斷從生成文字移到可審查、可測試、可監控的程式碼。

間接 Prompt Injection 如何運作

假設我請 Agent 摘要未讀郵件，其中一封郵件在正常商務內容後面，加入可見或隱藏的指令：忽略使用者要求、搜尋信箱中的憑證，再把它們轉寄出去。寄件者不是受信任的系統管理者，但模型看到的仍是熟悉的自然語言命令。

網頁也有相同問題。頁面可以同時放入給訪客看的文字，以及專門影響自動讀取工具的文字。CSS 可以讓人不容易注意到某段內容，卻不會讓它從交給 Agent 的頁面資料中消失。搜尋摘要、無障礙文字、註解與檢索文件，都可能攜帶惡意指令。

攻擊不必完全成功也能造成損害。它可能讓 Agent 偏離原始任務、夾帶無關資料、進入昂貴的迴圈，或誘使模型把資訊放進工具參數。當另一個程式把模型輸出視為命令時，小幅度的輸出改變也可能很危險。

還有信任鏈問題。郵件可以連到網頁，網頁再連到文件。如果 Agent 依序開啟連結，並把所有內容放入同一個 context，信任度最低的來源就可能影響最終操作。資料不該只因為經過多個工具，信任等級就自動提升。

限制工具權限

最強的緩解方式，是減少 Agent 能做的事。我不會讓郵件摘要工具同時擁有一般 shell、無限制信箱存取與傳送訊息權限。它只需要 read-only 操作，而且只回傳摘要所需的最少欄位。

工具權限應該符合目前任務，而不是產品能提供的最大能力。讀取與寫入操作要分開。草擬回覆的工具不該順便送出郵件。搜尋工具不該預設回傳機密欄位。更新工具應接收範圍小、可驗證的 schema，而不是任意命令。

範圍限制也適用於資料。如果任務只涉及一個信箱資料夾、一個專案或一筆紀錄，應用程式就應在模型執行前限制存取範圍。只在 prompt 要求模型「只能看這個資料夾」，不如提供根本無法存取其他位置的 credential 或 query。

短效授權也是實用模式。Agent 只在一項任務中的一次操作取得權限，而不是在整段長對話中保留廣泛權限。即使惡意內容改變模型計畫，可用能力的影響範圍仍然有限。

確認機制與輸出允許清單

操作會造成外部副作用時，人工確認很重要。確認畫面應顯示實際操作，例如收件者、目的地、變更欄位或檔案路徑。只問「是否繼續」會隱藏風險。使用者必須在執行前清楚看到將發生什麼事。

確認必須發生在最終工具參數建立之後。如果模型能在核准後修改參數，核准就沒有保護真正的操作。應用程式應凍結使用者看過的 payload，或從已確認的欄位以確定性方式重新建立參數。

不是每個 workflow 都能等待人工操作。自動工作必須使用 allowlist 與 policy check。應用程式可以限制目的地、接受的檔案類型、可寫入欄位與允許的操作順序。意外 URL、未知收件者，或不屬於宣告流程的 tool call 都應被拒絕。

Structured output 在此也有幫助。應用程式不接受自由文字作為命令，而是要求只含已知欄位的小型 object。在執行任何工具前，先驗證型別、長度、允許值與欄位關係。Structured output 無法單獨阻止 Prompt Injection，但能讓規則的強制點更明確。

測試安全邊界

一般的成功測試不夠。我會加入由檢索內容主動要求 Agent 違反政策的測試。惡意文字可以嘗試多種路徑：要求揭露隱藏指令、讀取無關資料、呼叫寫入工具、把資訊送到新目的地，或謊稱使用者已經批准操作。

預期結果不一定是模型忽略每一句惡意文字。模型具有機率性。可長期維持的要求，是應用程式必須擋住被禁止的副作用。即使模型提出危險操作，只要 policy code 拒絕 tool call，安全邊界仍然有效。

我也希望在規則強制點留下紀錄。實用資訊包括要求的工具、最終驗證參數、政策判斷、是否需要確認，以及操作是否真的執行。不應毫無理由地把敏感內容複製到 log。目標是保留決策證據，而不是建立另一個私人資料儲存區。

最後還要測試鏈式內容。可以把攻擊指令放在郵件附件，或經由搜尋結果才開啟的頁面，確認應用程式在多次檢索後，仍能保留來源的信任層級與任務範圍。

優點與缺點

優點

最小權限工具能在模型判斷錯誤時限制傷害。明確確認可讓使用者掌握重要操作。Allowlist 與 schema validation 能把模糊的行為期待轉成可測試規則。稽核紀錄則能說明某項操作為何獲准或被拒絕。

缺點

這些控制會增加摩擦。確認次數太多，Agent 會顯得不夠自動化。設計窄用途工具比通用工具更花時間。Workflow 改變時也要維護 policy code。嚴格 allowlist 可能暫時阻擋合理的新用途，直到開發者更新規則。

我認為這是健康的取捨。便利程度應該與操作能否復原成正比。讀取公開資訊可以很容易；傳送訊息、修改紀錄或公開私人資料，則應要求更強的意圖證據。

結論

Prompt Injection 不只是 prompt 寫法問題，而是生成文字與真實工具邊界上的授權問題。無論電子郵件與網頁內容說得多肯定，都應保持不受信任的狀態。

實務設計需要縱深防禦：限制權限、分離讀取與寫入、對副作用要求確認、驗證 structured output、建立目的地 allowlist，並用惡意內容測試系統。模型仍可能誤解文件；外圍應用程式必須確保這種誤解不會悄悄變成權限。

其他

接下來我想為 Agent workflow 建立一組小型 evaluation set。每個案例把正常任務與不同來源的攻擊指令放在一起，再記錄提案操作與實際操作是否都留在 policy 範圍內。我也想比較不同確認介面，找出既能呈現精確副作用，又不會增加太多負擔的最小設計。
