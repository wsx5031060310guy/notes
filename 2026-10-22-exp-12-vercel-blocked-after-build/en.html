Build Green, Deploy Blocked: The One Log Line I Missed

A successful build did not mean my deployment was allowed to reach production.

Background

In this blog, I will describe a deployment failure that looked contradictory at first. A Vercel build finished successfully. The deployment then stopped during the “Deploying outputs” stage. My first search of the log found no error, because I searched for the wrong word.

This was not a compiler failure. It was not a failed test. It was also not a generic platform outage. The platform examined the built output and blocked it because the application would have shipped a dependency version with a known critical vulnerability.

The distinction matters. A build answers one question: can the project produce an output? A deployment platform may ask more questions after that. It can decide that a technically valid output is not acceptable to release. When these stages are shown in one pipeline, a green build can make the later rejection feel surprising.

What I saw

The visible sequence was simple. The build completed. The pipeline moved to “Deploying outputs.” Then the deployment failed.

I did what many developers do when a long log fails: I searched for “error.” That search returned nothing useful. The one useful line did not start with “error.” It started with “Vulnerable version of”.

The build completed, but a later vulnerability check blocked the deployment output.

That wording described the reason, but it did not match my search term. I had reduced a full log to a narrow filter and accidentally removed the evidence I needed.

The result was a false mental model. I saw “build succeeded” and assumed the application was deployable. I saw no line containing “error” and assumed the failure message was missing. Both conclusions came from reading only part of the pipeline and only part of the log.

Why the first check failed

Log search is useful when the vocabulary is predictable. Compilers often print “error.” Test runners often print “failed.” A security policy does not have to use either word. It may name the condition directly: vulnerable package, blocked output, denied action, or policy violation.

In this case, the stage name was already a clue. The failure happened after the build had passed. Re-running the same build or reading only compiler output could not explain a decision made during deployment.

I should have changed the question. Instead of asking “where is the build error?”, I needed to ask “what happened after the build?” That directs attention to the transition between stages, the first line that differs from the successful path, and the platform’s own deployment checks.

A green stage proves only that stage. It does not certify every later gate.

The actual cause

The application included a dependency version associated with a known critical vulnerability. Vercel allowed the build to finish, then blocked the deployment while processing the output.

This ordering is reasonable. A platform may need the resolved dependency tree or final output before it can apply a release policy. The important point for debugging is that policy enforcement and compilation are separate checks, even when the interface presents them as one deployment run.

The build result was therefore accurate. The source could be compiled into an output. The deployment result was also accurate. That output did not satisfy the platform’s security requirement. There was no contradiction once I separated those two statements.

The fix

I upgraded the affected dependency. That was the fix listed by the deployment evidence. I did not treat the successful build as permission to bypass the security block.

I also changed how I inspect this class of failure. When a deployment fails after a green build, I read the complete deployment log with vercel inspect --logs. I do not search only for “error.” I look at the stage boundary and read the lines around the first failure.

This is a small debugging habit, but it prevents a large waste of time. A filtered view is a hypothesis. If the filter returns nothing, that does not prove the log has no cause. It may prove only that the cause uses different language.

The sequence I now recommend is:

  1. Confirm which stage passed and which stage failed.
  2. Open the complete deployment log.
  3. Read the first message after the last successful stage.
  4. Search for the exact phrase shown by the platform, not only generic words.
  5. Fix the stated dependency or policy issue, then run the normal deployment again.

Discussion

Benefits of stage-aware debugging

It narrows the search without hiding evidence. If compilation passed, I can stop looking for a syntax error. If output deployment failed, I can focus on policy checks, packaging, and platform decisions. The stage gives context; the full log gives the reason.

It also makes status reports more precise. “The build passed, but deployment was blocked” is more useful than “deploy failed.” It tells another engineer that the produced output exists and that a later gate rejected it.

Drawbacks of keyword-only triage

A keyword filter is fast, but it silently assumes the system will use my vocabulary. That assumption breaks across tools and stages. Security checks may say “vulnerable.” Permission systems may say “denied.” Capacity checks may say “limit reached.” None needs to print the literal word “error.”

Keyword-only triage can also make success indicators too powerful. A green build badge is visually strong. It invites me to ignore a later red stage or to treat it as infrastructure noise. The safer reading is local: green means this one check passed.

A better operational habit

I want deployment reviews to preserve stage names and the first failing line. A short summary should say what passed, what failed, and quote the platform’s reason. If an automated summary cannot preserve that evidence, the complete log should remain easy to open.

I also want dependency checks earlier in the development workflow. That would provide faster feedback, but it would not replace the platform gate. Local and CI checks can differ from the policy applied to the final deployment output. The platform remains the final source for why it accepted or rejected that release.

Conclusion

The build was green because the code produced an output. The deployment was blocked because that output contained a dependency version with a known critical vulnerability. The only useful clue began with “Vulnerable version of”, so my search for “error” hid it.

The fix was to upgrade the dependency. The debugging lesson was broader: identify the failing stage, then read its complete log. Do not let one successful stage answer a question it was never designed to answer.

Other

Next, I want to make the failure summary capture the stage boundary and the first policy message without replacing the raw log. I also want to review whether dependency checks can run earlier, so the same issue appears before the final deployment step.

These are improvements I want to try. The change I completed in this case was the dependency upgrade and the use of the full deployment logs for diagnosis.
