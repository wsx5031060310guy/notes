Build 綠燈，部署卻被擋：我漏看的那一行日誌

Build 成功，只代表產得出成果物，不代表它一定能部署到正式環境。

背景

這篇文章要記錄一個起初看起來很矛盾的部署失敗。Vercel 的 build 已成功完成，但流程接著在「Deploying outputs」階段停止。我第一次查看日誌時沒有找到原因，因為我搜尋了錯誤的字。

這不是編譯失敗，不是測試失敗，也不是一般的平台中斷。平台檢查 build 後的成果物，發現應用程式會帶著一個已有重大漏洞的相依套件版本上線，因此阻擋部署。

這個差異很重要。Build 回答的是「專案能否產生成果物」。部署平台在這之後還能提出其他問題。成果物即使技術上有效，仍可能不符合發布條件。當多個階段都顯示在同一條 pipeline 裡，綠色的 build 很容易讓後續拒絕顯得反常。

我看到的現象

畫面上的順序很簡單。Build 完成，pipeline 進到「Deploying outputs」，接著部署失敗。

面對很長的失敗日誌，我做了許多開發者都會做的事：搜尋「error」。這次搜尋沒有給我有用的結果。唯一真正重要的那一行並不是以「error」開頭，而是「Vulnerable version of」。

Build 已完成，但後續的漏洞檢查阻擋了部署成果物。

那行文字其實已經說明原因，只是它不符合我的搜尋條件。我把完整日誌縮成一個過窄的篩選結果，也順手把需要的證據藏了起來。

這讓我建立了錯誤的理解。我看到「build succeeded」，便以為應用程式已經可以部署。我找不到含有「error」的行，又以為日誌沒有留下原因。兩個結論都只來自部分 pipeline 與部分日誌。

第一次檢查為何失敗

如果能預測用詞，搜尋日誌很有用。編譯器常輸出「error」，測試工具常輸出「failed」。但安全性政策沒有義務使用其中任何一個字。它可能直接描述狀況，例如有漏洞的套件、遭阻擋的成果物、被拒絕的操作，或違反政策。

這次的階段名稱本身就是線索。問題發生在 build 通過之後。重跑同一個 build，或只讀編譯器輸出，都無法解釋部署階段做出的決定。

我應該改變問題。不要再問「build error 在哪裡」，而要問「build 之後發生了什麼」。這會把注意力拉回階段交界、與成功流程不同的第一行，以及平台自己的部署檢查。

綠色階段只能證明該階段成功，不能替後續所有關卡背書。

真正原因

應用程式包含一個有已知重大漏洞的相依套件版本。Vercel 讓 build 完成，之後在處理成果物時阻擋部署。

這個順序很合理。平台可能要先取得解析後的相依關係或最終成果物，才能套用發布政策。除錯時要記得，即使介面把它們放在同一次部署執行裡，政策執行和編譯仍是兩種不同的檢查。

所以 build 結果沒有錯。程式碼確實能編譯出成果物。部署結果也沒有錯。該成果物不符合平台的安全要求。把這兩句話分開後，就沒有矛盾。

修正方式

我升級了受影響的相依套件。這是部署證據直接指出的修正。我沒有因為 build 成功，就嘗試繞過安全性阻擋。

我也改變了這類問題的檢查方式。綠色 build 之後若部署失敗，我會使用 vercel inspect --logs 閱讀完整的部署日誌。我不再只搜尋「error」，而會先確認階段交界，再讀第一個失敗點周圍的文字。

這只是小習慣，卻能避免浪費很多時間。篩選後的畫面只是一項假設。篩選結果為空，不代表日誌沒有原因；它可能只表示原因用了別的詞。

我現在建議依照以下順序檢查：

  1. 確認哪個階段通過、哪個階段失敗。
  2. 開啟完整的部署日誌。
  3. 閱讀最後一個成功階段之後的第一則訊息。
  4. 搜尋平台實際顯示的文字，不要只搜尋通用關鍵字。
  5. 修正明確指出的相依套件或政策問題，再執行正常部署。

討論

依階段除錯的好處

它能縮小範圍，但不會先把證據丟掉。如果編譯已通過，我就不必繼續找語法錯誤。如果是在部署成果物時失敗，就能專注於政策檢查、封裝與平台決策。階段提供脈絡，完整日誌提供原因。

狀態回報也會更精確。「Build 通過，但部署遭阻擋」比「deploy failed」更有用。其他工程師可以立刻知道成果物存在，只是被後續關卡拒絕。

只用關鍵字分流的缺點

關鍵字篩選很快，但它默默假設系統會使用我的詞彙。跨工具、跨階段後，這個假設很容易失效。安全檢查可能寫「vulnerable」，權限系統可能寫「denied」，容量檢查可能寫「limit reached」。它們都不必包含「error」。

只看關鍵字也容易放大成功指標的影響。綠色 build 標記很顯眼，會讓人忽略後面的紅色階段，或把它當成平台雜訊。比較安全的讀法是局部解讀：綠色只表示這一項檢查通過。

更好的操作習慣

我希望未來的部署檢查能保留階段名稱與第一行失敗訊息。短摘要應該說清楚什麼通過、什麼失敗，並引用平台給出的理由。若自動摘要無法保留證據，完整日誌仍應該可以快速開啟。

我也想把相依套件檢查放到更早的開發流程。這能提早提供回饋，但不能取代平台關卡。本機與 CI 的檢查，可能不同於平台對最終部署成果物套用的政策。平台仍是判斷該次發布為何被接受或拒絕的最後依據。

結論

程式能產生成果物，所以 build 是綠色。成果物含有一個已知有重大漏洞的相依套件版本，所以部署遭阻擋。唯一有用的線索以「Vulnerable version of」開頭，因此我搜尋「error」時把它漏掉了。

修正方式是升級相依套件。更廣泛的除錯教訓是：先辨識失敗階段，再閱讀該階段的完整日誌。不要讓一個成功階段回答它原本就不負責的問題。

其他

下一步，我想讓失敗摘要保留階段交界與第一則政策訊息，同時不要取代原始日誌。我也想檢查能否提早執行相依套件檢查，讓相同問題在最後部署前就出現。

這些都是我準備嘗試的改善。這次已完成的變更只有升級相依套件，以及診斷時改讀完整部署日誌。
