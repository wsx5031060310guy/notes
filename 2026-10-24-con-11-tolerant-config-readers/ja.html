バージョンをまたいで共有する設定ファイル：Tolerant Reader と未知の値

共有設定ファイルは一つのインターフェースであり、それを読むすべてのプログラムがクライアントです。

はじめに

設定は一つのプログラムだけが所有する内部データに見えます。しかし実際には、同じマシン上の公開インターフェースになることがあります。CLI が読み、デスクトップアプリが編集し、後から定期ジョブが利用します。異なるバージョンが同じファイルに触れる場合もあります。その時点で、設定変更は互換性の変更にもなります。

TOML は人が読みやすく、文字列、整数、真偽値、配列、日時、テーブルなどを一般的なデータ構造へ明確に対応させます。ただし、構文として正しい TOML でも、特定のアプリケーションが内容を拒否する場合があります。Parser がキーと値を理解できても、アプリケーションがその値の意味を知らないことがあるからです。

構文検証は「正しい TOML か」を確認します。アプリケーション検証は「このバージョンが安全に使える設定か」を確認します。これは別の問いです。堅牢な設定 Reader は両方を扱う必要があります。

概要

一つのファイルを二つのプログラムが共有するとします。新しい Writer が設定を追加し、その後に古い Reader が起動します。Reader が完全一致の schema を要求すると、自分に無関係な設定でもファイル全体を拒否し、本来の処理を始められません。

互換性のある Reader は未知の任意項目を無視し、必須値の非対応は明確に報告します。

判断すべきケースは三つあります。

  • Reader が必要としない未知のキー。
  • 既知のキーに設定された有効な値。
  • 既知のキーに設定された非対応または不正な値。

すべてを致命的エラーにすると硬直的です。すべてを許すと危険です。無関係な追加には寛容で、正しい動作に必要な設定には厳格であることが実用的です。

未知の値が古い Reader を壊す理由

よくある実装は、ファイル全体を閉じた data type に直接 bind します。すべての field と enum 値が一致しなければなりません。予想外の内容を拒否できるため安全に見えますが、すべての Reader と Writer を強く結合します。古いソフトウェアが追加項目なしでも動けるのに、新しい任意項目が破壊的変更になります。

特に enum のような値は壊れやすいです。新しいプログラムが新しい mode を覚えて、その名前を保存します。古いプログラムは従来の名前しか知りません。ファイルは正しい TOML のままでも、deserialize や application validation に失敗します。

失敗は起動の非常に早い段階で起こります。ログ、network 接続、要求された command より先に停止するため、症状が設定と無関係に見えます。定期ジョブでは非ゼロの exit code しか見えないこともあります。別の component は新しい Reader を使うため正常です。一つの小さな不一致が、共有所有によってシステム問題になります。

Tolerant Reader の設計

Martin Fowler の Tolerant Reader pattern は、client が必要な data だけを読み、不要な追加項目を無視する考え方です。設定では、まず文書を一般的な構造として parse し、その後で自分が対応する設定だけを取り出します。未知の任意キーは触らずに残せます。

これは「何でも受け入れる」という意味ではありません。不正な構文は拒否します。動作に関係する既知の設定が非対応の値なら、それも拒否します。保存先の型が違う場合や必須 mode が未知の場合、推測値で続行するほうが危険です。

実用的な判断ルール

  • 任意で、このプログラムの責任外にある未知のキーは無視します。
  • 既知のキーは型と許可値を検証してから受け入れます。
  • 必須キーがない、または利用不能なら失敗させます。
  • 明示された非対応値を黙って default に置き換えません。

default は設定が欠けており、契約で既定値が定義されている場合に適します。明示的に要求された mode を実装できないなら、黙った fallback は互換性問題を隠します。

Writer は未知の data を保持することも重要です。ファイルを読み、一項目を変え、全体を書き戻す場合、理解できないキーを削除してはいけません。古い editor が新しい tool の設定を消す可能性があります。対象を限定した編集や、未知の値を round-trip できる表現が役立ちます。

検証と役に立つエラー

検証は処理開始前の startup で行います。エラーにはファイル、キー、受け取った値、分かる場合は許可値を含めます。「設定が不正です」だけでは不十分です。利用者はファイル全体を確認し、どの Reader が拒否したか推測することになります。

役に立つ文面は「キー X の値 Y は使用できません。この Reader は A または B に対応します」という形です。キーを消すのか、値を変えるのか、Reader を更新するのかも示します。ただし secret をエラーへコピーしてはいけないため、診断にも redaction が必要です。

定期ジョブでは、標準エラー出力の最初の実用的な行を保存します。exit code だけを通知する wrapper は最良の手掛かりを失います。設定 parse の段階で止まったのに、認証や rate limit と推測してはいけません。

test は進化の両方向を対象にします。古い Reader に未知の任意キーを含むファイルを渡し、起動できることを確認します。使用するキーに非対応値を渡し、具体的な message で失敗することも確認します。古い Writer が保存時に未知のキーを消さないことも検証します。

アップグレードと固定

寛容さは偶発的な破損を減らしますが、version 管理は必要です。同じファイルを意図的に共有するプログラムは一つの互換性グループです。可能なら一緒に更新します。同期できない場合は、対応する最古の Reader を文書化し、新しい Writer の出力をその Reader で試します。

自動化に予測可能な動作が必要なら version 固定が有効です。共有ツールは個別ではなく一組として固定します。Writer だけ先へ進み Reader が残ると、同じ問題が再発します。更新前には、各 Reader に config validation command があれば実行します。

別の方法は所有を分離することです。各プログラムに専用ファイルを与え、共有設定だけを小さく安定した層へ置きます。重複は増えますが、隠れた結合を減らせます。関係のないアプリが global document を書き直す代わりに、migration tool が既知の値だけを明示的に移せます。

利点と欠点

利点

  • 新しい任意設定が古い Reader を自動的に壊しません。
  • エラーが互換性の境界を具体的に示します。
  • 文書化した契約内で tool を独立して進化させられます。
  • 定期処理が曖昧な症状ではなく見える理由で失敗します。

欠点

  • 未知のキーを無視するとスペルミスを隠す場合があります。
  • 未知の data を保持する Writer は複雑になります。
  • 複数 version の互換性 test が必要です。
  • 寛容すぎると必要な migration を先送りします。

スペルミス対策として、owner ごとに table や namespace を分けられます。自分が所有する table の未知キーには warning を出し、他のプログラムが所有する table では無視します。全 component に全ファイルを理解させず、typo を検出できます。

まとめ

設定ファイルは単なる text ではなく、Writer と Reader の契約です。正しい TOML でも、すべての version が同じ値を理解するとは限りません。Reader は不要な追加を無視し、使用する設定を検証し、安全に動けない場合は正確な message で停止すべきです。

重要な問いは「parse できるか」ではありません。「自分の責任範囲はどこで、別のプログラムが進化したとき何をするか」です。二つの version がファイルを共有する前に決める必要があります。

今後

共有設定向けの小さな互換性 test matrix を試したいです。各 Writer が代表的なファイルを生成し、対応対象の Reader が検証します。また、古い Writer が未知の設定を消さないよう、round-trip 編集も test したいです。upgrade が定期ジョブへ届く前に互換性を可視化できます。
