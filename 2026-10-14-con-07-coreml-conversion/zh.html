iOS 裝置端機器學習：將模型轉換為 Core ML

這篇文章要說明如何把訓練完成的模型轉成 Core ML，並用驗證流程確保轉換完成不是終點。

前言

裝置端機器學習改變了應用程式的邊界。應用程式可以在資料產生的地方執行推論，不必把每張影像、每段聲音或每筆感測器資料都傳到遠端服務。這可能改善隱私、回應速度與離線體驗，但也把更多責任交給應用程式團隊。模型必須適合平台、接收正確輸入、產生可理解的輸出，並在真實裝置上穩定運作。

對 iOS 應用程式而言，Core ML 是執行模型時使用的格式與框架。在其他環境訓練的模型通常需要經過轉換。Apple 提供 coremltools，讓開發者從常見的機器學習框架轉換模型，也能檢查、測試及最佳化結果。產生模型檔案的指令很重要，但它只是可靠流程的一部分。

概觀

我把模型轉換視為「契約移轉」。來源模型有一份契約，內容包括輸入名稱、shape、資料型別、前處理、輸出名稱，以及輸出的意義。Core ML 模型需要用應用程式可使用的形式保留這份契約。只要其中一項悄悄改變，檔案即使能成功載入，預測結果仍可能錯誤。

基本路徑並不複雜。我先準備已訓練且已評估的來源模型，明確定義它期待的輸入，再用 coremltools 轉換。接著使用具代表性的樣本，比較來源模型與轉換後模型的結果。最後才整合進應用程式，並在目標實機上測試。

進入實機測試前，應先比較來源模型與轉換後模型的輸出。

定義模型契約

輸入 shape

輸入 shape 不是微不足道的細節。影像模型可能期待 batch 維度、固定的高度與寬度，以及特定的 channel 順序。序列模型可能在支援範圍內接受可變長度。應用程式必須知道哪些維度固定、哪些維度可以變動。我偏好在轉換前把這些條件寫清楚，而不是稍後讓行動應用程式碼自行猜測。

資料型別與前處理

數值型別很重要，但前處理往往更容易被忽略。像素縮放、channel 順序、色彩空間、正規化、tokenization 與 feature 排列，都是模型行為的一部分。如果訓練時使用一種轉換，而應用程式使用另一種，即使轉換後的 graph 正確，整個系統仍會得到錯誤結果。影像輸入也能表達相關 metadata，因而有機會減少應用程式內重複的前處理程式。

輸出的意義

只把輸出命名為 scores 並不足以形成文件。我需要知道它代表 logits、機率、座標、embedding，或其他形式。分類模型也需要穩定的 index 與 label 對應。清楚的輸出名稱能讓產生的 interface 更容易閱讀，也讓測試失敗時更容易找到原因。

使用 coremltools 轉換

coremltools 為支援的來源框架提供統一轉換 API，實際轉換路徑則取決於來源模型。核心做法是以支援的形式 export 或 trace 模型，宣告輸入，並有意識地選擇轉換 option。我不會在尚未了解範例對 shape 與型別做了哪些假設前，直接複製一段轉換 snippet。

轉換可能揭露無法直接對應到 Core ML 的 operation。發生這種情況時，有用的問題不只是 converter 是否回報 error。我也會檢查來源 graph 是否包含動態行為、不支援的 operation，或應該留在模型外的前處理。有時需要調整 export，有時需要用另一種方式表達同一項運算。真正的依據應該是模型行為，而不是某一條轉換指令是否方便。

deployment target 也是設計條件，它會影響 converter 可以使用哪些模型能力。我會依照應用程式真正支援的裝置政策選擇，而不會只為了簡化轉換就提高要求，卻忽略因此無法使用的使用者。

檢查轉換後的準確度

轉換後的模型應該和來源模型比較。我會準備涵蓋一般情況、邊界情況，以及已知困難案例的代表性輸入。對每一筆輸入，我記錄來源輸出與 Core ML 輸出，再用適合該任務的容許差異進行比較。

分類任務可以比較 score 與預測 label；回歸任務可以衡量數值差異；物件偵測或 segmentation 則需要符合任務特性的比較方式，因為很小的數值變化也可能移動 box、threshold 或 mask。要求每個 bit 完全相同未必合理，但無法解釋的變化仍是停止流程並調查的理由。

我也會分開「轉換驗證」與「應用程式驗證」。在開發機器上的比較，回答的是轉換表示是否接近來源模型；實機測試回答的則是包含 camera frame、audio buffer、記憶體壓力與應用程式碼的完整流程能否運作。兩種檢查都需要，而且回答不同問題。

量化的取捨

量化用較低精度表示模型中的數值。它可以減少儲存空間，也可能改善執行特性，但同時可能改變預測。最佳選擇取決於模型、任務，以及支援的執行環境。不存在一項通用設定，可以讓每個模型都變小，又完全保留相同準確度。

我把最佳化視為第二個實驗，而不是預設勾選項目。我先建立通過驗證的轉換 baseline，再建立最佳化候選版本，並用相同評估資料測試兩者。我會比較模型大小、任務品質與實機行為。如果品質變化無法接受，可以保留 baseline，或嘗試不同的最佳化方式。

這個順序也讓診斷更容易。如果轉換和量化同時進行，regression 會有兩個可能原因。若一般轉換已先通過驗證，新的差異就更容易連結到最佳化步驟。

實作流程

  1. 固定已知的來源模型 artifact 與前處理定義。
  2. 建立代表性樣本，並保存來源模型的預期輸出。
  3. 明確宣告輸入名稱、shape、型別與彈性。
  4. 使用符合應用程式目標的 option，透過 coremltools 轉換。
  5. 載入 Core ML 模型，將輸出與保存的 baseline 比較。
  6. 整合到一條小型應用程式路徑，在目標實機測試真實輸入。
  7. 完成以上步驟後，再用相同樣本評估量化或其他最佳化。

這套流程能縮小每種失敗的搜尋範圍。export 失敗屬於轉換前；數值差異屬於轉換驗證；camera 方向、feature 準備與 UI 整合屬於應用程式層；效能與記憶體行為則應在實機檢查。

討論

優點

裝置端推論可以把敏感輸入留在本機，沒有網路時仍能運作，也能從預測路徑移除一次網路來回。Core ML 還提供平台原生的模型描述與載入方式。有紀律的轉換流程會讓機器學習與應用程式碼之間的邊界更清楚。

缺點

裝置環境有其限制。模型大小、記憶體用量、啟動行為與散熱狀況都很重要。支援廣泛的裝置範圍，可能限制實際可用的模型功能。除非產品具有經過謹慎設計的模型分發機制，模型更新也需要跟著應用程式的發布流程前進。

最困難的缺點是錯誤的信心。模型 package 能載入，不代表語意等價；只用一筆樣本完成快速 demo，也不能證明準確度。準備測試 corpus 與可重複比較的成本，遠低於完成整合後才除錯錯誤預測的成本。

結論

把模型轉換成 Core ML 是一條 pipeline，而不只是檔案格式操作。我會定義輸入與輸出契約、有意識地轉換、和來源模型比較、在實機測試，並在建立 baseline 後才最佳化。這樣可以避免便利的工具掩蓋模型行為的變化。

真正的問題不是「converter 是否完成」，而是「應用程式是否從模型得到相同意義」。當這個問題有證據支持時，Core ML 檔案才準備好成為產品的一部分。

其他

接下來我想建立一個可重複使用的小型驗證 harness。它會保存代表性輸入、執行兩種模型、回報符合任務特性的差異，並把結果和模型 artifact 一起保存。我也想加入裝置端的 latency、記憶體與能源行為量測，而不是假設較小的 package 一定比較快。
