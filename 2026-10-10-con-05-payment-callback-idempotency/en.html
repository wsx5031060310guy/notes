Payment Callbacks: Idempotency, Signatures, and Compare-and-Swap

In this blog, I will explain how to accept repeated payment callbacks without trusting, losing, or applying the same event twice.

Introduction

A payment callback is a message from a payment gateway to my server. It tells the application that something happened outside the current browser session. A payment may have succeeded, failed, expired, or been refunded. This server-to-server message is often the most reliable place to update the order.

However, a callback is not a command that arrives exactly once. Networks retry. Gateways retry when they do not receive a timely response. A server can finish its database work and crash before sending the response. Two workers can receive the same event at nearly the same time. Delivery can also arrive out of order.

That means the handler must expect duplicates from the beginning. It must also prove that the sender is trusted and control how an order moves from one state to another. I use three separate ideas for these jobs: signature verification, idempotency, and compare-and-swap.

Overview

These three ideas solve different problems. A signature answers, “Did this message come from a party that knows the shared secret or private key?” Idempotency answers, “Have I already accepted this logical event?” Compare-and-swap answers, “Is the order still in the state that allows this transition?”

None can replace the others. A valid signature does not make duplicate delivery impossible. An idempotency key does not prove who sent the request. A state comparison does not detect every replay if the repeated action is valid from the current state.

I would keep the callback endpoint narrow. It should read the request in the form required by the gateway, verify authenticity, parse a small event envelope, find the internal order, and perform one transactional state change. Email, analytics, fulfillment, and other slow work can follow through durable internal jobs.

Proposed design: verify the callback before parsing and applying its business event.

Verify Before Processing

Use the exact signed representation

Gateways define their own signature schemes. Some sign the raw HTTP body. Others combine selected fields, a timestamp, or request metadata. The handler must follow that contract exactly. If the framework parses JSON and then serializes it again, spaces and field ordering may change. A signature over the rebuilt body can fail even when the message is legitimate.

I would capture the raw bytes first when the provider signs the body. I would then calculate the expected signature with the configured secret and compare it using a constant-time comparison where the platform provides one. Only after verification would I trust fields such as the order reference, amount, currency, and event type.

Transport encryption is still necessary, but HTTPS and message signatures answer different questions. HTTPS protects the connection. The signature lets the application authenticate the message according to the gateway’s protocol.

Reject invalid input safely

An invalid signature should not reach order logic. Logs should contain enough information to investigate, but they should not store secrets, complete payment credentials, or unnecessary personal data. Error responses should also avoid revealing how the expected signature was calculated.

Timestamp checks can reduce replay risk when the gateway includes a signed timestamp. The acceptable window and retry behavior must follow the provider’s documentation. A server clock problem can otherwise reject valid events, so time synchronization and observability matter.

Idempotency and Event Identity

Idempotency means that repeating the same logical operation has the same intended effect as doing it once. For callbacks, the easiest implementation usually starts with a stable event identifier supplied by the gateway. I would store that identifier in a table with a unique constraint.

The unique constraint is important. A prior “does this event exist?” query followed by an insert has a race. Two workers can both see nothing and both continue. Letting the database arbitrate one unique insert closes that gap.

The key needs the right scope. If event identifiers are unique only within a merchant account or gateway, the stored key should include that scope. A key that is too broad can suppress unrelated events. A key that is too narrow can let the same event through twice.

I would store a compact processing record: source, event identifier, order identifier, event type, receipt time, and outcome. The full payload should be retained only when there is a clear operational and privacy reason. Data minimization matters for payment systems.

A duplicate callback should normally receive a successful response after the system confirms that the original event was already accepted. Returning an error for a harmless duplicate can cause more retries. This response does not mean every downstream task finished; it means the event is safely recorded and will not be double-applied.

Compare-and-Swap for Order State

Deduplicating the event is not enough because different events can race. A late “payment succeeded” callback could arrive after a refund or cancellation workflow. The application needs an explicit state machine that defines which transitions are legal.

Compare-and-swap expresses the rule inside the database update. Instead of reading an order as pending and later updating it unconditionally, the statement updates it only where the identifier matches and the current state is still pending. The affected-row count tells the handler whether it won the transition.

This conditional update removes a dangerous gap between read and write. If another transaction changes the state first, the stale worker updates zero rows. The handler can then inspect the current state and decide whether the event is a duplicate, a legal later transition, or an inconsistency that needs review.

Money-related side effects must share the same boundary. If the event record says “processed” but the order update rolls back, or the order changes while the event record is lost, retries become difficult to reason about. I would put event claiming and the order transition in one database transaction. External effects should be driven by a durable outbox or job created in that same transaction.

Proposed design: claim the event and compare the order state in one transaction, then commit once.

Demo Flow

I would test the design with behavior, not only status codes. First, send one valid callback and confirm that the event and order transition are committed. Then send the identical callback again and confirm that no balance, entitlement, inventory, or notification is applied twice.

Next, send two copies concurrently. Exactly one transaction should claim the event. I would also test an invalid signature, an unknown order, a mismatched amount or currency, and a valid but late event that is not allowed from the current state.

Finally, simulate a crash after the database commit but before the HTTP response. The retry should find the stored event and return safely. This test represents a common reason for legitimate duplicate delivery.

Benefits and Drawbacks

Benefits

  • Signature verification keeps unauthenticated requests away from order logic.
  • A database uniqueness rule handles concurrent duplicate delivery.
  • Conditional updates make state transitions explicit and atomic.
  • A stored event record provides evidence for support and reconciliation.

Drawbacks

  • Every gateway has a different signing and retry contract.
  • Event records need retention, privacy, and cleanup decisions.
  • Out-of-order events still require a carefully defined state machine.
  • Downstream work needs its own idempotency or durable delivery pattern.

Conclusion

A reliable payment callback handler assumes that delivery is repeated, concurrent, and sometimes out of order. It authenticates the exact message first. It claims a correctly scoped event key under a unique constraint. It changes the order only when the current state permits that transition.

The central lesson is simple: “received once” is not a safe system property. “Applied once under a verified and legal transition” is the property to design and test.
