Why My Tender-Matching Tool Thought a CT Scanner Was a Computer

In this blog, I will explain why broad keywords broke a tender-matching tool and how I made each match easier to trust.

Disclosure: I drafted this post with AI assistance from my own project notes, and I review it before publishing.

Background

I built a small internal tool to match open Taiwanese government tenders to a company's capabilities. The first version used a keyword table. This was a deliberate choice. Each match could show the exact words that triggered it.

That explanation mattered. A person reviewing a tender could see why the tool selected it. If the reason was wrong, I could change one rule and inspect the result. There was no hidden score to interpret.

The weakness appeared when I reviewed the full list of open tenders. The rules recognized categories, but many tender titles named products instead. A title might say laptop, tablet, network firewall, or wireless network without using the broader category already in the table. Those tenders were relevant, but the tool missed them.

The tempting fix was to add shorter and broader words. That would increase recall quickly. It would also create matches that looked reasonable until someone read the original Chinese title.

Overview

Keyword matching has two common failure modes. A narrow rule misses relevant records. A broad rule catches unrelated records. In this case, the language made broadening especially risky.

The bare word for "computer" also appears inside the Chinese term used for a CT scanner. A rule for "workstation" can match an irrigation agency's field station. A rule for "monitor" can match patient monitors. Ticket-machine paper can also be pulled into a search intended for computers.

These are not obscure edge cases invented for a test. They appeared while I reviewed the live list of open tenders. Each false match had a visible reason, which made the mistake easy to diagnose. The problem was not the matcher. The problem was what the keyword claimed to mean.

I adopted one rule: the qualifier must live inside the keyword itself. Instead of relying on a broad word plus later interpretation, the keyword should carry enough context. "Laptop computer" and "network firewall" are examples. The rule becomes more specific at the point where the match is created.

The adopted workflow: add a qualified keyword, run it against the live tender list, and review every new match before merging.

Demo

My review process starts with the live corpus, not with a few handpicked examples. I run the current keyword table against all open tenders and record the existing matches. Then I add a candidate keyword and run the same list again.

I compare the before and after counts. The count is useful, but it is not the decision. A larger number can mean better coverage, more noise, or both. I therefore inspect every newly matched tender line by line.

For each addition, I ask a simple question: would I be comfortable showing this tender to the company as a match? I also read the trigger shown by the tool. If the trigger is a broad fragment with a different meaning in context, the keyword is not ready.

This is where qualified phrases help. A phrase such as "laptop computer" says more about intent than "computer" alone. "Network firewall" is narrower than "firewall" when the goal is to match a particular capability. The phrase may miss some wording variants, but its reason is clear. I can add another specific phrase later after measuring it.

In one measurement, one company's matches increased from 150 to 174. I reviewed every addition and found zero noise among those new matches. That result belonged to that live list and that keyword change. I do not treat it as a universal benchmark. The useful part was the method: compare, inspect, then merge.

The same process also tells me when not to add a word. "Monitor" sounds relevant in isolation, but patient-monitor tenders change its meaning. "Workstation" sounds like computing equipment, but a field station for an irrigation agency is not the intended match. A broad term that needs repeated exceptions is a sign that the qualifier belongs in the keyword.

Discussion

Benefits

The biggest benefit is debuggability. The tool can state, "this title matched because of this phrase." When the result is wrong, I can inspect the phrase, the title, and the surrounding meaning. The path from symptom to rule is short.

The second benefit is controlled change. I do not judge a keyword from intuition alone. I measure it against the live corpus. The before and after counts show the size of the change, while the line-by-line review checks its quality.

This also makes review easier. A teammate does not need to understand an embedding model or an opaque relevance score. The evidence is the tender title and the keyword that fired. A visible wrong reason is easier to discuss and fix than an invisible score.

Drawbacks

Specific phrases require maintenance. Real tender titles use variations, abbreviations, and different word order. A qualifier that removes noise can also reduce recall. I have to add variants carefully rather than assume one phrase covers the whole category.

Manual review also takes time. It is practical when I inspect only the newly matched set, but it would become expensive if every change produced a very large difference. The method works because the tool exposes the delta instead of asking me to reread the entire corpus.

Keyword rules do not understand meaning in the way people do. They match text. That limitation is acceptable here because the output is explainable and the changes are measured. The matcher is a filter for human review, not a final decision maker.

I also learned to separate recall from trust. Adding a broad term can make the match count look better immediately. If reviewers start ignoring noisy results, however, the tool becomes less useful. A smaller set with visible reasons can be more useful than a larger set that needs guessing.

Conclusion

The CT scanner match was not a strange failure of search technology. It was the predictable result of a keyword that carried too little context.

I fixed the process by putting the qualifier inside the keyword and testing each change against the live list of open tenders. I compare counts, review every new match, and merge only after the added results make sense. In the measured change described here, the match count grew from 150 to 174 with zero noise in the additions.

Explainable keyword matching is crude, but that can be a strength. When the system gives a wrong answer for a visible reason, I know where to start.

Other

I want to keep building a test set from reviewed tenders. It should include positive examples, known confusing terms, and titles near the decision boundary. That would make later rule changes easier to compare without replacing the live-corpus review.

I also want to explore a hybrid design. Specific keywords could keep providing clear evidence, while a semantic method could suggest records that the rules may have missed. I would still present the trigger and require review before treating a suggestion as a match.
