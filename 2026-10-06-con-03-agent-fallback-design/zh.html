讓 LLM 備援鏈明確失敗，而不是悄悄降級

這篇文章要說明，如何保留 LLM 備援的好處，又不讓它掩蓋已經故障的主要路徑。

前言

LLM 備援鏈看起來是一項可靠性功能。偏好的模型無法回答時，應用程式改呼叫另一個模型。請求仍會完成，排程工作維持綠燈，使用者也會收到文字。

遇到短暫服務中斷或速率限制時，這很有用。但備援也可能把長期故障藏起來。替代模型的推理能力、長上下文處理、工具呼叫行為、延遲或成本可能不同。收到格式正確的回應，只能證明有某個模型回答，不能證明產品政策指定的模型回答了。

因此，我把備援視為降級模式，而不是一般成功。系統可以繼續，但必須記錄切換、讓維運人員看見，必要時也要讓使用者知道。沒有人看得見的備援不是優雅降級，而是未回報的路由變更。

概觀

良好的備援設計要在第一次 API 呼叫前開始。每個請求都需要明確政策。政策要指定主要路徑、哪些錯誤可以重試、重試預算、可接受的備援路徑，以及整個請求必須停止的條件。

政策也要定義品質契約。較小或調校方向不同的模型，可能足以處理分類與短摘要，卻不適合安全性審查、財務決策，或會改變外部狀態的操作。一條全域備援清單很難表達這些差異。

我傾向依任務類型決定是否允許備援。每一類都能定義是否可降級，以及降級後還能使用哪些工具。如此一來，呼叫端可以知道完成的回應符合原始契約，還是只符合縮小後的契約。

建議的設計：在固定預算內重試；只要由備援模型回答，就必須標示並告警。

無聲備援為什麼危險

傳輸成功不等於政策成功

多數健康檢查只問服務有沒有回應。這是傳輸層問題。LLM 路由器還需要問第二個問題：是哪條路徑產生回應？如果主要路徑失敗，由備援路徑回答，端點可以回傳成功的 HTTP 狀態，但路由政策其實不健康。

這對排程工作特別重要。工作執行器通常記錄是否完成，而不是回答品質。如果每項工作都轉到備援，儀表板仍可能維持綠色。狀態持續越久，結果越難比較，也越難解釋非預期回答。

不同模型不是可直接互換的零件

模型可以使用相同介面，行為卻不同。它們可能用不同格式呼叫工具、拒絕不同類型的要求、在長上下文遺失指示，或產生比流程預期更短的回答。API 相容不代表行為等價。

每一條核准路徑都應用它可能接收的任務測試。如果某條路徑尚未在一類任務上評估，就不該默默接手那類任務。它可以保留給手動操作，或限制在風險較低的任務。

暫時備援會變成新常態

暫時恢復路徑常比預期存在更久。若沒有記錄實際模型，維運人員只會看到成功的工作。主要路徑可能一直故障，直到明顯的品質問題出現。那時，系統可能已依不同政策產生許多輸出。

重試與備援政策

先分類錯誤

不是每種錯誤都該換模型。短暫網路中斷或供應商服務異常，可以考慮重試。無效憑證、不支援的模型名稱、格式錯誤的請求，通常需要修正設定或程式。把同一個壞請求送往多條路徑，只會浪費時間，也讓原始原因更難找。

路由器應保留第一個有意義的錯誤，並把後續嘗試連到同一筆紀錄。最終紀錄要包含指定模型、每次嘗試的路徑、切換原因，以及最後實際回答的模型。

設定重試預算

重試需要嘗試次數與經過時間的上限。沒有預算時，多個供應商會把延遲一層層疊加，讓單一使用者請求長時間占用資源。退避與隨機延遲可以減少同步重試流量，但不能取代停止條件。

預算也要尊重呼叫端。互動請求與背景報表的時間期待不同。呼叫端應能選擇政策，而不是被迫繼承一個隱藏的全域設定。

降級時必須標示

允許備援時，結果應帶有機器可讀的中繼資料，例如指定路徑、實際路徑、備援原因、嘗試次數與政策名稱。面向使用者的畫面不一定每次都要顯示技術警告，但系統要保留足夠資訊，讓高敏感度任務可以顯示。

高影響任務應該停止，而不是回傳未標示的較弱答案。明確失敗讓維運人員有機會修復路徑。由未核准模型產生、看似有自信的答案，事後通常更難補救。

可觀測性與使用者標示

我會把備援視為獨立事件，不只是在大型日誌裡多放一個欄位。實用的檢視包括：各任務類型的備援率、引發切換的主要錯誤、實際回答模型，以及降級狀態持續多久。

告警應關注持續或異常的備援行為。一次成功切換可能符合預期；備援率上升、每次排程都使用備援，或未核准的任務類型使用某條路徑，就需要處理。確切門檻依服務而異，所以應放在政策中，不適合硬套通用數字。

追蹤資料可以把最終回答與先前嘗試串起來；指標顯示趨勢；日誌保留錯誤細節。它們回答不同問題，而且都不能取代在結果中記錄實際模型。

標示也有助於客服與除錯。使用者回報答案品質不佳時，團隊可以確認那是主要模型或備援模型產生的。缺少這項事實，調查只能靠猜。

優點與缺點

優點

  • 供應商短暫故障時，不必停止所有任務。
  • 依任務制定政策，可避免敏感工作流向未核准路徑。
  • 實際路徑的中繼資料能協助調查事故與品質問題。
  • 有上限的重試可控制延遲與資源使用。

缺點

  • 路由器會成為需要測試與維護者的政策引擎。
  • 提示詞、工具或模型改變後，核准路徑必須重新評估。
  • 每次無害切換都警告，可能干擾使用者。
  • 更多遙測資料代表更多儲存與檢查工作。

設計目標不是消除所有備援，而是讓它有意圖、有邊界，而且看得見。系統可以維持可用，但不應假裝什麼都沒改變。

結論

LLM 備援鏈應回答兩個問題：請求能不能繼續，以及結果是否仍符合任務政策。傳統的運作時間檢查通常只回答第一個問題。

我會把實際回答模型放進每個結果，在切換路徑前分類錯誤，套用重試預算，並依時間監控備援行為。若任務不能接受較弱路徑，正確的備援就是明確失敗。

只有在降級看得見時，優雅降級才真的有用。

其他

下一步，我想建立一套小型政策測試。它會注入網路錯誤、被拒絕的模型名稱、格式錯誤的請求與慢速回應，再確認選中的路徑，以及回傳給呼叫端的中繼資料。

我也想比較依任務制定的政策與單一全域鏈。成果不會只是一個品質分數，而是列出哪些任務允許降級、哪些需要標示，以及哪些情況必須停止。
