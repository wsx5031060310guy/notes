静かに壊れない LLM フォールバックチェーンの設計

このブログでは、壊れた主経路を隠さずに LLM のフォールバックを活用する設計を説明します。

はじめに

LLM のフォールバックチェーンは、信頼性を高める機能に見えます。優先モデルが回答できなければ、アプリケーションは別のモデルを呼びます。要求は完了し、定期ジョブは成功のままになり、利用者にも文章が届きます。

短い障害やレート制限の回避には役立ちます。しかし、長く続く異常を隠すこともあります。代替モデルは、推論力、長い文脈への対応、ツール呼び出し、遅延、コストが異なるかもしれません。正常な応答が返ったという事実だけでは、製品方針で選んだモデルが答えたとは確認できません。

私はフォールバックを通常の成功ではなく、縮退運転として扱います。処理を続ける場合でも、経路の変更を記録し、運用者に見えるようにし、必要なら利用者にも示します。誰にも見えないフォールバックは、優雅な縮退ではありません。報告されていないルーティング変更です。

概要

よい設計は最初の API 呼び出しより前に始まります。要求には明示的な方針が必要です。優先経路、再試行できる失敗、再試行予算、利用できる代替経路、処理を停止する条件を決めます。

品質の契約も決めます。小型モデルや別の調整を受けたモデルでも、分類や短い要約なら許容できる場合があります。一方、セキュリティレビュー、金銭に関わる判断、外部状態を変える操作には使えないかもしれません。全タスク共通の一つのチェーンでは、この違いを十分に表現できません。

私はタスク分類ごとにフォールバックの可否を決めたいと考えます。各分類は、縮退を許すか、どのツールを使えるかを定義します。呼び出し元は、完了した応答が元の契約を満たしたのか、縮小した契約だけを満たしたのかを判断できます。

改善案：決めた予算内で再試行し、代替モデルが答えた場合は必ず表示して通知します。

静かなフォールバックが危険な理由

通信の成功と方針の成功は別です

多くのヘルスチェックは、サービスが応答を返したかを確認します。これは通信の質問です。LLM ルーターには、どの経路が応答を作ったかという二つ目の質問が必要です。主経路が失敗して代替経路が答えた場合、HTTP は成功でもルーティング方針は異常です。

定期処理では特に重要です。ジョブ実行基盤は通常、回答品質ではなく完了を記録します。すべてのタスクが代替経路へ流れても、ダッシュボードは緑色のままかもしれません。その状態が長いほど、結果の比較や予想外の回答の説明が難しくなります。

モデルは交換可能な部品ではありません

同じ API を使うモデルでも動作は違います。ツール呼び出しの形式、拒否する要求、長い文脈での指示保持、回答の長さが変わることがあります。API 互換性を行動の同等性と考えてはいけません。

承認する経路は、受け取る可能性があるタスクで試す必要があります。あるタスク分類で評価していない経路に、そのタスクを静かに渡すべきではありません。手動利用に残すか、危険が小さい範囲だけに絞ります。

一時的な代替が通常運転になります

一時的な復旧経路は、予想より長く残りがちです。実際のモデルを記録しなければ、運用者には成功したジョブしか見えません。目に見える品質問題が出るまで、主経路の故障が放置されます。その時点では、別の方針で多くの出力が作られている可能性があります。

再試行とフォールバックの方針

失敗を分類します

すべての失敗で別モデルを呼ぶ必要はありません。短いネットワーク障害やプロバイダー側の一時的な問題なら再試行が有効です。無効な認証情報、未対応のモデル名、不正な要求は、設定やコードの修正が必要です。同じ壊れた要求を複数の経路へ送ると、時間を使い、最初の原因も見えにくくなります。

ルーターは最初の意味のあるエラーを保持し、その後の試行を関連付けるべきです。最終記録には、要求されたモデル、試した経路、切り替え理由、実際に答えたモデルを残します。

再試行予算を設けます

再試行には回数と経過時間の上限が必要です。上限がなければ、複数のプロバイダーによって遅延が積み重なり、一つの要求が長時間リソースを占有します。バックオフとジッターは同時再試行を減らしますが、停止条件の代わりにはなりません。

予算は呼び出し元の事情も考慮します。対話型の要求とバックグラウンドのレポートでは、許容時間が違います。呼び出し元が方針を選べるようにし、隠れた全体設定だけに依存しない設計が必要です。

縮退を表示します

フォールバックを許す場合、結果には要求経路、実経路、切り替え理由、試行回数、方針名などの機械可読なメタデータを付けます。すべての画面で技術的な警告を出す必要はありません。しかし、重要なタスクでは表示できる情報を保持します。

影響が大きいタスクでは、弱い回答を無表示で返すより停止を選びます。明確な失敗なら運用者が経路を修正できます。未承認モデルの自信に満ちた回答は、その後の修復が難しくなります。

可観測性と利用者への表示

フォールバックは大きなログの一項目だけでなく、独立したイベントとして追跡したいです。タスク分類ごとの発生率、切り替えを起こした主エラー、実際の回答モデル、縮退状態の継続時間を確認できるようにします。

アラートは継続的または異常な動きに向けます。一度の成功した切り替えは想定内かもしれません。しかし、発生率の上昇、すべての定期実行でのフォールバック、未承認のタスク分類での利用は確認が必要です。基準はサービスごとに違うため、共通の数字ではなく方針に置きます。

トレースは最終回答とそれ以前の試行をつなぎます。メトリクスは傾向を示し、ログはエラーの詳細を残します。それぞれ質問が違います。どれを使っても、結果メタデータに実モデルを記録する必要はなくなりません。

表示はサポートにも役立ちます。利用者が弱い回答を報告したとき、主経路か代替経路かを確認できます。この情報がなければ、調査は推測になります。

利点と欠点

利点

  • 短いプロバイダー障害で全タスクを停止せずに済みます。
  • タスク別方針により、重要な処理を未承認経路から守れます。
  • 実経路のメタデータにより、障害と品質問題を追跡できます。
  • 制限付き再試行で遅延とリソース使用を抑えられます。

欠点

  • ルーター自体が、テストと所有者を必要とする方針エンジンになります。
  • プロンプト、ツール、モデルが変われば承認経路を再評価する必要があります。
  • 無害な切り替えまで警告すると利用者の負担になります。
  • 保存し確認すべきテレメトリが増えます。

目的はフォールバックをすべて防ぐことではありません。意図的で、制限があり、見える動作にすることです。可用性を保ちながら、何も変わっていないふりをしない設計です。

まとめ

LLM のフォールバックチェーンは、要求を続けられるか、結果がタスク方針を満たすかという二つの質問に答える必要があります。一般的な稼働確認は前者しか見ません。

私は、実際に答えたモデルをすべての結果に含め、経路を変える前に失敗を分類し、再試行予算を適用し、時間に沿ったフォールバックの動きを監視したいです。弱い経路を許せないタスクでは、明確な失敗が正しいフォールバックです。

縮退運転は、縮退が見える場合にだけ機能します。

今後

次は小さな方針テストを作りたいです。ネットワークエラー、拒否されたモデル名、不正な要求、遅い応答を注入し、選ばれた経路と呼び出し元へ返すメタデータを確認します。

タスク別方針と一つの共通チェーンも比較したいです。単一の品質点数ではなく、縮退を許せる分類、表示が必要な分類、必ず停止すべき分類を一覧にします。
