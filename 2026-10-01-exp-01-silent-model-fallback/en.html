My AI Agent Quietly Ran on a Smaller Model for Four Weeks

In this blog, I will describe how a healthy-looking fallback chain hid a serious decline in my scheduled AI jobs.

Disclosure: I drafted this post with AI assistance from my own project notes, and I review it before publishing.

Introduction

I run a self-hosted AI agent framework. It handles about twenty scheduled jobs. These jobs prepare reports, audits, and summaries, then deliver the results to Telegram.

The system had a primary language model and a fallback chain. That design looked sensible. If the main model became unavailable, a smaller model could keep the jobs running. The scheduler would not stop. Reports would still arrive.

That is exactly what happened, but not in the way I wanted. The provider retired the primary model. Every call to it returned HTTP 400 with the message “model not supported.” The framework caught the error and silently moved every request to a small flash-lite class model.

The jobs stayed green. Messages kept arriving. No alert fired. From the outside, the automation looked healthy.

What happened: the retired model turned an outage into silent quality decay.

Overview

A fallback chain changes the meaning of success. Without a fallback, an unavailable model produces a visible failure. With a fallback, the same outage can produce a valid response from a different model. The transport layer succeeds, but the quality characteristics may change.

This distinction matters for scheduled work. A person using an interactive chat may notice that an answer feels weaker. A cron job has no such judgment. It sees a completed request, saves the response, and continues.

My monitoring watched whether jobs completed and whether Telegram received messages. It did not watch which model actually answered. It also did not treat repeated fallback use as an incident. The system therefore measured delivery while ignoring execution identity.

Proposed design: record the model that actually answered, alert when fallback use stays high, and cap delivered output. So far only the model switch and the output cap are in place.

How the Failure Stayed Invisible

Green status was too narrow

The scheduler considered a job successful when the request eventually returned and the delivery step completed. A response from the fallback model met that definition. The dashboard was technically correct, but the definition was incomplete.

A basic health check also returned “PONG.” That proved that some model could answer a tiny prompt. It did not prove that the primary model was available. It did not prove that the scheduled job used the intended capability. The check tested reachability, not the whole contract.

Quality decay arrived later

The first clear symptoms appeared weeks later. One daily web-performance job entered a loop. It produced a transcript of fake tool calls that was about 360,000 characters long. The chat adapter split the transcript into roughly two hundred Telegram messages and eventually hit Telegram flood control.

Another symptom appeared in an investment journal. It reported a Bitcoin price about eleven percent away from the real price. Each event looked like a separate content problem. Together, they suggested that the execution environment had changed.

The dangerous part was the delay. The model outage started first. Obvious quality failures appeared later. A system that only alerts on visible job failures gives silent degradation time to spread across many tasks.

Demo of the Investigation

I stopped looking only at the scheduler status. I queried the framework’s session database instead. The model column showed which model had actually served each scheduled session.

The result made the pattern clear. Every scheduled session since early September showed the fallback model. The primary model name was not appearing as the serving model because its calls had failed before generation.

This query answered a better question: not “Did the job return something?” but “Which model produced the thing I delivered?” That is the evidence I had been missing.

For similar systems, I would inspect a small set of fields together:

  • The requested model.
  • The model that actually answered.
  • The reason for fallback.
  • The job or session identifier.
  • The final delivery size and delivery result.

These fields separate provider failure, fallback behavior, content quality, and delivery pressure. A single green status cannot express all of them.

Benefits and Drawbacks

Benefits

The fallback chain did preserve availability. Reports and summaries did not all disappear when the primary model was retired. For temporary rate limits or short provider outages, that behavior can be useful. It gives the system a controlled way to continue.

Fallback also buys investigation time. An operator can repair the primary route without every downstream task failing at once. This is valuable when the output is low risk and the degraded model is still suitable for the task.

Drawbacks

Fallback can convert a loud outage into silent quality decay. The scheduler sees success. The chat adapter sees text. The recipient sees a message. None of those observations confirm that the intended model handled the work.

A smaller model may also fail differently. It can loop, produce less reliable facts, or imitate tool calls instead of using tools correctly. The fallback mechanism itself is not the problem. The problem is allowing degraded operation without a label, a budget, or an alert.

The Fix

I first switched the primary model so scheduled jobs could use a supported model again. That removed the immediate source of the HTTP 400 responses.

I also added a hard cap to the chunking chat adapter. It will deliver no more than 12,000 characters as chat messages. If the output is longer, the remaining content is saved to a file and linked. This does not fix a looping model, but it prevents one bad response from becoming hundreds of messages.

The larger lesson is to alert on fallback rate. A single fallback may be normal. A sustained rate across scheduled sessions means the primary path is unhealthy, even if every job eventually returns text.

I would now define the operating contract this way:

  1. Record the requested and actual model for every session.
  2. Count fallback events by job and by reason.
  3. Alert when fallback use becomes sustained or widespread.
  4. Label degraded output when the recipient should know.
  5. Cap delivery volume independently from model output.
  6. Test the primary route directly instead of accepting any “PONG.”

These controls cover different failure boundaries. Model telemetry detects the routing problem. Output caps protect the delivery channel. Direct health checks verify the intended dependency.

Conclusion

My automation did not fail closed. It failed quietly and kept producing plausible output. That was more dangerous than a red job because it encouraged me to trust the system.

A fallback chain is not only an availability feature. It is a degraded operating mode. I need to observe it as such. The most important signal is not whether a response exists. It is whether the intended model answered, how often the system fell back, and whether the delivered output stayed within safe limits.

A “PONG” is useful, but it is not proof. Green delivery is useful, but it is not proof. The execution record must show what actually happened.

Other

Next, I want to make fallback identity visible in each scheduled session and build a simple report of fallback rate by job. I also want to test failure cases deliberately: an unsupported primary model, an oversized response, and a fallback that produces unusable content.

The goal is not to remove fallback. The goal is to make degraded operation obvious, bounded, and reversible.
