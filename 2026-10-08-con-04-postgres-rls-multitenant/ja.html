マルチテナント SaaS のための Postgres Row Level Security 入門

この記事では、Postgres の Row Level Security を使い、見えにくい落とし穴を増やさずにテナント境界をデータの近くで守る方法を説明します。

はじめに

マルチテナント SaaS では通常、複数の組織のデータを同じデータベースに保存します。そのため、多くのテーブルはテナント識別子を持ちます。すべてのクエリは、現在処理しているテナントに属する行だけを返す、または変更する必要があります。

アプリケーションコードですべてのクエリにテナント条件を追加する方法は理解しやすい一方、条件を一つ書き忘れただけでセキュリティ境界を越えてしまいます。新しいレポート、バックグラウンドジョブ、raw SQL のいずれでも、このルールが抜ける可能性があります。コードレビューは役立ちますが、それだけではデータベースが危険なクエリを受け付けることを防げません。

一般に RLS と呼ばれる Postgres Row Level Security は、もう一つの強制ポイントを追加します。ポリシーによって、データベースロールが閲覧または変更できる行を決めます。ポリシーはクエリの一部として評価され、条件を満たさない行はアプリケーションに届く前に除外されます。

ただし、RLS を導入しても、通常の権限管理、慎重なコネクション管理、アプリケーション側の認可が不要になるわけではありません。RLS は多層防御の一つです。テナントコンテキストを明示し、短いスコープに限定し、テストし、ログから確認できるようにすると効果を発揮します。

概要

RLS は、対象テーブルと一つ以上のポリシーで構成します。RLS を有効にすると、通常のアクセスはポリシーによって許可されなければなりません。適用できるポリシーがなければ、Postgres はデフォルト拒否として扱います。そのため、エラーになるのではなく、クエリが一行も返さない場合があります。

ポリシーはすべてのコマンドに適用することも、SELECT、INSERT、UPDATE、DELETE のいずれかに限定することもできます。対象のデータベースロールも指定できます。ポリシー内の Boolean 式により、既存行のうち参照できるものと、新しい行の値として許可できるものを判定します。

USING 式は、コマンドから利用できる行を制御します。WITH CHECK は、INSERT または UPDATE が書き込もうとする行を検査します。単純なポリシーで WITH CHECK を省略すると、Postgres は USING 条件を再利用できます。ただし、読み取りと書き込みのルールが異なる場合は、意図が明確になるよう個別に記述するほうがよいでしょう。

改善案：各トランザクション内でテナントコンテキストを設定してから、RLS で保護されたテーブルをクエリします。

方針とテナントコンテキスト

行の属性として境界を持たせる

共有テーブルには通常、NULL を許可しないテナント列が必要です。ポリシーは、その値を現在のテナントコンテキストと比較します。セキュリティ上の判定が各行の中で完結するため、挙動を理解しやすくなります。

コンテキストには、トランザクションローカルな設定や、データベース側で制御できる別の仕組みを利用できます。重要なのはスコープです。プールされたコネクションは時間とともに異なるテナントから使われるため、セッション全体に残る値は次のリクエストへ漏れるおそれがあります。トランザクションローカルな値なら、トランザクション終了時に消えるので、より安全です。

アプリケーションはトランザクションを開始し、テナントコンテキストを設定して処理を実行し、commit または rollback します。コンテキストの設定とクエリの実行を一つの単位として扱う必要があります。コンテキストが設定される前に実行されたクエリが、過去の値や範囲の広いデフォルト値を黙って使う設計にしてはいけません。

認証をポリシーの外に置く

アプリケーションはテナントを選ぶ前に、呼び出し元を認証する必要があります。RLS の役割は、すでに決定されたテナント境界を強制することであり、テナントを推測することではありません。サーバーは、リクエストで渡された任意のテナント識別子をそのまま受け入れず、信頼できる ID とメンバーシップ情報からテナントを決めるべきです。

テナント内の認可には、複数のルールが必要になることがあります。正しいテナントに所属しているユーザーでも、請求書の承認や別メンバーの編集権限を持つとは限りません。単純なテナント分離は RLS で維持し、細かなプロダクト権限は、追加ポリシーまたはアプリケーションサービスのいずれかで明示的に適用するのがよいと考えています。

ポリシーの合成を理解する

Postgres は、適用可能な複数のポリシーを組み合わせます。permissive policy は OR、restrictive policy は AND で結合されます。このため、permissive policy を追加するとアクセス範囲が広がる可能性があります。ポリシーレビューでは、一つずつ個別に見るのではなく、適用されるポリシー全体を確認する必要があります。

別テーブルを参照する複雑なポリシーは、性能や並行処理の問題も引き起こします。公式ドキュメントには、ポリシー式が別の場所で変更中の行を参照するときに起こり得る競合状態が説明されています。通常のテナント条件を保護対象の行に置く設計は単純で、一般にテストもしやすくなります。

ENABLE、FORCE、バイパスロール

ENABLE ROW LEVEL SECURITY は、通常のテーブルアクセスに対してポリシー適用を有効にします。ただし、通常はテーブル所有者が RLS をバイパスします。migration とテストを所有者ロールで実行していると、テスト結果を誤解することがあります。ポリシーが適用されていないため、本来は危険なクエリが成功してしまうからです。

FORCE ROW LEVEL SECURITY を使うと、テーブル所有者もポリシーの対象になります。所有者ロールをアプリケーションプロセスでも使っている場合には有効ですが、所有権を持つロールと実行時ロールを分離するほうが明快です。なお、FORCE を指定しても、superuser や BYPASSRLS 属性を持つロールは制限されません。

BYPASSRLS は強力な権限です。この属性を持つ実行時ロールは、ポリシーに関係なくテナント境界を越えて読み取れます。superuser にも同じ問題があります。このようなロールは、管理、migration、復旧など、管理された作業だけに限定し、通常の Web リクエストには決して使わないようにします。

安全なロール構成は、あえて単純にします。一つのロールが schema object を所有し、別の制限付きロールでアプリケーションを実行します。特別な保守作業には、明示的なレビューを伴う別経路を使います。便利だからという理由で使い回された認証情報が、保護をひそかに無効化する事態を避けやすくなります。

改善案：アプリケーションロールには RLS を適用し、所有者または BYPASSRLS によるアクセスは管理された保守作業用に分離します。

テナント分離のテスト

正常系だけのテストでは不十分です。実用的な分離テストでは、少なくとも二つのテナントを作り、それぞれに異なる行を用意します。アプリケーションと同じロールで接続し、一つ目のテナントコンテキストを設定したうえで、二つ目のテナントの行を SELECT、UPDATE、DELETE できないことを確認します。

書き込みテストは、読み取りテストと同じくらい重要です。別テナントの行を INSERT する操作と、既存行のテナント識別子を変更する操作も試すべきです。WITH CHECK により、現在の境界外にある値が拒否されることを確認します。

コンテキストがない場合もテストします。期待する結果は設計として決めておきます。コンテキスト式がエラーを発生させるか、デフォルト拒否によって結果がゼロ行になるかのどちらかです。バックグラウンド処理では、多くの場合、エラーのほうが異常を検知しやすくなります。空の結果は業務上正しい場合もあるため、壊れたジョブが成功したように見える可能性があります。

コネクションプールには専用のテストが必要です。再利用されるコネクションを通じてテナント A とテナント B の処理を順に実行し、トランザクションローカルなコンテキストが残らないことを確認します。データベースのトランザクションが閉じられても、失敗によってアプリケーションの状態が予期しない場所に残ることがあるため、rollback の経路も確認してください。

最後に、テーブル所有者ロールとアプリケーションロールの両方で、選んだテストを実行します。この差を見ることで FORCE が有効かどうかを確認でき、特権ロールでのテストが誤った安心感を与えるのを防げます。HTTP status や repository の戻り値だけでなく、データベース上で実際に起きた結果を検証する必要があります。

利点と欠点

利点

  • クエリにテナント条件を書き忘れても、データベースが境界を強制します。
  • 制限された実行時ロールを共有する ad hoc SQL の経路にもポリシーが適用されます。
  • ポリシーが不足している場合、デフォルト拒否によって意図しないデータ公開を防げます。
  • 分離ルールを保護対象データの近くに置き、直接テストできます。

欠点

  • 除外された結果が、業務上正しい空の結果に見えることがあります。
  • 所有者、superuser、BYPASSRLS の挙動によって、テスト結果を誤解する可能性があります。
  • プールされたコネクションでは、トランザクションスコープのコンテキストを厳密に管理しなければなりません。
  • 重複するポリシーや別テーブルを参照するポリシーが増えると、監査とチューニングが難しくなります。

RLS は、「この実行時リクエストが触れられるのは、現在のテナントに属する行だけ」という狭く明確な invariant として使うと最も力を発揮します。あらゆるプロダクトルールを一つの大きなポリシー式に詰め込む用途には向きません。

まとめ

Postgres RLS を使うと、テナント分離を繰り返し守るコーディング規約ではなく、データベースの invariant にできます。必要なのは、明確なテナント列、読み取りと書き込みのポリシー、トランザクションごとに設定するコンテキスト、そしてポリシー適用をバイパスできないアプリケーションロールです。

ENABLE と FORCE は同じではありません。通常、テーブル所有者は RLS をバイパスしますが、FORCE を指定すると所有者にもポリシーが適用されます。それでも、superuser と BYPASSRLS ロールはバイパスできます。テストには実運用と同じロールを使い、テナントをまたぐ読み取りだけでなく書き込みも試す必要があります。

特に定期実行ジョブでは、予期しない空の結果をセキュリティ上のシグナルとして扱うのがよいと考えています。fail-closed の挙動はデータを守りますが、運用時には「対象データが存在しない」のか「テナントコンテキストが設定されていない」のかを区別できるだけの可視性が必要です。

今後

次は、再利用できる小さな分離テストハーネスを作りたいと考えています。二つのテナントを作成し、SELECT、INSERT、UPDATE、DELETE を実行して、再利用されるプール済みコネクションでも同じ検査を繰り返せるものです。

テナントをまたぐアクセスが本当に必要な保守作業についても、実行パターンを文書化したいと考えています。通常のリクエストハンドラーから利用できない、分離され、明示的で、監査可能な経路にすることが目標です。
