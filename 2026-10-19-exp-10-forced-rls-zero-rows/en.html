Row Level Security Returned Zero Rows and No Error

In this blog, I will describe how a background job passed every run while Row Level Security quietly hid all of its work.

Background

I worked on a multi-tenant SaaS that used Postgres Row Level Security, usually called RLS. The database stored rows for more than one tenant. A policy decided which rows a database session was allowed to see.

The application also used FORCE ROW LEVEL SECURITY. This matters because ordinary RLS has exceptions. Table owners normally bypass row security. FORCE makes the table owner obey the policies too. It reduces the chance that an application connection can accidentally read every tenant’s data.

A background job connected to the database without setting its tenant context. Its queries did not fail. They returned zero rows. The job interpreted the empty result as “nothing to do,” completed normally, and did the same thing on every run.

This is an uncomfortable kind of failure. There was no database exception to catch. There was no permission-denied message. The security control worked as designed: without a valid tenant identity, the session could not see tenant rows. The application was the part that misunderstood the result.

Overview

RLS adds an implicit filter to a query. A policy can compare a row’s tenant identifier with a value stored in the current database session. When the values match, the row is visible. When the session has no tenant context, the policy expression does not match.

That fail-closed behavior is useful. A missing security context should not reveal all rows. However, “safe” and “operationally correct” are different questions. A background job that expects tenant data must notice when its security context is missing.

  • The scheduler starts the job.
  • The job opens a database transaction.
  • The transaction should set the intended tenant context.
  • Queries then run under that context.
  • The job should treat an unexpected empty result as suspicious.

The failure and fix: a missing tenant context produced zero visible rows, so the transaction now sets the context explicitly before querying.

Demo

Consider a worker that processes records for one tenant. The worker receives a tenant identifier, opens a transaction, selects pending rows, performs its work, and commits.

In the broken path, one step was absent. The job opened its connection and queried immediately. FORCE RLS applied the policy to that connection, even though the connection used the table owner. Because the transaction had no tenant context, no rows satisfied the policy.

The SQL still executed successfully. From Postgres’s point of view, returning an empty result was valid. From the worker’s point of view, the result looked exactly like a tenant that had no pending records. The job therefore finished without an error.

A zero-row result can mean “there is no work,” or it can mean “this session is not allowed to see the work.”

The fix was to set the tenant context explicitly for each transaction. The placement is important. Connection pools reuse sessions, so a tenant value must not be treated as an informal global setting. The transaction establishes the context, runs the tenant queries, and then ends.

The job also needs an application-level signal when data is expected. The implemented fix included making jobs that expect data assert a non-zero count or log the tenant context they ran under. This turns an empty result into information that can be investigated instead of a silent success.

This does not mean every zero-row result should fail. Some jobs legitimately have no work. The assertion belongs where the job’s contract says data must exist. In other cases, logging the effective tenant context gives an operator enough evidence to distinguish an empty queue from a missing identity.

Discussion

Security filters are not ordinary errors

An authorization policy often removes data instead of throwing an exception. This is safer than returning rows to the wrong tenant. It also means error monitoring alone cannot prove the job is healthy. The query can be valid, fast, and empty for the wrong reason.

I should therefore define expected outcomes at the application layer. If a reconciliation job is created for a known tenant and a known set of records, zero may violate that expectation. If a polling job checks for optional work, zero may be normal. The database cannot infer that distinction from SQL alone.

Context should follow the transaction

Tenant context is part of the authorization decision. It should be established near the transaction that depends on it. This keeps the identity and the queries in one visible scope.

A better interface would make it difficult to run tenant SQL before context is set. For example, the worker could accept a tenant identifier and expose database operations only inside a transaction callback. That is a design recommendation, not something this incident proved was already built.

FORCE RLS exposes hidden assumptions

Without FORCE, code running as the table owner may appear to work because that role normally bypasses RLS. That success can hide a missing-context bug. The same code may behave differently when it later runs under a restricted role.

FORCE removes that accidental privilege for the owner. In this case, it made the security boundary consistent, but the worker had not been designed to supply the context the policy required. The right response was not to weaken the policy. It was to repair the worker’s transaction.

Test both isolation and expected visibility

RLS tests often focus on the most important negative case: tenant A must not read tenant B’s rows. That test is necessary, but it is incomplete. The positive case matters too: tenant A should see the rows that belong to tenant A after the correct context is set.

I also want a missing-context case. It should confirm that no tenant rows are exposed and that a job expecting data does not report a normal success. These tests describe both sides of fail-closed behavior.

Benefits

Explicit per-transaction context keeps the tenant identity close to the queries it authorizes. It works with FORCE RLS instead of relying on table-owner privileges. It also reduces ambiguity when a pooled connection is reused.

An assertion or context log makes the job easier to diagnose. Operators can see which tenant context was active, or detect that an expected data set was empty. That is more useful than a generic successful run.

The security posture remains fail closed. Missing context still reveals no rows. The change adds operational visibility without turning a safety mechanism into a bypass.

Drawbacks

The application has more responsibility. Every tenant-aware transaction must establish the right context, and tests must cover that setup. A forgotten step can still produce an empty result if the surrounding job has no expectation check.

Non-zero assertions also need care. They are appropriate only when the job truly expects records. Applying them to optional work would create false alarms. The contract for each job must say whether empty is normal, suspicious, or impossible.

A more structured database wrapper could reduce mistakes, but it would add design and migration work. I want to evaluate that approach rather than claim it is already part of the system.

Conclusion

The background job did not crash. Postgres did not reject its SQL. FORCE Row Level Security correctly hid tenant rows from a transaction that had no tenant context, and the worker mistook zero rows for zero work.

The fix was to set tenant context explicitly in every transaction. Jobs that expect data now need to assert a non-zero count or log the tenant context they used.

My main lesson is simple: security features designed to fail closed can fail silently at the application layer. Empty results deserve a meaning. A successful query is not proof that the job saw the data it was supposed to process.

Other

I want to make tenant context harder to omit by designing a transaction helper that requires the tenant identifier before it exposes tenant queries. I also want tests for three cases: the correct tenant sees its rows, another tenant cannot see them, and missing context cannot produce a misleading successful job.

I also want job dashboards to separate “completed with work,” “completed with no work,” and “completed with an unexpected empty result.” That would make the application contract visible without weakening RLS.
