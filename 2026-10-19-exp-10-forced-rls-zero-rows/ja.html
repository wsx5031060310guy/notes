Row Level Security はエラーなしで 0 行を返した

このブログでは、Row Level Security が処理対象を静かに隠し、バックグラウンドジョブが毎回成功扱いになった事例を説明します。

背景

私は Postgres の Row Level Security、一般に RLS と呼ばれる機能を使うマルチテナント SaaS に取り組みました。データベースには複数テナントの行が入り、ポリシーが各セッションから見える行を決めます。

このアプリケーションでは FORCE ROW LEVEL SECURITY も有効にしていました。通常、テーブル所有者は RLS を回避します。FORCE を使うと所有者もポリシーの対象になります。アプリケーション接続が誤って全テナントのデータを読む危険を減らせます。

ところが、あるバックグラウンドジョブはテナントコンテキストを設定せずに接続していました。クエリは失敗せず、0 行を返しました。ジョブはそれを「処理対象なし」と解釈し、正常終了しました。そして毎回同じことを繰り返しました。

これは見つけにくい失敗です。捕捉すべきデータベース例外も、権限拒否のメッセージもありません。セキュリティ機能は設計どおりに動作し、有効なテナント識別情報を持たないセッションに行を見せませんでした。結果の意味を取り違えたのはアプリケーション側です。

概要

RLS はクエリに暗黙のフィルターを追加します。ポリシーは行のテナント識別子と、現在のセッションに設定された値を比較できます。一致すれば行が見えます。コンテキストがなければ条件は一致しません。

この fail-closed の動作は重要です。セキュリティコンテキストがないときに全行を見せるべきではありません。しかし「安全であること」と「処理が正しいこと」は別の問題です。テナントデータを期待するジョブは、コンテキスト欠落を検知する必要があります。

  • スケジューラーがジョブを開始します。
  • ジョブがトランザクションを開きます。
  • 対象テナントのコンテキストを設定します。
  • そのコンテキストでクエリを実行します。
  • 予想外の 0 行を異常として扱います。

失敗と修正：コンテキスト欠落で可視行が 0 件になったため、クエリ前に各トランザクションで明示的に設定します。

デモ

1 テナント分のレコードを処理するワーカーを考えます。ワーカーはテナント識別子を受け取り、トランザクションを開き、保留中の行を選び、処理してコミットします。

問題の経路では一つの手順が抜けていました。ジョブは接続後すぐにクエリしました。FORCE RLS により、テーブル所有者の接続にもポリシーが適用されます。トランザクションにはテナントコンテキストがないため、ポリシーを満たす行はありませんでした。

SQL 自体は正常に実行されます。Postgres にとって空の結果は正当です。ワーカーには「そのテナントに保留中の処理がない」場合と同じに見えます。そのためエラーなしで終了しました。

0 行という結果は「処理がない」という意味にも、「このセッションから処理対象が見えない」という意味にもなります。

修正では、トランザクションごとにテナントコンテキストを明示的に設定しました。設定場所も重要です。コネクションプールはセッションを再利用するため、テナント値を曖昧なグローバル設定として扱うべきではありません。トランザクション内でコンテキストを設定し、クエリを実行してから終了します。

データがあるはずのジョブには、アプリケーション側のシグナルも必要です。実施した修正では、データを期待するジョブで件数が 0 ではないことを確認するか、実行時のテナントコンテキストをログに残します。空の結果を沈黙した成功ではなく、調査できる情報に変えます。

すべての 0 行を失敗にするわけではありません。処理対象が本当にないジョブもあります。アサーションは、ジョブの契約上データが存在する箇所に置きます。それ以外では、有効なコンテキストを記録すれば、空のキューと識別情報の欠落を区別できます。

考察

セキュリティフィルターは通常のエラーではありません

認可ポリシーは例外を投げる代わりにデータを見えなくすることがあります。別テナントの行を返すより安全ですが、エラー監視だけではジョブの健全性を証明できません。クエリは正しく高速に終わりながら、誤った理由で空になれます。

そのため、期待する結果をアプリケーション層で定義します。既知のテナントと既知のレコード群を処理するジョブなら、0 行は契約違反かもしれません。任意の処理を探すポーリングなら正常です。データベースは SQL だけからこの違いを判断できません。

コンテキストはトランザクションと一緒に扱います

テナントコンテキストは認可判断の一部です。依存するトランザクションの近くで設定すべきです。識別情報とクエリを一つの明確なスコープに保てます。

より良い設計では、コンテキスト設定前にテナント SQL を実行しにくくできます。たとえばワーカーにテナント識別子を必須で渡し、トランザクションのコールバック内だけでデータベース操作を公開できます。これは改善案であり、この事例ですでに実装した機能ではありません。

FORCE RLS は隠れた前提を表面化させます

FORCE がなければ、テーブル所有者で動くコードは RLS を回避して成功して見える場合があります。その成功がコンテキスト欠落を隠します。後で制限されたロールへ変更すると挙動が変わる可能性があります。

FORCE は所有者の偶発的な特権を取り除きます。この事例では境界が一貫しましたが、ワーカーが必要なコンテキストを渡していませんでした。ポリシーを弱めるのではなく、ワーカーのトランザクションを直すべきでした。

分離と正しい可視性の両方をテストします

RLS のテストは、テナント A がテナント B の行を読めないという重要な否定ケースに集中しがちです。しかし肯定ケースも必要です。正しいコンテキスト設定後、テナント A は自分の行を見られるべきです。

さらにコンテキスト欠落のケースも試したいです。行が公開されないことに加え、データを期待するジョブが通常成功として報告しないことを確認します。これで fail-closed の両面を表現できます。

利点

トランザクションごとの明示的なコンテキストは、テナント識別情報を認可対象のクエリに近づけます。テーブル所有者の特権に頼らず FORCE RLS と共存し、プールされた接続の再利用時の曖昧さも減らします。

アサーションやコンテキストログにより診断しやすくなります。どのテナントとして実行したか、期待したデータが空だったかを確認できます。単なる正常終了より有用です。

セキュリティは fail closed のままです。コンテキスト欠落時には行を返しません。安全機構を迂回せず、運用上の可視性を追加できます。

欠点

アプリケーションの責任は増えます。テナントを扱う各トランザクションで正しいコンテキストを設定し、テストする必要があります。期待値の確認がなければ、設定忘れはまだ空の結果になります。

0 件ではないことの確認にも注意が必要です。本当にレコードを期待する場合だけ適切です。任意の処理に適用すると誤警報になります。各ジョブで「空」が正常、疑わしい、不可能のどれかを定義する必要があります。

構造化されたデータベースラッパーはミスを減らせますが、設計と移行の作業が増えます。すでに導入済みとは言わず、今後評価したい方法です。

まとめ

バックグラウンドジョブはクラッシュせず、Postgres も SQL を拒否しませんでした。FORCE RLS はコンテキストのないトランザクションからテナント行を正しく隠し、ワーカーが 0 行を処理なしと誤解しました。

修正は、各トランザクションでテナントコンテキストを明示的に設定することです。データを期待するジョブでは、0 件ではないことを確認するか、使用したテナントコンテキストを記録します。

教訓は単純です。fail closed に設計されたセキュリティ機能も、アプリケーション層では静かに失敗できます。空の結果には意味を定義すべきです。クエリの成功だけでは、処理すべきデータが見えていた証拠になりません。

今後

テナント識別子を渡すまでテナントクエリを使えないトランザクションヘルパーを設計したいです。また、正しいテナントは自分の行を見られる、別テナントは見られない、コンテキスト欠落が誤った成功を生まない、という三つのテストを用意したいです。

ジョブの表示も「処理ありで完了」「処理なしで完了」「予想外の空で完了」に分けたいです。RLS を弱めずに、アプリケーションの契約を見えるようにできます。
