一份儲存到一半的試算表，悄悄讓我的監看清單空了五天

檔案可以仍然存在、名稱看起來也很熟悉，卻已經悄悄不再是有效資料。

前言

這篇文章要說明，一次中斷的試算表儲存，如何讓每日自動化工作連續五天都沒有追蹤任何帳號。檔案並未被刪除，工作也照常啟動，錯誤甚至確實寫進了紀錄。不過，其中一個函式把損壞的活頁簿轉成空白監看清單，後續流程因此無事可做。

這件事發生在一項每日執行的潛在客戶蒐集工作。程式會把新列附加到外接 exFAT 磁碟中的 .xlsx 檔案；另一個函式則讀取同一份活頁簿，建立要追蹤的帳號清單。這樣的設計讓試算表同時是輸出也是輸入。因此，一次不完整的寫入不只影響當下的儲存，也改變了之後每一次執行的行為。

這次經驗的重點不只適用於 Excel 檔案。任何結構化檔案都可能成為隱藏的相依項目。如果讀取端把損毀當成「沒有任何紀錄」，儲存失敗看起來就會像是合理的空白結果。

這項工作原本在做什麼

這套流程有兩條互相關聯的路徑。一條負責蒐集潛在客戶，並把資料附加到活頁簿；另一條讀取活頁簿，再產生監看清單。兩條路徑都仰賴同一份檔案能夠正常讀取。

失敗路徑：儲存中斷造成活頁簿損壞，而被捕捉的讀取錯誤最後變成空白監看清單。

這種安排很方便，因為活頁簿很容易直接查看，但也讓兩項操作彼此耦合。寫入與讀取不再是互相獨立的操作；如果寫入時損壞檔案，下一次讀取就無法建立清單。

.xlsx 活頁簿並不是一張扁平表格，而是包含 XML 檔案與相關中繼資料的 ZIP 壓縮檔。ZIP 壓縮檔會在接近檔案尾端的位置，以中央目錄描述其中的項目。如果尾端不完整，即使大部分工作表內容仍留在檔案裡，一般的活頁簿讀取器也可能無法再辨識這個壓縮檔。

一次中斷的儲存如何破壞後續執行

有一次儲存進行到一半時被中斷。活頁簿尾端存放 ZIP 中央目錄的位置只剩下零位元組。檔案仍在磁碟上，但對一般讀取器而言，它已不再是有效的壓縮檔。

之後每一次附加資料的嘗試，都在紀錄中留下 File is not a zip file。這則訊息沒有錯。真正危險的行為發生在監看清單函式裡：它捕捉例外後，回傳了一個空白清單。

回傳空白清單雖然避免了程式當掉，卻改變了這次失敗的意義。「我無法讀取來源」變成「來源裡沒有任何帳號」。接著，工作帶著一個正常的資料結構繼續執行。整整五天，它追蹤的帳號數都是零。

這是常見的邊界問題。例外描述的是操作失敗；空集合描述的是有效結果，兩者不能互換。呼叫端看到空白清單時，很合理地會解讀成「今天沒有工作要做」。除非錯誤被保留下來或清楚回報，否則呼叫端不可能知道讀取其實已經失敗。

紀錄裡雖然有活頁簿錯誤，流程卻沒有把空白輸出視為可疑狀況。這項工作因此可以繼續執行，卻沒有產生原本預期的效果。

復原

活頁簿雖然損壞，工作表的 XML 區段仍然完整。儲存格使用的是內嵌字串，因此剩餘內容可以直接從 XML 復原。我重建了每一列：其中一張工作表有 2,593 列，另一張有 1,450 列，也保留了原本相同的去重複鍵。重建後的活頁簿再次產生了 59 個帳號。

復原時必須理解這項差異。容器可能無法讀取，其中一部分內容卻仍然存在。第一個該問的問題不能只有「Excel 打得開嗎？」還要問「哪些壓縮檔項目與 XML 區段仍然存在？」在回答這個問題的過程中，復原操作也應避免覆寫損壞的原始檔案。

我也用 zip -FF 復原壓縮檔項目。它確實找回了這些項目，但程式會停下來等待互動式提問，直到收到 yes 才繼續。這項行為對自動化很重要：在終端機裡可用的指令，如果需要輸入內容，在無人值守的工作中可能會永遠等下去。

復原後的列數，以及重新出現的 59 個帳號，提供了具體的檢查依據。新的活頁簿能夠開啟，並不代表復原已經完成。它還必須保留原有列、去重複鍵，以及這項工作所依賴的下游清單。

修正方式

修正方式是不再直接覆寫唯一一份正常的檔案。現在，工作會先把內容存到同一個資料夾內的暫存檔，再用 os.replace 取代原始檔案。

實際採用的修正：寫入並驗證暫存活頁簿，再用 os.replace 取代目標檔案。

暫存檔必須放在同一個資料夾。這樣才能讓取代操作維持在同一個檔案系統上。寫入新內容的期間，舊活頁簿會留在原位；只有等暫存活頁簿完整寫入後，才會進行取代。

如果寫入暫存檔失敗，現有活頁簿不會被更動。程式可以刪除暫存檔，下一次執行仍有上一份有效資料可用。這做法無法消除所有儲存問題，但能避免應用程式直接在唯一一份檔案上原地改寫的危險時段。

我也新增了一項測試，模擬儲存到一半時發生失敗。測試會確認舊檔案沒有改變。它檢查的是我真正需要的特性，而不只驗證一切順利時是否能建立活頁簿。

討論

不要把損毀轉成空白

讀取器成功讀取一份沒有任何資料列的有效來源時，可以回傳空白清單；但解析失敗時，不應回傳相同的值。較好的介面應該把這兩種狀態分開。它可以拋出錯誤、回傳明確的失敗結果，或在下游動作開始前停止這項工作。

驗證實際效果，不要只確認程序有執行

排程程序準時啟動，只能算是薄弱的證據。真正有用的檢查，應確認預期輸出是否產生。在這個案例中，帳號數為零的監看清單雖然可能是有效資料，但當它與活頁簿讀取錯誤同時出現時，已經異常到值得檢查。

不要把復原工具放進一般寫入路徑

事件發生後，壓縮檔修復工具確實有用，但它不能取代安全寫入。復原工具可能需要互動操作，也可能改動損壞的內容，而且未必能保留複雜活頁簿內的每一項關聯。正常系統應在需要復原前，先保護上一份正常的檔案。

外部儲存裝置不會改變應用程式的契約

這份活頁簿存放在外接 exFAT 磁碟上。不論儲存位置在哪裡，應用程式仍需要清楚的契約：外界應該只能看見上一份完整的活頁簿，或下一份完整的活頁簿。原地儲存會暴露不完整狀態；用暫存檔取代，則能為應用程式提供較安全的邊界。

結論

這起事件始於一次中斷的儲存，後續程式又把讀取失敗轉成空白清單，於是影響持續了五天。檔案仍然存在，工作持續執行，流程在使用空白結果時也沒有當掉。這些訊號看起來很平靜，實際狀況卻不是如此。

工作表 XML 仍然完整，因此活頁簿可以復原。我重建了一張工作表的 2,593 列與另一張的 1,450 列，保留去重複鍵，也恢復了包含 59 個帳號的監看清單。長久的修正反而比復原簡單：先把暫存活頁簿寫到同一個資料夾，再用 os.replace 取代原始檔案。

對以檔案為基礎的自動化而言，「空白」應該表示來源已成功讀取，而且其中確實沒有任何內容。它絕不能悄悄拿來代替「我無法讀取來源」。

其他

我想更清楚地區分有效的空白活頁簿與失敗的活頁簿讀取。我也希望這項工作能在接近最終結果的地方回報來源讀取失敗，避免正常啟動的表象掩蓋未完成的工作。

後續還可以在取代前驗證暫存活頁簿，並有限度地保留上一份已知正常的備份。這些仍是規劃，並不是本文所述現行流程已具備的功能。
