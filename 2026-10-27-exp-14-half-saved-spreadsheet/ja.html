保存途中のスプレッドシートが5日間ひそかに監視リストを空にした

ファイルは存在し、見慣れた名前のままでも、気づかないうちに有効なデータではなくなることがあります。

はじめに

この記事では、スプレッドシートの保存が中断された結果、毎日の自動化ジョブが5日間にわたって一つのアカウントもフォローしなくなった経緯を説明します。ファイルは削除されていませんでした。ジョブも起動していました。エラーはログにさえ記録されていました。しかし、ある関数が破損したワークブックを空の監視リストに変換したため、その後のワークフローには処理すべき対象が残りませんでした。

これは、毎日実行する見込み客収集ジョブで起きました。ジョブは外付けの exFAT ディスクに保存した .xlsx ファイルへ行を追加していました。別の関数は同じワークブックを読み、フォロー対象のアカウント一覧を作っていました。この設計では、スプレッドシートが出力であると同時に入力でもありました。そのため、不完全な書き込みは実行中の保存だけでなく、それ以降のすべての実行動作にも影響しました。

重要な教訓は Excel ファイルだけに関するものではありません。どのような構造化ファイルも、隠れた依存関係になり得ます。読み取り側が破損を「レコードなし」として扱うと、ストレージ障害が正当な空の結果に見えてしまいます。

ジョブの処理内容

ワークフローには、相互に関係する二つの経路がありました。一方は見込み客を収集し、ワークブックへ追記します。もう一方はワークブックを読み、監視リストを生成します。どちらも同じファイルが読み取り可能であることに依存していました。

障害の流れ：保存の中断でワークブックが破損し、捕捉された読み取りエラーが空の監視リストになりました。

ワークブックは確認しやすかったため、この構成は便利でした。一方で、処理同士の結合も生まれました。書き込みと読み取りは、もはや独立した操作ではありません。書き込みによってファイルが破損すると、次の読み取りでは一覧を作れなくなります。

.xlsx ワークブックは、一つの平坦な表ではありません。XML ファイルと関連メタデータを収めた ZIP アーカイブです。ZIP アーカイブは、ファイルの末尾近くにあるセントラルディレクトリを使って各項目を記述します。その末尾が不完全な場合、ワークシートの内容が内部にかなり残っていても、通常のワークブック読み取り機能はアーカイブとして認識できなくなることがあります。

中断された一度の保存が後続実行を壊した経緯

ある保存処理が途中で中断されました。ZIP のセントラルディレクトリが置かれるワークブック末尾は、ゼロバイトのまま残されました。ファイルはディスク上に存在していましたが、通常の読み取り機能にとっては、もはや有効なアーカイブではありませんでした。

その後の追記処理は毎回 File is not a zip file とログに記録しました。このメッセージは正確でした。危険な動作は監視リスト関数の中で起きました。その関数は例外を捕捉し、空のリストを返していたのです。

空のリストを返すことでクラッシュは防げましたが、障害の意味が変わりました。「データ源を読めなかった」が「データ源にアカウントが存在しない」になったのです。その後、ジョブは通常のデータ構造を受け取ったまま処理を続けました。結果として5日間、フォローしたアカウントはゼロでした。

これは境界部分でよく起こる問題です。例外は運用上の失敗を示します。空のコレクションは正当な結果を示します。この二つは置き換えられません。呼び出し側が空のリストを「今日は作業がない」と解釈するのは合理的です。失敗を保持するか明確に報告しない限り、実際には読み取りが失敗したことを呼び出し側は知ることができません。

ログにはワークブックのエラーが残っていましたが、ワークフローは空の出力を疑わしいものとして扱いませんでした。ジョブは意図した結果を生まないまま実行できてしまいました。

復旧

ワークブックは破損していましたが、ワークシートの XML 部分は無傷でした。セルではインライン文字列が使われていたため、残った内容を XML から直接復旧できました。すべての行を再構築し、一方のシートで2,593行、もう一方で1,450行を復元しました。重複排除キーは以前と同じものを維持しました。再構築したワークブックからは、再び59アカウントが得られました。

復旧時には、この違いが重要です。コンテナを読み取れなくても、ペイロードの一部が残っている場合があります。最初に問うべきなのは「Excel で開けるか」だけではありません。「どのアーカイブ項目と XML 部分がまだ存在するか」も確認する必要があります。この問いに答える間は、破損した原本を上書きしないように復旧を進めるべきです。

アーカイブ項目の復旧には zip -FF も使いました。このコマンドで項目は復旧できましたが、yes を受け取るまで対話形式の質問を待ち続けました。この動作は自動化において重要です。端末では動くコマンドでも、入力を待つ場合、無人ジョブではいつまでも停止する可能性があります。

復元した行数と、再び得られた59アカウントという結果が、具体的な検証項目になりました。新しいワークブックが開けるようになっただけでは、復旧完了とはいえません。行、重複排除キー、そしてジョブが依存していた後続の一覧を維持する必要がありました。

修正

修正内容は、唯一の正常なコピーへ直接上書き保存するのをやめることでした。現在のジョブは同じフォルダー内の一時ファイルへ保存してから、os.replace で元のファイルを置き換えます。

実装した修正：一時ワークブックを書き込んで検証し、os.replace で対象を置き換えます。

一時ファイルは同じフォルダーに置く必要があります。同じ場所に置けば、置換を同一ファイルシステム内で実行できます。新しい内容を書き込んでいる間も、古いワークブックはそのまま残ります。一時ワークブックが完成して初めて置換を実行します。

一時ファイルへの書き込みに失敗しても、既存のワークブックは変更されません。一時ファイルを削除でき、次回の実行でも以前の有効なデータを利用できます。これですべてのストレージ問題が消えるわけではありませんが、アプリケーションが唯一のコピーをその場で書き換える危険な時間帯はなくなります。

保存途中の失敗を再現するテストも追加しました。このテストでは、古いファイルが変更されていないことを確認します。正常系でワークブックを作れるかだけでなく、必要な性質そのものに焦点を当てたテストです。

考察

破損を空の結果に変換しない

読み取り機能は、行のない有効なデータ源を正常に読み取った場合には、空のリストを返せます。しかし、解析に失敗したときに同じ値を返すべきではありません。より良いインターフェースでは、これらの状態を分けます。エラーを送出する、明示的な失敗結果を返す、あるいは後続処理を始める前にジョブを停止する方法があります。

処理だけでなく結果を検証する

スケジュールされた処理が予定どおり開始したことは、弱い証拠にすぎません。有用な確認では、期待した出力が生成されたかを問うべきです。この事例では、アカウント数ゼロの監視リストもデータ値としてはあり得ました。しかし、ワークブックの読み取りエラーと同時に発生したなら、調査が必要なほど異常な結果として扱うべきでした。

復旧ツールを通常の書き込み経路に入れない

アーカイブ修復は事故後に役立ちましたが、安全な書き込みの代わりにはなりません。復旧ツールは対話入力を求める場合があり、破損した内容を変更する可能性もあり、複雑なワークブック内の関係をすべて維持できるとは限りません。通常のシステムは、復旧が必要になる前に、最後の正常なコピーを保護すべきです。

外部ストレージでもアプリケーションの契約は変わらない

ワークブックは外付けの exFAT ディスクにありました。保存場所にかかわらず、アプリケーションには明確な契約が必要でした。つまり、以前の完全なワークブックか、次の完全なワークブックのどちらかが見える状態にすることです。その場での保存は不完全な状態を外部にさらしました。一時ファイルからの置換は、アプリケーションにより安全な境界を与えます。

まとめ

この事故は一度の保存中断から始まり、その後のコードが読み取り失敗を空のリストへ変換したため、5日間続きました。ファイルは存在し、ジョブは動き、空の結果が使われた箇所でもワークフローはクラッシュしませんでした。これらの兆候は、実際の状態よりも問題がないように見えました。

ワークシートの XML が無傷だったため、ワークブックは復旧できました。一方のシートの2,593行と、もう一方の1,450行を再構築し、重複排除キーを維持して、59アカウントの監視リストを復元しました。恒久的な修正は、復旧作業より単純でした。同じフォルダー内に一時ワークブックを書き込み、os.replace で元のファイルを置き換えます。

ファイルを利用する自動化において、「空」はデータ源の読み取りに成功し、中身が何もなかったことを意味するべきです。「データ源を読めなかった」を静かに言い換えた結果であってはいけません。

今後

有効だが空のワークブックと、ワークブックの読み取り失敗とを、さらに明確に区別したいと考えています。また、通常どおり起動したという事実が作業の欠落を隠さないよう、ジョブの最終結果に近い場所でデータ源の読み取り失敗を報告したいです。

さらに、一時ワークブックを置換前に検証し、最後に正常だったファイルのバックアップを一定数保持する改善も考えられます。これらは計画であり、ここで説明した現在のワークフローに実装済みの機能ではありません。
