一次被動式安全掃描，讓我的正式環境資料庫停擺

一場安靜的安全檢查，揭露了平常流量沒有碰到的容量計算錯誤。

前言

這篇文章要說明一次被動式弱點掃描如何讓正式環境資料庫停擺。掃描器沒有利用任何漏洞，也沒有送出極端流量。它只製造了足夠的平行請求，讓一個無法承受自動擴充的連線池設定浮上檯面。

這個應用程式運行在可以擴充成多個執行個體的 serverless container 平台。後方是一個小型的受管理 PostgreSQL 資料庫，大約有 25 個可用連線額度。

每個應用程式執行個體都會建立自己的資料庫連線池。只看單一連線池時，數值似乎合理。真正的問題要把連線池大小乘上執行個體上限才會出現。乘積可能大於資料庫能接受的連線數。

觸發事件是 OWASP ZAP baseline scan。它產生足以讓平台向外擴充的平行工作。更多執行個體代表更多連線池。這些連線池耗盡資料庫連線，網站因此中斷。

概覽

最重要的關係很簡單：

每個執行個體的連線池大小 × 同時運行的執行個體數，必須小於資料庫連線預算

事故之後看起來很明顯，事前卻很容易忽略。serverless container 改變了容量的計算單位。寫在應用程式設定裡的連線池數值，不是整個系統的總量，而是每一個執行個體各自擁有的上限。

啟動一個執行個體時，資料庫看到一個連線池。啟動多個執行個體時，資料庫會看到數個互相獨立的連線池。資料庫不會因為這些連線池屬於同一個應用程式，就自動替它們協調總量。

大約 25 個可用額度還需要保留實務上的操作空間。應用程式不能把所有理論額度都當成一般請求可用。容量規劃應該從資料庫往回推，而不是只從單一容器向外看。

故障如何發生

故障路徑：平行掃描請求促使平台增加執行個體，連線池總量隨之放大，直到資料庫額度耗盡。

步驟一：被動式掃描產生平行請求

OWASP ZAP baseline scan 的行為就像規模不大的真實流量。它不必直接攻擊資料庫，只要沿著正常路徑請求 Web 應用程式即可。

步驟二：平台向外擴充應用程式

serverless container 平台按照設計運作。為了處理同時到來的請求，它啟動更多執行個體。從平台本身的角度看，這是健康而正常的行為。

步驟三：每個執行個體都建立連線池

每個新執行個體都使用相同的連線池設定。這個上限只屬於當下的程序，並不會與其他執行個體的連線池協調。

步驟四：合計需求超過資料庫限制

資料庫大約有 25 個可用連線額度。當所有連線池合計競爭的數量超過預算，請求就無法取得資料庫連線，網站最後變得無法使用。

這段過程的重點是，每個元件單獨看都在正常運作。掃描器發出一般 Web 請求，平台增加容量，應用程式開啟設定好的連線池，PostgreSQL 執行自己的連線限制。事故來自這些局部正確行為彼此組合後的結果。

討論

連線池不是免費容量

連線池可以改善連線重複使用，但不會創造資料庫容量。當應用程式有多個執行個體時，過大的連線池甚至會宣告超過資料庫所能服務的潛在需求。

我現在把連線池視為一項預算請求。每個執行個體最多要求固定數量的資料庫連線，自動擴充會重複這項要求。資料庫必須能承受總和，還要保留操作與復原空間。

自動擴充把乘號帶進容量規劃

在單一長時間運行的伺服器上，很自然會拿一個連線池與一個資料庫比較。在可擴充平台上，更安全的問題是：數個執行個體同時存在時，合計需求是多少？

這不只是一般流量問題。部署、cold start、掃描或短暫尖峰都可能增加執行個體數量。如果只按照平常的數量規劃，不尋常的瞬間就可能成為事故。

掃描器意外成了一場容量測試

這次掃描沒有攻擊任何東西。它揭露的是規模不大的真實流量也可能碰到的限制。只封鎖掃描器會隱藏設定錯誤，卻不會修正容量模型。

安全檢查可能測到安全控制以外的系統特性，例如佇列、逾時、並行與資源預算。這很有價值，但也代表正式環境掃描需要配合維運風險來安排。

修正方式

我修改了兩個與故障直接相關的地方。

第一，我依照資料庫限制與平台可能的執行個體數，重新計算連線池。我把每個執行個體的連線池縮小為 6。採用的規則是：每個執行個體的連線池大小乘上執行個體上限，必須放得進資料庫連線限制。

第二，我加入 10 秒連線逾時。若等待沒有上限，請求會一直等候一個不會及時出現的連線。逾時讓請求較快失敗，而不是無止境卡住。

兩項修改處理不同層面的問題。較小的連線池降低合計需求上限；逾時則限制仍然無法取得連線時的等待行為。

我不再把一次成功的掃描或正常 HTTP 狀態碼當成充分證據。這場事故的核心是資源計算。驗證時需要檢查資料庫連線預算與應用程式執行個體數，而不只是某一個請求是否完成。

優點與缺點

優點

  • 容量規則變得明確，也能接受檢視。
  • 較小的單一連線池可避免自動擴充把需求放大到資料庫限制之外。
  • 連線逾時可限制資料庫飽和時的等待時間。
  • 執行個體上限或資料庫方案改變時，可以使用同一套計算重新檢查。

缺點

  • 較小的連線池可能限制單一執行個體內的並行量。
  • 較短的逾時可能把緩慢復原轉為明確的請求失敗。
  • 正確數值取決於資料庫預算與平台擴充設定。
  • 任何一側改變後，原本的計算都可能過時。

這些缺點不代表修正無效。它們說明連線設定應該被視為整體系統的容量控制，而不是獨立複製的應用程式預設值。

結論

正式環境中斷的原因是一個乘法問題。對單一執行個體看似安全的連線池，在平台建立多個執行個體後就不再安全。被動式掃描剛好提供足以揭露落差的平行工作。

長期教訓是把自動擴充納入容量計算。先確認資料庫可用的連線預算，保留實務上的餘裕，再把剩餘預算分配給可能同時存在的最大執行個體數量。連線等待也要有上限，讓飽和清楚失敗，而不是持續卡住。

掃描器不是敵人。它的行為像規模不大的真實流量，在更大的使用事件發生以前，先指出應用程式與資料庫之間不相容的假設。

其他

我想讓這項計算更容易重新檢查。建議的設計是把資料庫連線預算，與應用程式連線池及執行個體上限記錄在一起。任何一側改變時，審查者就更容易看見影響。

我也想加入連線使用量、執行個體數、連線等待時間與逾時的監控。這些都是計畫，不是事故當時已存在的功能。目標是在使用者看到中斷之前，先看見乘法正在發生。

另一個有用的下一步，是在安全環境做受控制的負載測試。測試應逐步提高並行量，確認應用程式維持在規劃的資料庫預算內。它應該量測真正失敗的資源，而不只是最後的 HTTP 結果。
