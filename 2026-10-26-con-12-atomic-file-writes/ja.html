アトミックなファイル書き込み：一時ファイル、fsync、rename

この記事では、一時ファイル、fsync、rename を使い、更新途中の壊れたファイルを公開しない方法を説明します。

はじめに

ファイルは最も単純な永続化手段に見えます。開いて、新しい内容を書き、閉じるだけです。すべてが正常に終わる限り、この方法でも動きます。しかし難しいのは中断時です。プロセスが強制終了することがあります。マシンが停止することもあります。ストレージがエラーを返す場合もあります。対象ファイルを直接上書きすると、新しい内容の一部だけが残る可能性があります。

この問題は、設定、ローカル状態、レポート、インデックス、小規模なデータ保存で重要です。書き込み側の失敗は一度でも、その後のすべての読み取りが壊れた結果を受け取ります。パーサーは構文や形式のエラーを報告しますが、原因となった中断はすでに過去のものです。そのため、エラーと書き込み処理を結び付けにくくなります。

一般的な対策は明快です。別の名前で完全な置換ファイルを準備し、バッファをフラッシュし、OS に同期を要求してから、対象名へ rename します。Python では置換に os.replace を使えます。それぞれの手順には別の役割があり、省略可能な飾りではありません。

概要

アトミックな更新では、ファイルの作成と公開を分けます。新しい内容を構築している間、読み取り側には古い対象ファイルが見え続けます。一時ファイルが完成した後にだけ、対象名を置き換えて公開します。

置換方式では、準備が終わるまで古いファイルを読み取り可能な状態に保ちます。

手順は次のとおりです。

  1. 対象ファイルと同じディレクトリに一時ファイルを作ります。
  2. 新しい内容をすべて一時ファイルへ書きます。
  3. 言語側のバッファを flush し、ファイル記述子に fsync を実行します。
  4. 一時ファイルを閉じます。
  5. os.replace で一時ファイルを対象ファイルへ置き換えます。
  6. POSIX 環境でより強いクラッシュ耐性が必要なら、rename 後に親ディレクトリも同期します。

アトミック性と耐久性は関係しますが、同じものではありません。アトミック性は、読み取り側が古い版か新しい版のどちらかを見て、公開途中の混在状態を見ないことです。耐久性は、完了した更新がクラッシュや電源断を越えて残るかという問題です。rename は公開境界を作り、同期処理はストレージ層への永続化を扱います。正確な保証は OS とファイルシステムにも依存します。

直接上書きが危険な理由

プログラムが対象ファイルを切り詰めて開く場合を考えます。最初の新しいバイトを書く前に、古い内容が消えることがあります。新しいデータの一部だけを書いた時点でプロセスが止まると、ファイルは存在していても不完全です。読み取り側は、その短い内容が意図した結果なのか判断できません。

切り詰めずに書くことも一般的な解決にはなりません。新しい内容が古い内容より短いと、末尾に古いバイトが残ります。構造化ファイルなら、正しい新しい先頭部分の後に古いデータが続く可能性があります。その結果、問題が別の場所の破損に見えることがあります。

ファイルを閉じることと、データを安定したストレージへ強制することも同じではありません。flush 前にはバッファード I/O がデータを保持します。アプリケーション側のバッファを flush しても、カーネルが書き込みをキャッシュしている場合があります。Python は os.fsync を、ファイル記述子に関連するデータをディスクへ強制的に書く機能として説明しています。そのため、ファイルオブジェクトを先に flush し、その記述子へ os.fsync を使います。

一時ファイルは汎用の一時ディレクトリではなく、対象と同じディレクトリに置くべきです。別のディレクトリは、別のファイルシステムにマウントされている可能性があります。POSIX の rename はファイルシステムをまたぐ同一操作の置換を保証せず、失敗することがあります。同じ場所に置けば、権限や後始末についても考えやすくなります。

デモ

Python の実装は小さくできます。重要なのは大きな抽象化ではなく、処理の順序です。

対象ディレクトリに名前付き一時ファイルを開きます。書き込みと flush を行い、開いた記述子に os.fsync を実行します。閉じた後、os.replace で対象を置き換えます。失敗時には、残っている一時ファイルだけを削除します。

私は try と finally を使って実装します。一時パスは後始末コードから参照できる必要があります。すべての書き込みと同期に成功した後だけ、置換を実行します。os.replace が成功した後に、後始末処理が対象ファイルを誤って消さない設計も必要です。

メタデータは明示的に扱います。古い対象に必要な権限や所有者が設定されていても、置換ファイルが期待どおりに継承するとは限りません。公開前に一時ファイルへ必要なモードを設定するか、プログラムの方針に従ってメタデータを保存します。暗黙の前提にしないことが大切です。

シリアライズ自体も失敗します。公開前に完全なバイト列を生成し、検証する方が安全です。JSON なら先にシリアライズし、必要なら置換前に再度 parse できます。アーカイブなら、一時ファイルを開き直して構造を確認できます。検証はストレージの耐久性を証明しませんが、プログラムが不正だと分かっている出力を公開することは防げます。

考察

rename が保証すること

POSIX 仕様では、置換先が既存の通常ファイルを指す場合、rename の処理中も置換先の名前は見え続け、以前のファイルか新しいファイルのどちらかを参照します。これが読み取り側にとって中心的な性質です。対象名が一時的に消える瞬間を避けるための調整が不要になります。

ただし、すべてのストレージが同じ動作をするという意味ではありません。ネットワークファイルシステム、特殊なマウント、非 POSIX 環境では、失敗時の動作が異なることがあります。Python の os.replace は既存の置換先を置き換えるための機能ですが、元と先が別のファイルシステムなら失敗する可能性があります。厳密な保証が必要なアプリケーションは、実際に配備するファイルシステムで試すべきです。

fsync が加えるもの

Python のファイルオブジェクトを flush すると、バッファ内のデータが OS 側へ進みます。os.fsync は、そのファイルのデータをディスクへ強制するよう OS に要求します。POSIX でクラッシュ耐性を重視する設計では、rename 後に親ディレクトリを開いて同期し、ディレクトリエントリの変更を永続化する実装もあります。この追加手順は耐久性のためであり、rename 自体をアトミックにする手順ではありません。

失敗後の後始末

書き込み、flush、置換のどれかが失敗した場合、古い対象を正しい版として残します。コードはハンドルを閉じ、放棄された一時ファイルだけを削除します。後始末のエラーで元の例外を隠してはいけません。一意な一時名を使うと、複数の writer が同じ準備パスを共有する事故も避けられます。

同時に複数の writer が動くなら、別の方針が必要です。アトミックな置換は公開途中の破損を防ぎますが、どの writer を勝者にするかは決めません。ロックや version check がなければ、最後に成功した置換が残ります。更新の消失が問題になる場合は、アトミック書き込みに加えて調整機構が必要です。

テスト方法

有効なテストは、既知の古い対象ファイルから始めます。新しい内容の一部だけを一時ファイルへ書いた後に、意図的な失敗を発生させます。その後、元の対象が変更されず、読み取り可能であることを確認します。放棄された一時ファイルが削除されたことも確認します。

別のテストでは置換呼び出しを失敗させます。この場合も対象には古い内容が残るべきです。成功ケースでは、完全な新しい内容が見えることを確認します。これらは読み取り側に見える契約をテストします。突然の電源断にはより強い環境が必要ですが、決定的な failure injection でも順序や後始末のミスを検出できます。

利点と欠点

利点

  • 読み取り側は完全な古い版か完全な新しい版を見ます。
  • 書き込み失敗で現在の対象を壊しにくくなります。
  • 小さなパターンで、多くのローカル形式に使えます。
  • failure injection により、明確でテスト可能な契約を作れます。

欠点

  • 更新中は両方の版を置く容量が必要です。
  • 権限などのメタデータを明示的に扱う必要があります。
  • 置換だけでは writer 間の更新消失を防げません。
  • 耐久性の詳細はプラットフォームとファイルシステムで異なります。
  • 複数ファイルや複数レコードにまたがる transaction が必要なら、データベースの代わりにはなりません。

まとめ

直接上書きは、対象が不完全な状態を外部に見せます。一時ファイル方式は考え方を変えます。非公開で構築し、検証し、同期して、一度だけ公開します。rename が commit point です。読み取り側は安定した名前を使い、途中まで作られた置換結果を見ずに済みます。

重要なローカル状態では、正常と分かっている版を、置換の準備が終わる前に破壊しないことが設計原則になります。また、アトミックな可視性とクラッシュ後の耐久性を分けて考える必要があります。前者は同じファイルシステム内の置換で得られます。後者には慎重な同期と、実際の環境でのテストが必要です。

今後

書き込み後、flush 後、replace 前に障害を注入できる、小さく再利用可能な Python helper を試したいです。アプリケーションが実際に使うファイルシステム上でのテストも行いたいです。より良い設計では、メタデータ方針、同時 writer の方針、耐久性レベルを明示的な選択肢にし、一つの関数名の裏へ隠さないようにします。
