原子檔案寫入：暫存檔、fsync 與 rename

在這篇文章中，我會說明如何用暫存檔、fsync 與 rename，避免把只寫到一半的檔案公開給讀取端。

前言

檔案看起來是最簡單的持久化方式。我開啟檔案、寫入新內容，再把它關閉。只要每次操作都正常完成，這樣似乎沒有問題。真正困難的是中斷情況。程序可能被終止，機器可能停止，儲存裝置也可能回報錯誤。若程式直接覆寫目標檔案，最後可能只留下部分新資料。

這個問題會影響設定檔、本機狀態、報表、索引與小型資料儲存。寫入端可能只失敗一次，但之後每個讀取端都會看到損壞的結果。解析器接著回報看似無關的語法或格式錯誤。原始中斷早已結束，因此很難把後來的錯誤與那次寫入連在一起。

常見的做法很直接：先用暫存名稱準備完整的替代檔案，flush 緩衝區，要求作業系統同步資料，最後再 rename 到目標路徑。在 Python 中，os.replace 可以表達替換動作。每個步驟都有不同用途，不是可有可無的儀式。

概觀

原子檔案更新把「建立」與「公開」分開。建立新內容時，讀取端仍會看到舊的目標檔案。只有暫存檔完成後，寫入端才用替換目標名稱的方式發布新版本。

替換流程會保留可讀的舊檔案，直到新檔案準備完成。

流程如下：

  1. 在目標檔案的同一個資料夾建立暫存檔。
  2. 把完整的新內容寫進暫存檔。
  3. 先 flush 語言層的緩衝區，再對檔案描述符呼叫 fsync。
  4. 關閉暫存檔。
  5. 使用 os.replace，以暫存檔替換目標檔案。
  6. 若 POSIX 系統需要更強的當機耐久性，rename 後再同步所在資料夾。

原子性與耐久性彼此相關，但並不相同。原子性代表讀取端應看到舊名稱或新名稱，而不是發布到一半的混合結果。耐久性則關心已完成的更新能否撐過當機或斷電。rename 提供發布邊界，同步則處理資料經過儲存層後能否保留。精確保證仍取決於作業系統與檔案系統。

直接覆寫為何脆弱

假設程式用截斷模式開啟目標檔案。第一個新位元組寫入前，舊內容就可能已消失。如果程序只寫入部分資料便停止，目標檔案雖然存在，內容卻不完整。讀取端無法知道較短的內容是不是刻意產生的結果。

不截斷也不是通用解法。新內容可能比舊內容短，舊資料的尾端就會殘留。結構化檔案可能出現正確的新前段，後面卻接著舊資料。這種錯誤最後可能看起來像程式其他位置造成的損壞。

關閉檔案也不等於強制把資料寫到穩定儲存裝置。flush 之前，buffered I/O 可能仍持有資料。即使應用程式已 flush 自己的緩衝區，核心仍可能快取寫入。Python 文件把 os.fsync 說明為強制將檔案描述符的資料寫入磁碟。因此，謹慎的順序會先 flush 檔案物件，再把它的描述符交給 os.fsync。

暫存檔應放在相同資料夾，而不是通用的暫存資料夾。通用暫存位置可能掛載在另一個檔案系統。POSIX rename 無法跨檔案系統提供同樣的單一步驟替換，操作也可能直接失敗。把兩個路徑放在一起，也比較容易推理權限與清理行為。

示範

Python 實作可以很小。重點是操作順序，不是大型抽象層。

在目標資料夾開啟具名暫存檔，寫入並 flush，對開啟中的描述符呼叫 os.fsync，接著關閉檔案。用 os.replace 把暫存路徑替換到目標路徑。若流程失敗，只刪除仍存在的暫存檔。

我會用 try 與 finally 實作。清理程式必須能取得暫存路徑。只有每個寫入與同步步驟都成功後，才執行替換。一旦 os.replace 成功，清理邏輯不能誤刪新的目標檔案。

中繼資料也需要明確處理。舊目標可能有必要的權限或擁有者，但替代檔案不一定照應用程式預期繼承。寫入端應在公開前替暫存檔設定預期模式，或依程式政策保存中繼資料。這項行為不應只靠假設。

序列化本身也可能失敗。先產生並驗證完整位元組，再進行發布會更安全。JSON 可以先序列化，並在替換前視需要重新解析。產生壓縮檔時，可以重新開啟暫存檔檢查結構。驗證無法證明儲存耐久性，但可以避免發布程式已知無效的輸出。

討論

rename 保證什麼

POSIX 規格指出，當目的地已經是一般檔案時，rename 過程中目的地名稱會持續可見，並且會指向舊檔案或替代檔案。這是讀取端最需要的性質。讀取端不必為了「目標名稱短暫消失」而額外協調。

這不表示所有儲存系統都有完全相同的行為。網路檔案系統、特殊掛載點與非 POSIX 平台，可能有不同的失敗模式。Python 的 os.replace 用於替換既有目的地，但來源與目的地位於不同檔案系統時可能失敗。需要嚴格保證的應用程式，應在實際部署的檔案系統上測試。

fsync 加入什麼

flush Python 檔案物件，會把緩衝資料往作業系統移動。呼叫 os.fsync 則要求作業系統強制將檔案資料寫到磁碟。POSIX 上重視當機耐久性的實作，通常也會在 rename 後開啟並同步父資料夾，讓目錄項目的更新持久化。這個額外步驟處理的是耐久性，不是讓 rename 本身變成原子操作。

失敗後的清理

如果寫入、flush 或替換失敗，舊目標應繼續當作正式版本。程式需要關閉 handle，並且只刪除被放棄的暫存檔。清理錯誤不應蓋掉原始例外。唯一的暫存名稱也能避免兩個 writer 誤用同一個 staging 路徑。

同時存在多個 writer 時，需要另外定義政策。原子替換能防止發布破損檔案，卻不會決定哪個 writer 應該勝出。沒有鎖定或版本檢查時，最後成功替換者會留下。如果不能接受更新遺失，設計除了原子檔案寫入外，還需要協調機制。

如何測試

實用測試會先建立已知的舊目標。把部分新內容寫到暫存檔後，刻意注入失敗。接著驗證原始目標沒有變更，而且仍可讀取。測試也要確認被放棄的暫存檔已移除。

另一個測試可以讓替換呼叫失敗。目標同樣應保留舊內容。成功案例則應確認完整的新內容已出現。這些測試聚焦於讀取端能觀察到的契約。模擬突然斷電需要更強的環境，但可重現的 failure injection 仍能找出順序與清理錯誤。

優點與缺點

優點

  • 讀取端會看到完整舊檔案或完整新檔案。
  • 寫入失敗通常不會破壞目前的目標。
  • 模式簡單，可用於許多本機檔案格式。
  • 透過 failure injection，可以建立清楚而可測試的契約。

缺點

  • 更新期間需要同時容納兩個版本的空間。
  • 權限與其他中繼資料需要明確處理。
  • 只有原子替換，仍無法避免多個 writer 互相覆蓋更新。
  • 耐久性細節會隨平台與檔案系統而異。
  • 若 transaction 涵蓋多個檔案或紀錄，這個模式不能取代資料庫。

結論

直接覆寫會在目標尚未完成時就暴露它。暫存檔模式改變了做法：私下建立、驗證、同步，最後一次公開。rename 是 commit point。讀取端持續使用穩定名稱，也不會看到只完成一部分的替代內容。

對重要的本機狀態，我會把這個模式當作設計原則：替代版本準備好之前，不要破壞已知良好的版本。我也會區分原子可見性與當機耐久性。前者來自相同檔案系統內的替換；後者則需要謹慎同步與平台實測。

其他

我想試做一個可重複使用的小型 Python helper，並在寫入後、flush 後與 replace 前提供可注入的失敗點。我也想在應用程式實際使用的檔案系統上執行測試。更好的設計會把中繼資料政策、多 writer 政策與耐久性等級變成明確選項，而不是全部藏在一個函式名稱後面。
