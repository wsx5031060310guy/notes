HTTP 201, No Errors, and My New Code Never Ran

A successful response proved that an endpoint answered, but it did not prove that my latest server-side code produced the intended effect.

Background

I was working on a Next.js route handler and server action. I changed server-side code to add a side effect. After the edit, I ran a verification script against the endpoint. The response was HTTP 201. No error appeared.

The check looked green, but the new side effect had not happened. The development server was still serving the previous server bundle. My request succeeded against old behavior.

This was harder to notice than stale CSS. A stale visual change is often obvious when I look at the page. A stale server bundle can return a valid status and a familiar response. If my verification asks only whether the request succeeded, the answer can be yes even though the code I meant to test never ran.

The problem was not that HTTP 201 was false. The endpoint really did create the response represented by that status. The problem was that I treated transport success as evidence for a separate business effect.

Overview

There were three different facts in this incident. First, the verification script reached a running server. Second, that server accepted the request and returned HTTP 201. Third, the new side effect did not execute because the process was serving an older bundle.

Only the first two facts were covered by the original check. The third fact was the requirement that mattered.

The actual failure: the request succeeded against the previous server bundle, so the new side effect never ran.

The fix had two parts. I restarted the development server after changing server-side code and before verifying it. Then I verified the side effect itself. Depending on the change, that evidence could be the expected row, message, or file. I did not use the status code as a substitute for that evidence.

Demo

The misleading verification

The original flow was simple. I edited the handler. I called the endpoint with a script. The script received HTTP 201 and reported success. This flow checked availability and the response contract, but it did not identify which server bundle handled the request.

A status code belongs to the request-response boundary. It says what the server chose to report for that request. It does not say that every downstream effect occurred, and it does not prove that the running process contains the latest source edit.

The missing observation

The new code was supposed to produce a side effect. That effect was the observable result of the change. When it was absent, the status code should not have been allowed to close the test.

This distinction is useful in many systems. An API can accept work before a background step finishes. A queue producer can succeed while a consumer later fails. A database write can succeed while a notification does not. In my case, the simpler issue was a stale server bundle, but the testing principle is the same: observe the requirement at the boundary where it becomes real.

The fix

I restarted the development server after the server-side edit. That ensured the next request was handled by a process built from the code I intended to test. I then ran the request again and inspected the side effect directly.

If the intended result is a row, I should read that row. If it is a message, I should verify the message at its destination. If it is a file, I should inspect the file. The exact evidence changes with the feature, but the rule does not: test the effect, not only the acknowledgement.

Discussion

Green checks can answer the wrong question

A verification script can be completely correct and still be insufficient. Mine correctly established that an endpoint returned HTTP 201. It failed only when I gave that narrow result a broader meaning.

I now separate questions that are easy to blur together:

  1. Did the request reach a server?
  2. Did the server return the expected response?
  3. Was the running server using the code I meant to test?
  4. Did the intended state change or side effect actually occur?

A single status assertion usually answers only the second question.

Server-side staleness is deceptive

Front-end staleness often leaves visual evidence. Server-side staleness may preserve a valid protocol response. The older handler may still know how to answer the same route. There is no syntax error, crash, or failed request to attract attention.

That makes the failure look like a problem in the new logic, an external service, or the verification script. Before investigating those paths, it is worth confirming that the running development process actually loaded the new server-side code.

Verification should follow the effect

The strongest check is usually close to the claim. If I claim that a row was created, I verify the row. If I claim that a message was delivered, I verify the destination. If I claim that a file was written, I verify the file. HTTP success remains useful, but it is an earlier checkpoint, not the final proof.

This also prevents a different mistake: reporting success when a handler acknowledges work before the work is complete. Direct evidence narrows the gap between what a check says and what a user needs.

Benefits and Drawbacks

Benefits of effect-level checks

  • They verify the requirement rather than only the transport.
  • They expose stale code even when the endpoint still returns success.
  • They produce clearer evidence for debugging.
  • They reduce false-green reports from narrow scripts.

Drawbacks

  • They require access to the destination where the effect appears.
  • They can need cleanup when a test creates rows, messages, or files.
  • They are slower than checking one status code.
  • Each type of effect needs its own observation method.

The answer is not to remove response assertions. It is to layer them. Check the response, then check the state change that justifies the feature claim.

Conclusion

My verification script received HTTP 201 with no errors, but my latest server-side code had not run. The Next.js development server was still serving the previous server bundle, so the request succeeded against old behavior.

I fixed the verification flow by restarting the development server after changing server-side code. I also checked the side effect itself instead of treating the status code as proof.

The main lesson is simple: a successful response proves that something answered successfully. It does not prove which code answered, and it does not prove that the effect I care about happened.

Other

I want to make this distinction explicit in future verification scripts. A better script would label response checks and effect checks separately, so a green transport result cannot be mistaken for completed behavior.

I also want to document which server-side changes require a development-server restart in each project. That is a plan, not a feature of the setup described here.

For important side effects, a better design would make the resulting evidence easy to query. The verification step should be small, specific, and close to the user's outcome.
