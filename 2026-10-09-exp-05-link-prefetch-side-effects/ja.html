next/link が全訪問者のダウンロードボタンを押していた

この記事では、何の問題もなさそうに見えた Next.js のエクスポートリンクが、訪問者ごとに顧客データの CSV を生成していた事例を説明します。

本記事は、私自身のプロジェクトメモをもとに AI の支援を受けて下書きし、公開前に私が確認しています。

はじめに

管理画面に CSV のエクスポートリンクがありました。この画面では、Next.js Link をベースにした共通リンクコンポーネントを使っていました。遷移先は通常の URL に見えたため、アプリケーションの他の場所と同じコンポーネントを使うことは自然に思えました。

しかし、遷移先は通常のページではありませんでした。GET で呼ばれる API endpoint です。リクエストを受けるたびにレポートの閲覧を記録し、顧客データを含む CSV を生成していました。つまり、利用者が結果をダウンロードしたり開いたりしなくても、URL を取得するだけで意味のある処理が実行されました。

本番環境では、管理画面を開くだけで endpoint がバックグラウンドから呼ばれました。エクスポートリンクを誰かが押す必要はありません。その結果、レポートの利用指標は想定のおよそ三倍になり、クリックされていないのに機密性のある CSV ファイルが生成されました。

この問題はローカル環境では発生しませんでした。Next.js は開発モードでは prefetch しませんが、本番環境ではリンクが viewport に入ると prefetch する場合があります。ローカルテストはクリック後の経路だけを確認しており、障害を起こしたバックグラウンドリクエストを再現していませんでした。

概要

Next.js Link は、画面遷移を速く感じさせるための仕組みです。自動 prefetch の対象となる route では、利用者がクリックする前に route data を読み込めます。遷移先がページであり、読み取りが安全であれば便利な機能です。

ブラウザーは URL の業務上の意味を理解しません。Prefetcher は、まもなく必要になりそうな URL を見つけてリクエストを送ります。Crawler、link preview service、security scanner、ブラウザー機能も似たリクエストを送ることがあります。どれも、人がその操作を実行しようとしたことを保証しません。

HTTP で GET が safe method とされるのは、この違いがあるためです。Safe とは、サーバーが一切処理できないという意味ではありません。ログや cache は通常の処理です。重要なのは、client が状態変更を要求していないことです。機密 export の生成とレポート閲覧の計上を GET に結び付けると、基盤が投機的に呼んでもよいリクエストに業務上の副作用が発生します。

実際の障害：本番環境の prefetch がエクスポートリンクを取得し、クリックなしで閲覧を記録して機密 CSV を生成しました。

デモ

複雑な再現環境がなくても失敗の流れは理解できます。まず、CSV export を行う /api/ 配下の URL を Next.js Link の遷移先として管理画面に表示します。次に、本番用に build してアプリケーションを実行します。リンクが prefetch の対象になると、framework はクリック前に URL をリクエストする場合があります。

この endpoint では、一回のリクエストが二つの目に見える結果を生みました。一つは利用指標に使うレポート閲覧の記録、もう一つは顧客データ CSV の生成です。Response が訪問者に表示されなくても、サーバー側では処理がすでに完了していました。

エクスポート機能はクリック時にも正常に動いたため、症状は分かりにくいものでした。壊れたボタンも明らかな client error もありません。代わりに、バックグラウンド通信が実際の利用に見えました。およそ三倍に増えた指標からは、当初、顧客が急に export を多用し始めたように見えました。

重要な手掛かりは、本番環境での network の確認です。ページが待機中で、リンクがクリックされる前にリクエストが現れます。Endpoint の log は意図的な export ではなく、ページ表示と対応していました。開発モードではこのリクエストがないため、development server だけで確認すると安全だと誤認します。

考察

今回実施した修正

共通リンクコンポーネントを変更し、/api/ URL では Next.js Link ではなく通常の <a> 要素を出力するようにしました。通常のページ route は引き続き Next.js Link を使います。今回実施した修正はこれだけです。これにより、この共通コンポーネントから API link が navigation prefetch の対象として渡されなくなりました。

呼び出し側が download ごとに特別な prop を覚える必要がないため、この修正は共通コンポーネントに置くのが適切です。このアプリケーションでは path 自体が境界を示します。ルールを一か所にまとめることで、review もしやすくなります。

提案する設計：API の遷移先には通常の anchor を使い、Next.js Link はページ遷移に限定します。Endpoint の再設計は今後の作業です。

より根本的な問題

コンポーネントの変更で今回の prefetch 経路は防げますが、endpoint の設計にはリスクが残ります。GET URL は prefetcher、crawler、link preview、retry、scanner、または新しい tab で開いた人から呼ばれる可能性があります。副作用は、そのたびに繰り返され得ます。

より強い対策として、export の準備と作成済み結果の download を分離する計画が考えられます。明示的な non-GET request で、認可と利用者の意図を確認してから export を作成します。その後、安全な読み取りで準備済みファイルを取得します。この再設計は提案であり、今回完了した作業ではありません。

Product analytics と transport event を分けることも提案したいです。Request を受けた事実だけでは、人がその名前の操作をした証明になりません。意図が確定した位置で export を記録し、ファイルの生成と配信は別の operational log に残すべきです。

さらに、本番モードのテストを追加する計画もあります。管理画面を開き、クリックせずに待って export が作成されないことを確認します。その後リンクを一度クリックし、意図した結果が一件だけ生成されることを確認します。このテストも提案であり、実施済みの修正には含まれません。

利点と欠点

利点

  • 共通コンポーネントの小さな修正で、それを使うすべての /api/ link を保護できます。
  • ページ遷移では Next.js Link の性能上の利点を維持できます。
  • Navigation と API access の違いがコード上で明確になります。
  • 通常の anchor でも、実際のクリック後に browser の標準 download 動作を利用できます。

欠点

  • Endpoint はまだ GET であり、呼ばれると副作用を起こします。
  • 別の client は利用者のクリックなしに URL を呼べます。
  • Path prefix のルールはアプリケーションの URL 規約に依存します。
  • 開発モードだけでは本番の prefetch behavior を確認できません。

実務上の教訓は、prefetch が危険だということではありません。Prefetch は navigation のために有用な仕事をしています。GET endpoint は、クリックがなくても呼ばれることを前提にする必要があります。それができない場合、HTTP method と workflow が実際の操作を正しく表していません。

まとめ

管理画面の Next.js Link により、CSV export が訪問者ごとのバックグラウンド処理になりました。本番の prefetch が GET endpoint を呼び、利用指標をおよそ三倍に増やし、クリックなしで機密性のある顧客データ CSV を生成しました。開発モードでは prefetch しないため、問題が隠れていました。

私は共通リンクコンポーネントを修正し、/api/ URL では通常の <a> 要素を出力するようにしました。これにより、通常のページでは Next.js Link を維持しながら、確認された prefetch 経路を閉じました。

より広い原則は単純です。GET は、利用者の意図を表さない機械からも呼ばれるものとして扱います。Prefetcher、crawler、link preview、scanner は Web の通常の一部です。副作用のある処理には、意図を明示できる設計が必要です。

今後

次は、明示的な作成 request、個別に認可する download、生成ファイルの retention policy を含む export workflow への再設計を計画しています。また、ページ表示、export request、完了した download を同じ event と決めつけずに比較する本番モードのテストと alert も追加したいと考えています。
